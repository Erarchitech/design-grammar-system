Метрики считает `python tools/mapping/evaluate_session.py --session <saved session JSON>`. Сохранённые ответы API — в `evidence/` (без заголовков авторизации; проверка: `grep -i "dgk_\|bearer\|password" evidence/*` пусто).

## Сюжет (≈ 10 минут)

1. **Проблема.** Один и тот же фасад: в GH — потоки HU/GU/PB/PA/F, в Revit — Generic Model по адаптивным точкам с почти одинаковым IFC-экспортом. Ни категория, ни IFC-класс классы DG не разделяют; ручная привязка по индексам уже ломалась (F5, F12, сдвиг выборщиков после A1).
2. **Акт 1 — холодный старт GH.** Все 125 контуров модулей одним потоком (как до исправления F5). Система задаёт два вопроса: пакетное подтверждение очевидных групп и «25 контуров из HU (5 вершин): как HexagonalUnit — R12 нарушено ×25, как GroundFloorUnit — R11 выполняется ×25. Ошибка меппинга или ошибка проекта?». Ответ создаёт профиль `vertexCount = 5 → GroundFloorUnit` с автором и датой.
3. **Акт 2 — обучение.** V2 (F1 = 4400, 140 панелей) и V3 (F1 = 10000): новая геометрия размечается профилями без вопросов; нарушения R2/R7/R1 остаются ошибками проекта (сигналы), а не поводом перепривязать элементы.
4. **Акт 3 — Revit (только чтение).** Выбранные элементы модели читаются через revit-mcp, загружаются в Web UI. Категория и IFC не помогают; помогают имена семейств, численность групп из GH и вопрос «обе роли?» (HexagonalUnit + FacadeModule). Повторное чтение — 0 вопросов.
5. **Акт 4 — валидация.** Классы из меппинга → OBJECT STATE (по имени, не по индексу) → VALIDATOR: V1 11/11 PASS; для контраста ответ «HexagonalUnit — ошибка проекта» даёт R12 ×25.
