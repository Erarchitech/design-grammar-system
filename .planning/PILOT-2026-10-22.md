## 1. Что этот пилот НЕ делает

Пилот использует только *ограниченный опережающий срез* v14 вручную подтверждённого нормативного сценария.
- **Не закрывает и не помечает требования.** Ни один ID (DGCL/DGKN/DGBN/DGST/HOST/N*) не получает PASS от пилотного прогона. Фазы 1301 (приёмка открыта), 1302 (планы проверены, продукт не реализован), 1303/1304/1306 (не начаты), 1309 (hosting readiness открыт) сохраняют свои обязательства полностью.
- **Не является milestone transition.** v13 остаётся Current Milestone; v14 остаётся изолированным future milestone. `.planning/phases/`, STATE.md metadata и REQUIREMENTS.md не изменяются этим планом.
- **Не обещает внешний публичный ingress.** Аудит 2026-10-15: внешний пилот NO-GO (Caddy только `127.0.0.1:443`, нет runtime-bundle harness, нет frozen image digests, права ALNST на web-embedding не подтверждены, backup/restore — планы). См. [1309-03-SUMMARY.md](phases/1309-dg-hosting-package-without-local-ollama/1309-03-SUMMARY.md).

## 2. Площадка отложена — принятое решение, не утверждённая топология

На вопрос «где размещаем пилотный сервер?» были предложены: **1** — внешний сервер/VPS; **2** — имеющаяся машина в доверенной сети с VPN; **3** — пока не выбирать площадку, продолжать только переносимый пакет и offline-проверки, дату развёртывания оставить неподтверждённой. Ответ владельца: **«3»**.

Прежняя рекомендация trusted-network варианта A не была подтверждена владельцем и больше не задаёт рабочую топологию. VPS и доверенная сеть остаются кандидатами; ни один не выбран. Неизвестные host/DNS/TLS/доступы не блокируют независимую offline-подготовку, но блокируют зависимые runtime-этапы. HOST-блокеры из §1 не считаются снятыми или исключёнными из будущего допуска.

Переносимый CPU-only профиль проверяется в порядке **base → multi-user → hosted** с синтетическими параметрами, без Docker daemon/service операций. Двухфайловый local-профиль остаётся без изменений; его нельзя считать CPU-only hosted-пакетом. Выбор DNS, сертификатов и способа доступа последует после выбора площадки.

**HTTP gate сохранён:** GH сейчас использует Bolt (`DG/src/DG.Core/Data/Neo4jRuleRepository.cs`), тогда как DGBN-01 требует HTTP repository path. Доверенная сеть/VPN не доказывает tenant-изоляцию и не разрешает обход этого требования. Прежняя формулировка «это принимается» отозвана как несогласованная: Bolt-direct не является утверждённым отклонением. Для многопользовательского пилота нужен проверенный HTTP subset; любое исключение требует отдельного решения владельца и проверки доступа/изоляции. Bolt наружу не публикуется.

Операционный предел будущего развёртывания: **один data-service worker/instance** — `data-service/auth.py` использует `threading.RLock` + atomic replace, не distributed store. Горизонтальное масштабирование вне пилота.

## 4. Порядок подготовки и условные live-этапы

Цель 22.10 сохраняется; прежние окна 16–22.10 не являются подтверждённым графиком запуска. Сейчас разрешён только первый ряд. Переход к каждому зависимому этапу требует его фактических prerequisites и отдельной авторизации; отложенная площадка не делает готовый runtime или нормативный pipeline существующим.

| Этап | Работы | Результат и условие перехода |
|---|---|---|
| Сейчас — offline | Переносимый пакет из точной committed revision; allowlist/manifest и Compose-проверки на синтетических входах; подготовка runbook/limitations; фиксация блокеров | Статические результаты и честный статус draft, не runnable release; наблюдения §9 |

| Источники — условно | После применимого допуска `1302-08` и выбора разрешённых источников: DeGram → source/revision/citation → подтверждённое правило; EU + СП РФ | Две source-linked записи со свежим evidence; неподписанный entry gate блокирует зависимую реализацию/операции |
| GH и Revit — условно | Подтверждённые typed bindings и DesignState на обеих платформах; reuse `DesignStateBindingService`/`RuleEvaluator`; negatives: ambiguous/same-name, два объекта с разными значениями, stale, missing counterpart, unit mismatch | Сохранённые состояния и результаты; HTTP/auth/изоляция и native-live gates обязательны |

При неподписанном `1302-08` разрешены только независимые offline-контракты/синтетические фикстуры; ручной журнал не обходит entry gate и не разрешает создание source-linked продуктовых правил.

## 5. Критерии live-допуска ревьюверу (цель 22.10, дата не подтверждена)

Передача состоится, если demonstrated live, а не offline-тестами:

1. На выбранной и отдельно разрешённой площадке reviewer входит через браузер и отдельный ПК DeGram, видит только свой проект; чужой проект и отозванный грант дают отказ. GH HTTP-path проверен; Bolt-direct не считается принятым исключением.
2. Оба правила читаются в web с указанием источника (документ, пункт, цитата/координаты) и статуса подтверждения человеком.
3. Для каждого правила видна подтверждённая пользователем привязка: GH-параметр и Revit-параметр; same-name/ambiguous кейсы дают явный отказ, а не произвольную привязку.
4. Прогон валидации из GH и из Revit сохраняет DesignState/Run; reviewer видит измеренные значения, units и канонические статусы; пустая выборка → `no_population`, неразрешимая привязка → `unknown`, неподдержанный конструкт → `unsupported`; ни один из них не отображается как `passed`/`failed`.
5. Reviewer восстанавливает цепочку правило → источник → привязка → состояние → результат **без чата автора**.
6. Pilot pack содержит перечень открытых gates и ограничений: HTTP, `1302-08`, один worker, ALNST, HOST/runtime/restore, источник и редакция данных. Раскрытие ограничения не равно его принятию и не отменяет gate.

Провал или отсутствие проверки любого обязательного пункта → NO-GO работающего пилота. Подготовленный offline-pack может передаваться только как материал для проверки подготовки, не как замена live-пилоту.

2. **Источники норм — OPEN:** выбрать точные EU и СП РФ (документы/URL, редакции, права). Два локальных файла и ручное выделение пунктов в §3 — предложенное ограничение, ещё не решение владельца; автоматический импорт и извлечение остаются v14.
3. **Фикстуры — OPEN:** GH-определение и Revit-модель, класс, typed параметр и единицы на каждой платформе. Обе платформы обязательны; их live-доступ сейчас не разрешён.

6. **Reviewer — OPEN перед независимой приёмкой:** аккаунт/ПК/доступ и реальное evidence; имя и hardware inventory не нужны для упаковки. Дата live-передачи к 22.10 остаётся неподтверждённой, цель не объявлена выполненной или перенесённой.

## 9. Фактические результаты offline-этапа (наблюдено 2026-10-15)

Запущено только на синтетических входах; ни один контейнер/сервис/live-операция не выполнялись. Фиксация — для отличия проверенного от заявленного; это не release readiness.

- `python deploy/hosted/tests/run_required.py test_compose_profile.py` — exit 0, discovered=4, ran=4, failures=0, errors=0, skipped=0 (структура base/multi-user/hosted: CPU-only, no Ollama в hosted, edge-порты/origins).
- `... run_required.py test_release_manifest.py` — exit 0, 16/16, 0 skip (allowlist/manifest/blob-vs-commit негативы).
- `... run_required.py test_edge_routes.py` — exit 0, 8/8, 0 skip (интерполяция/негативные shape-mutation; Windows-фикстуры).
- **Сборка из текущей рабочей политики — BLOCKED:** точный commit `8a6ddf5c79e1cb460450f05bbc60568955787785`; assembler exit 1, `selection policy differs from exact commit`. Рабочая политика содержит 43 inputs против 42 в HEAD и отличается даже после нормализации переводов строк. Предсуществующие правки `deploy/hosted/{assemble.py, validate_manifest.py, release-allowlist.json}` не изменялись этой работой и не коммитились.
- **Отдельная попытка из scratch-клона HEAD тоже BLOCKED, но по другой причине:** при clean Git status checkout политики сохранил 73 CRLF, committed blob — 0 CRLF; raw bytes не совпадают. Установка `core.autocrlf=false` и повторный reset не изменила существующие checkout-байты. Прямой вызов assembler подтвердил `selection policy differs from exact commit`. Поэтому эта попытка не доказывает, что сборка из канонических committed входов невозможна; смешивать её с семантическим отличием рабочей политики нельзя.
- **Пакет не создан:** вызовы `validate_manifest.py` вернули exit 1 против отсутствующего output directory — это не проверка целостности собранного пакета и не тест frozen-release отказа. 28 успешных проверок выше относятся к текущим offline-тестам на синтетических fixtures, не к финальному архиву.
- **Следующее независимое действие:** продолжать offline-подготовку; exact-source сборка остаётся открыта. Возможный инженерный путь — канонические committed inputs без checkout-конверсии с обязательной проверкой полноты allowlist и ALNST. Он не разрешает молча убрать referenced font или ослабить policy. Для включения предсуществующих WIP потребуется отдельно согласованная интеграция/commit; Git commit и push/publication — разные разрешения. Немедленный выбор площадки или разрешение на commit не являются prerequisites остальных offline-проверок.
- `deploy/hosted/tests/run_bundle_runtime.py` (runtime harness) отсутствует; `test_bundle_runtime.py` fail-closed и вернёт ненулевой BLOCKED без owner sandbox approval (`DG_HOSTED_SANDBOX_APPROVAL_REF`/`SPEC`, целевая машина `DESKTOP-OS4Q8CP`). Runtime-доказательство не подменяется синтетикой.
