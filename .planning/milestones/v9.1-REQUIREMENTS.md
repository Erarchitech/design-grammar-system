# Requirements: Design Grammar System v9.1 — DG Canvas Chatbot Node

**Defined:** 2026-07-27
**Status:** Future (isolated — defined now, activates after v9.0's canvas-intelligence phases land; do NOT activate while v9.0 is in flight)
**Core Value:** The architect drops one node on the Grasshopper canvas and talks to the Design Grammars platform. Selecting components *is* the context; `/dg-` commands do the deterministic work; the LLM the architect chose on the platform answers, and nothing reaches the canvas or Neo4j without an explicit confirmation.

> **Isolation contract:** This document and `v9.1-ROADMAP.md` are the only v9.1 artifacts. Nothing here modifies `.planning/phases/`, `STATE.md`, `.planning/REQUIREMENTS.md`, or PROJECT.md's Current Milestone (which stays **v9.0**). Phase numbers are **910–917** per the `vX.Y → X·100+Y·10` convention. Activation happens via `/gsd-new-milestone` once v9.0's Phases 32–36 are verified.

**Reference product:** [Ant](https://rhino-ant.ai/) — canvas widget → dockable chat → selection-based context → on-canvas proposals. DG differentiates on (a) an explicit `/dg-` slash-command namespace mapped to deterministic handlers, and (b) a visible, architect-chosen LLM surfaced from the platform gateway. Research: `.planning/research/v9.1-CHATBOT-NODE-RESEARCH.md`.

**Depends on (all v9.0):** Phase 32 (Computgraph serialization core — `CanvasAnnotationParser`, `ComputgraphContextSerializer`, `cgContextJson v1`), Phase 33 (DG Canvas Bridge — listener, UI-thread marshalling, `gh_bridge.py`), Phase 34 (tagging components — `EntityTagComponent`, `ObjectMarkerComponent`, `CanvasAnnotationNameFactory`), Phase 35 (recognition + `PreviewRegistry` + preview groups), Phase 36 (`POST /computgraph/publish`). Also v8.1/v9.0 Phase 28 (`llm_gateway.py`, `/llm/settings`) and v8.2 Phase 825 (CONNECTOR token → project).

## v9.1 Requirements

### Chatbot Node and Auto-Listening Lifecycle (CHTN) — Phase 910

- [ ] **CHTN-01**: Dropping the DG CHAT component on the canvas starts the DG Canvas Bridge listener automatically via `AddedToDocument` — there is no `Run` boolean and no `Port` input to wire; the architect performs zero setup gestures between placing the node and using it
- [ ] **CHTN-02**: The listener is a process-wide singleton: a second DG CHAT component, a second open Grasshopper document, or a co-existing legacy DG CANVAS LISTENER attaches to the running listener instead of racing to bind the port — no instance ever reports a bind error caused by another DG component
- [ ] **CHTN-03**: When the port is unavailable for an external reason, the node degrades to a clearly-labelled non-listening state with a What+Where+How-to-fix message and remains usable for non-canvas chat — it never throws, never blocks, and never leaves a half-open socket
- [ ] **CHTN-04**: The listener shuts down cleanly on `RemovedFromDocument` and on `DocumentContextChanged` (unloaded/closed), releasing the port; re-adding the component in the same Rhino session starts it again successfully
- [ ] **CHTN-05**: Listener state (listening / not listening / degraded, plus port) is readable from the component itself without a `Run` input — via the component's own status output and its canvas rendering — so the architect can diagnose without opening the chat window

### Eto Chat Window and Session Shell (CHTW) — Phase 911

- [ ] **CHTW-01**: Double-clicking the DG CHAT component opens a modeless Eto.Forms chat window (via a custom `GH_ComponentAttributes.RespondToMouseDoubleClick`); the window can be dockable in Rhino and is built on Eto so it runs on both Windows and macOS
- [ ] **CHTW-02**: The chat window header always shows three live values: the active LLM (provider + model, read from the platform's `/llm/settings`), the active project name (derived from the CONNECTOR platform token), and the listener connection status — each updating when the underlying value changes, without reopening the window
- [ ] **CHTW-03**: Sending a message never blocks the Grasshopper solution: `SolveInstance` stays fast and side-effect-free, the LLM call runs off the UI thread, and Rhino remains fully interactive (canvas pan/zoom, other components solving) for the whole duration of a slow or hanging request
- [ ] **CHTW-04**: Every update the chat or canvas receives from a background thread is marshalled through `RhinoApp.InvokeOnUiThread` — no Eto control or Grasshopper document object is ever touched off the UI thread
- [ ] **CHTW-05**: The conversation transcript survives closing and reopening the chat window within a Rhino session, and an in-flight request can be cancelled from the window, leaving the chat usable
- [ ] **CHTW-06**: When no LLM is configured, the project is unresolved, or the platform is unreachable, the header shows the specific unset/unreachable state and message sending is disabled with an actionable reason — never a silent failure or a generic error

### Selection Context and Free-Form Ask (CTXS) — Phase 912

- [ ] **CTXS-01**: The current Grasshopper canvas selection is the chat's context — the architect selects components, parameters, or groups, and the window shows what is captured (count and a readable summary) before the message is sent
- [ ] **CTXS-02**: Selected objects serialize through the existing v9.0 path (`CanvasAnnotationParser` + `ComputgraphContextSerializer` → `cgContextJson v1`) — v9.1 adds no second canvas-serialization implementation
- [ ] **CTXS-03**: The architect can ask free-form questions about the selection and receive answers grounded in the serialized structure and the DG Computgraph concept catalog — including which entities are already tagged, which are untagged, and how they relate
- [ ] **CTXS-04**: With an empty selection the chat still works, scoped to the whole definition, and says so explicitly — it never silently sends an empty context or a whole-canvas payload the architect did not ask for
- [ ] **CTXS-05**: Context sent to the LLM respects a stated token budget; when a selection exceeds it, the chat reports what was truncated rather than sending a silently trimmed payload

### `/dg-` Slash Command Framework (SCMD) — Phase 913

- [ ] **SCMD-01**: Typing `/` in the chat input opens an autocomplete list of available `/dg-` commands with one-line descriptions, filtering as the architect types; selecting one inserts it with its argument hint
- [ ] **SCMD-02**: Commands are declared in a single schema-driven registry (name, description, typed arguments with required/optional, risk level) that drives autocomplete, argument hints, validation, and `/dg-help` from one source — adding a command requires no edits to the chat UI
- [ ] **SCMD-03**: A `/dg-` command dispatches to a deterministic handler and never routes through the LLM — the same command with the same arguments against the same canvas produces the same result
- [ ] **SCMD-04**: Argument errors and unknown commands are rejected before anything executes, with a usage line and a pointer to `/dg-help`; `/dg-help` with no arguments lists every command, and with a command name shows its full usage
- [ ] **SCMD-05**: Commands are risk-classified: read-only commands run immediately; preview-only commands write nothing outside temporary canvas previews; mutating and publishing commands first show a summary of exactly what will change and require an explicit confirm, with cancel leaving no trace
- [ ] **SCMD-06**: Every canvas mutation performed by a command is wrapped in a Grasshopper undo record, so one Ctrl+Z reverts the whole command's effect

### Tagging and Marking Commands (TAGX) — Phase 914

- [ ] **TAGX-01**: Tagging and marking logic is extracted from `EntityTagComponent` and `ObjectMarkerComponent` into shared services, so the component and the chat command invoke one code path — the annotation grammar (`CanvasAnnotationNameFactory`) remains the single source of truth for names
- [ ] **TAGX-02**: A tagging command wraps the current canvas selection into a convention-named, convention-coloured group for a chosen entity kind (Proc/Pat/Var/Const/Emg/IntF), with the same auto-index assignment and Pattern nesting behaviour as DG ENTITY TAG, undoable
- [ ] **TAGX-03**: A marking command creates or updates the `OBJECT - <NAME>` and `<n>_ALGORITHM` scribbles idempotently, matching DG OBJECT MARKER's behaviour including the optional `dg:Class` IRI binding
- [ ] **TAGX-04**: Tags created from chat are indistinguishable from component-created tags downstream — they serialize with `source: tagged` and re-parse identically on the next extraction
- [ ] **TAGX-05**: The architect can ask the chatbot to tag a selection in natural language and receives a proposed command with its arguments filled in, which executes only after confirmation — natural language never silently mutates the canvas

### Recognition, Confirm and Publish Commands (RCMD) — Phase 915

- [ ] **RCMD-01**: A recognition command runs the existing Tier-0/Tier-1 recognition pipeline over the selection (or the whole definition), rendering proposals as the v9.0 temporary preview groups on canvas, and lists them in the chat with kind, name, member count, and confidence
- [ ] **RCMD-02**: The chatbot can volunteer its own recognised entities for a selection the architect asks about — surfaced as proposals with rationale, subject to the same preview-then-confirm path, never auto-applied
- [ ] **RCMD-03**: The architect accepts or rejects proposals from the chat individually or in bulk; accepted proposals become permanent convention groups carrying `source: recognized` provenance, rejected ones are removed cleanly, and partial acceptance is supported
- [ ] **RCMD-04**: A publish command publishes the confirmed structure to the Computgraph via the existing `POST /computgraph/publish`, showing a pre-publish summary (entity counts by kind, target project, stale entity ids) and requiring confirmation; the result reports what was written
- [ ] **RCMD-05**: A status command reports, in one message, the current listener state, active LLM, active project, selection summary, pending proposal count, and last publish result
- [ ] **RCMD-06**: Nothing reaches Neo4j without an explicit confirm in the chat, and entities the pipeline cannot classify are reported as unrecognised with their member ids — never invented, never silently dropped

### Legacy Component Deprecation (DEPR) — Phase 916

- [ ] **DEPR-01**: DG CANVAS LISTENER, DG ENTITY TAG, DG OBJECT MARKER, DG STRUCTURE CONFIRM, and DG COMPUTGRAPH PUBLISH keep their existing GUIDs and continue to function unchanged — an existing `.gh` file opens and solves with zero missing-component placeholders
- [ ] **DEPR-02**: The five superseded components are marked deprecated and hidden from the Grasshopper ribbon (still placeable from search and still loadable from saved files), and each surfaces a remark naming DG CHAT as the recommended replacement
- [ ] **DEPR-03**: Release notes document the supersession per the established convention: which component each `/dg-` command replaces, that no GUID changed, and that no canvas breaks — explicitly contrasted with the v7.0 CLASSIFICATOR and v8.2 CONNECTOR GUID breakages
- [ ] **DEPR-04**: CLAUDE.md, `spec/GRASSHOPPER.md`, and the ui-v2 DG API Documentation region describe the DG CHAT node, the chat window, and the full `/dg-` command reference

### Integration and E2E (CHIN) — Phase 917

- [ ] **CHIN-01**: A live-Rhino E2E runs the whole chain from one node: drop DG CHAT → it listens → double-click → header shows LLM/project/status → select components → ask a question → `/dg-mark` → `/dg-tag` → `/dg-recognize` → confirm → `/dg-publish` → the structure is visible in the ui-v2 Computgraph layer for the active project
- [ ] **CHIN-02**: Switching the LLM provider or model on the Design Grammars platform is reflected in the chat window header and in subsequent answers without restarting Rhino or reloading the plugin
- [ ] **CHIN-03**: The legacy component path is regression-verified: a `.gh` built with the five deprecated components produces the same tags, proposals, and published Computgraph as the equivalent chat-driven flow
- [ ] **CHIN-04**: Failure paths are verified live — platform unreachable, no API key configured, port occupied, LLM timeout, publish rejected — each producing an actionable What+Where+How-to-fix message with Rhino left responsive

## Future Requirements

Deferred beyond v9.1, in rough priority order:

- **Chat-driven rule authoring** — ingesting or editing a Design Rule from the Grasshopper chat (needs v9.0 Phase 31 RING to land first)
- **Structure-validation commands** — `/dg-validate` over the published Computgraph (depends on v9.0 Phase 37 SVAL)
- **Multi-document / multi-project chat sessions** — one window serving several open definitions
- **Transcript persistence across Rhino sessions** — saved with the `.gh` or in platform storage
- **Voice / `Shift+Shift`-style global hotkey** to summon the chat without locating the node
- **WebView chat surface reusing the ui-v2 design system** — revisit if the native Eto surface proves visually limiting

## Out of Scope

Explicit boundaries for v9.1, with reasoning:

- **Creating or rewiring native Grasshopper components from the chat** — this is v10.0's `BWRT` (Bridge Write Commands) scope, already planned with a component knowledge base and a writes-off-by-default posture. v9.1 writes DG artefacts only (tag groups, scribbles, preview groups, publishes). Pulling it forward would duplicate a planned milestone.
- **Script generation / editing (Ant's Script and Edit modes)** — v10.0 `SGEN`/`SEDT`. Same reasoning.
- **Removing or re-GUIDing the five superseded components** — explicitly rejected in favour of deprecated-fallback, so no saved canvas breaks. Revisit only in a later milestone once chat adoption is proven.
- **A WebView/React chat surface** — Eto native was chosen for cross-platform reach and zero asset-packaging cost. Listed under Future Requirements rather than pursued now.
- **A second canvas-serialization implementation** — v9.1 re-fronts the v9.0 pipeline; it does not rebuild it.
- **Routing `/dg-` commands through the LLM** — commands must be deterministic. Natural-language *intent* may propose a command, but execution is always handler-driven and confirmed.
- **Changing the DG Canvas Annotation Convention** — `CanvasAnnotationParser` / `CanvasAnnotationNameFactory` stay the single source of truth; v9.1 consumes the grammar, never forks it.
