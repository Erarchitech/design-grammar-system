Close GAP-1 / CR-01: make the C# canonical-JSON writer preserve a decimal's stored scale exactly as
Python's `format(Decimal, "f")` does, and add the golden vector that proves it — the vector whose
absence let the defect ship green in both suites.

most ordinary class of architectural measurement value there is.

## Reference direction — stated explicitly

**Python is the reference; the C# leg is what changes.** `data-service/canonical_json.py`'s
`_canonicalize_number` uses `format(value, "f")` on a `Decimal`, which preserves the value's stored
scale exactly. `spec/EVIDENCE-CONTRACT.md` §6 rule 2's wording ("rendered as fixed-point decimal
strings via `decimal` / `Decimal`") was written to that behavior, and
`data-service/tests/test_canonical_json.py` already pins `canonicalize(Decimal("2.50")) == "2.50"`
as a direct assertion. The Python side is correct, is already asserted, and is not touched by this
plan. `DG/src/DG.Core/Contracts/CanonicalJsonWriter.cs` is the side that diverges and the side that
is edited.

This reference direction also settles what "correct" means for the new golden vector: the vector's
`canonical` string is whatever the Python leg already produces, and the C# leg must be made to match
it — not the reverse.

## Contract-text change — declared, not silent

Task 3 adds a sentence to `spec/EVIDENCE-CONTRACT.md` §6 rule 2 making the scale-preservation
requirement explicit. Per the frozen-artifact constraint this is declared here rather than done
quietly: it is a **clarification of an existing rule, not a change to one**. The behavior the
contract intends is unchanged — Python has always preserved scale and §6's stated purpose is
byte-parity — so `canonicalizationVersion` stays **1** and no already-recorded hash becomes
meaningless. Had the rule's meaning actually changed, D-07's reversibility note would require a
`canonicalizationVersion` bump; it does not apply here. The shape and vocabulary of the contract and
of `spec/evidence-contract.schema.json` are untouched.

branching on integrality.

Derive the scale from the decimal's own representation: `decimal.GetBits(value)` returns four ints,
and the scale is bits 16-23 of the fourth element — `(decimal.GetBits(value)[3] >> 16) & 0xFF`.
Assign that to an `int scale`.

When `scale == 0`, append `value.ToString(CultureInfo.InvariantCulture)` — a scale-0 decimal has no
decimal point in its invariant string form, which is what rule 2 requires for integers and what
`format(Decimal("3"), "f")` returns.

Otherwise append `value.ToString("F" + scale, CultureInfo.InvariantCulture)`. The `F{n}` specifier
emits exactly `n` fractional digits with no exponent and no group separators, so a scale-2 decimal
renders `100.00` and a scale-1 decimal renders `82.5`.

on every `ToString` call.
