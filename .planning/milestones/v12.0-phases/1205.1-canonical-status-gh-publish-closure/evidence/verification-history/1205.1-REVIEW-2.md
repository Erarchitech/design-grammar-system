### CR-01-R2 — BLOCKER / critical: admitted escaped surrogate по-прежнему ломает evidence/SHACL response; новый C# traversal может бросать вне catch

**Файлы (actual current source):**
- `C:/Users/Admin/source/repos/design-grammar-system/data-service/evidence_contract.py:226–265,322–345`.
- `C:/Users/Admin/source/repos/design-grammar-system/data-service/app.py:1185–1216,1309–1310`.
- `C:/Users/Admin/source/repos/design-grammar-system/DG/src/DG.Core/Contracts/EvidenceEnvelopeReader.cs:47–49,72–75,83–87,100–115`.

**Проблема.** Python guard проверяет числа и глубину, но не корректность Unicode строк/ключей; `json.loads` допускает escaped lone surrogate. В arbitrary `sourceRepresentation` он проходит full schema/model/read и сохраняется в original dict. Реальный `JSONResponse` затем использует UTF-8 и падает с `UnicodeEncodeError`. Это тот же corrupt-read → response seam, ради которого итерация добавляет общий guarded decoder, а не требование новой бизнес-функции или универсального security audit.

В C# новый `JsonResources` обращается к `property.Name` **до** version dispatch. Для `"\ud800"` как имени property `System.Text.Json` бросает **InvalidOperationException**, тогда как `TryRead`/`IsStrictEnvelope` ловят только `JsonException`. Repository `BuildPerObjectVerdicts` имеет внешний catch и действительно возвращает absent; **не заявляю crash repository/view в C#**. Но публичные guards сами не выдерживают этот malformed input; `strict` harness завершается необработанным exception.

**Независимое воспроизведение:** взять retained valid full envelope и добавить:

```json
"sourceRepresentation": {"x": "\ud800"}
```

или:

```json
"sourceRepresentation": {"\ud800": 1}
```

- Для каждого exact token `1`, `1.0.0`, `2.0.0` настоящая `parse_evidence_envelope` (неизменённый AST node с настоящим `evidence_contract`) возвращает dict; `JSONResponse({'evidenceEnvelope': result})` бросает `UnicodeEncodeError`: **6/6 cases**.
- `_parse_shacl_report` с `{"source":{"x":"\ud800"}}` и с surrogate-key также возвращает dict; response падает: **2/2 cases**. NaN sibling control правильно даёт None/renderable response.
- Actual existing C# harness `strict` для surrogate-key: **3/3 process failures**, `InvalidOperationException: Cannot read incomplete UTF-16 JSON text as string with missing low surrogate`, stack указывает `JsonResources` line 114. C# repository `read` этих ключей даёт absent, Python принимает — подтверждённое расхождение.
- При surrogate **value** в unused metadata C# projection также может принять envelope; это не устраняет Python response crash.

Evidence: `evidence/review-2-probe.json`, cases `unpaired-surrogate-*`, отдельный раздел `shacl`. Это ASCII raw JSON с escape, не ошибка transport encoding/non-ASCII консоли. Нового POST/GET к сервису не выполнялось: failure доказан настоящими parse и response functions; wiring view подтверждено исходником.

**Исправление.** Узко согласовать Unicode admission на этом же raw/persisted boundary: проверять ключи и string values до model/response, отвергать непарные surrogates без silent replacement; сохранить валидные surrogate pairs/обычные Unicode names и их duplicate-equivalence. C# decoder traversal должен возвращать false на такой decode failure (проверка либо узкий catch соответствующего исключения), не полагаться на внешний repository catch. Добавить escaped key/value cases для old/v2, SHACL response и public strict/read guards. Не менять hash/identity normalization и не вводить blanket catch на весь handler.

**Происхождение:** Python latent sibling того же заявленного safe-corruption contract, не доказанное новое regression относительно pre-fix. C# `property.Name` на arbitrary metadata — новая traversal surface этой итерации. Оба остаются внутри рассматриваемого admission/resource boundary.

### WR-01-R2 — WARNING / warning: pre-dump finite validation пропускает tuple в `dict[str, Any]`, NaN/Infinity незаметно превращаются в null

**Файлы:**
- `C:/Users/Admin/source/repos/design-grammar-system/data-service/evidence_contract.py:226–247,348–368,456–474`.
- Обещание in-memory admission: `C:/Users/Admin/source/repos/design-grammar-system/spec/EVIDENCE-CONTRACT.md:230–233,249–256`.

**Проблема.** Iterative traversal раскрывает `BaseModel`, `dict` и `list`, но не `tuple`. В `source_representation: dict[str, Any]` tuple допустима публичным Python API и сериализуется Pydantic как JSON array. Поэтому именно добавленный до JSON-mode dump guard не видит NaN/Infinity внутри неё, а последующий dump необратимо заменяет nonfinite на null. Это остаток причины original CR-03, не требование изменить approved legacy constructor defaults.

**Выполнено на текущих functions:**

```python
meta = {'x': (float('nan'),)}
m = build_envelope_with_rule_results(
    'p', 'd', 's', '1', 'test', [], [], source_representation=meta)
# Нет исключения; m.sourceRepresentation == {'x': [None]}.

old = build_envelope('p', 'd', 's', '1', 'test', [],
                     source_representation={'x': (float('inf'),)})
validate_envelope(old)  # Нет исключения; JSON-mode metadata содержит [null].
```

Два tuple controls (NaN/Infinity) допускаются обоими gates; соответствующие list controls правильно отклоняются. Evidence: `review-2-probe.json` → `inmemory` (4 cases, каждое проверяет factory и legacy validator). Дополнительный pure probe подтвердил: `read_envelope_dict` с tuple+NaN в metadata также принимает original in-memory dict, а `JSONResponse` бросает ValueError.

**Влияние/уровень.** Нарушено явное обещание reject-before-coercion для in-memory admission; происходит silent metadata loss. Raw HTTP/`json.loads` создают lists, не tuples, поэтому **не объявляю это новым HTTP exploit или raw POST write bypass**. На текущий GH happy path влияние не доказано; поэтому WARNING, а не ещё один critical.

**Исправление.** До любого JSON-mode dump рекурсивно/итеративно проверять поддерживаемые сериализатором array containers, как минимум tuple наряду с list, с тем же container-depth accounting; либо явно отвергать неподдержанные in-memory формы до сериализации. Не переписывать NaN в null и не менять historical constructor defaults. Добавить factory/validate_envelope tuple controls и positive finite tuple control.
