Close CR-02 (unescaped pipe delimiter permitting identity collisions) and the `project`-in-hash gap in ONE coordinated re-derivation across both languages, updating every pinned identity literal in lockstep.

Output: length-prefixed hash encoding in `DgIdMintingService`, `DesignStateIdGenerator`, and `dg_identity.compute_dg_id`; `project` folded into DesignState hashes where legitimately available; new golden vectors and collision regression tests in both suites.
</objective>

  <behavior>
    - Encoding two different tuples that share a naive pipe-join must produce two different identity strings. The canonical adversarial case: tuple A = `("a|b", "c", "d")` and tuple B = `("a", "b|c", "d")`. Both naively join to `a|b|c|d`. After length-prefixing they must differ.
    - Encoding the same tuple twice must produce the identical string (determinism preserved).
    - The C# and Python encoders must produce the identical string for the same tuple — proven by the shared golden dgId literal.
    - A null or absent optional component must encode distinguishably from an empty-string component.
  </behavior>

  <action>
Introduce one length-prefix encoding scheme and apply it in both languages. The format, per CONTEXT.md's Claude's Discretion grant, is: for each component, emit the component's character length in invariant decimal, then a colon, then the component's raw text; join the resulting units with a single pipe. So the tuple `(p1, frame.gh, cg:1:proc:11_Proc)` encodes to `2:p1|8:frame.gh|17:cg:1:proc:11_Proc`. Because every unit is preceded by an unambiguous length, a pipe inside a component can no longer shift the boundary between components.

Represent an absent (null) optional component distinctly from an empty one. Use the literal unit `-1:` for null and `0:` for empty string. State this rule in the helper's doc-comment in both languages so the two encoders cannot drift.

In C#, add a private static `EncodeHashInput` accepting the ordered components and returning the encoded string; place it next to `HashToHex16` in `DesignStateIdGenerator`, and add the matching encoder to `DgIdMintingService`. Both must implement the identical rule — put the rule in a doc-comment in each, citing the other file by name so a future editor knows they are twinned.

In Python, add a module-private `_encode_hash_input(*parts)` to `dg_identity.py` implementing the identical rule, with a docstring naming both C# files as its twins.

Use invariant/ordinal semantics for the length: count characters, not bytes, and format the integer with invariant culture in C# so a non-English locale cannot change the digits.

Change `DgIdMintingService.Mint` to build its hash input through the new encoder rather than the naive interpolation, keeping the existing argument-validation and exception behavior exactly as-is. Change `dg_identity.compute_dg_id` the same way.

Then write the collision regression tests BEFORE reading the new golden value, so they encode intent rather than observed output:

In `DgIdMintingServiceTests.cs`, add `Mint_PipeBoundaryShift_ProducesDifferentDgId` asserting `Mint("a|b", "c", "d")` and `Mint("a", "b|c", "d")` are not equal. In `test_dg_identity.py`, add `test_compute_dg_id_pipe_boundary_shift_does_not_collide` asserting the same two calls differ. Both tests must be written such that they would FAIL against the pre-change naive-join implementation — confirm this claim by reasoning about the old encoding in the test's own comment.

Do not update the golden vector literal in this task; task 2 does that once, after all encoding changes land, so the value is computed against the final contract.
  </action>
