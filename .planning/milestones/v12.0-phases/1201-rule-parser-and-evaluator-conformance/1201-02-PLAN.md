<objective>
Complete the evaluator's typed-outcome surface. Plan 01 proved the mechanism on the unsupported
builtin; this plan applies it to the three remaining collapse sites and to the publish boundary.

The four outcomes currently collapsed into one boolean, with the exact site for each:

| Site | True meaning | Today | Target (D-05 table) |
|---|---|---|---|
| `RuleEvaluator.cs:24-34` | empty population | `Passed=false` | `no_population` (D-06) |
| `EvaluateAtom:100` / `ResolveArgValue:148` | binding unresolvable | throws → failing binding | `unknown` (D-08) |
| `EvaluateAtom:104-105` | ObjectPropertyAtom / unclassifiable atom | bare `return true` | `unsupported` (D-14) |
| `ValidationPublishPackageBuilder.cs:34-42` | no result exists for the rule | `Passed=false` | `not_evaluated` |

Purpose: after this plan, `failed` is expensive to say. Every one of the five situations the D-05
table distinguishes is separately reportable from the C# evaluator, and the catch-all at
`RuleEvaluator.cs:52-56` — the single point where four distinct outcomes became `failed` — no longer
has ordinary outcomes routed through it.

Output: an evaluator that emits the full typed vocabulary, and a publish package that carries the
typed status to its consumer.

  documented non-authoritative. Canonical→boolean is lossy-and-defined; boolean→canonical is
  forbidden, so nothing here may infer a status from an existing boolean.

**Decision recorded, reversibility one-way (D-06/D-07/D-08 semantics):** these three status
assignments are not re-litigated at execution time. They are transcribed verbatim from the D-05

  <behavior>
    - EvaluateRule with an empty bindings list returns Status = NoPopulation, Passed = false, and an
      empty FailingBindings.
    - Its Message states the population was empty and does not use the word violated.
    - EvaluateRule over a binding whose row lacks the variable the body references returns
      Status = Unknown, not Failed, and that binding is not in FailingBindings.
    - A builtin argument that is a variable absent from the binding row also yields Unknown, not
      Failed — covering the ResolveArgValue path as well as the EvaluateAtom path.
    - A rule over two bindings, one unresolvable and one genuinely violating, rolls up to Failed
      (shipped precedence puts Failed above Unknown) and FailingBindings contains only the violating
      one.
    - A rule over two bindings, one unresolvable and one satisfied, rolls up to Unknown — an
      unresolvable binding never decays into passed either.
  </behavior>
  <action>
At `RuleEvaluator.EvaluateRule`'s zero-binding early return, set `Status = EvidenceStatus.NoPopulation`
and keep `Passed` derived through `EvidenceEnvelopeFactory.ToLegacyBoolean`, which yields false.
Reword the message so it no longer reads as a verdict: state that the rule was evaluated and its
binding population was empty, per `spec/EVIDENCE-CONTRACT.md`'s `no_population` semantics ("a real,
distinguishable evaluation outcome, not a failure and not a non-evaluation"). Leave `FailingBindings`
empty.

Replace the two `InvalidOperationException` throws for a missing binding — `EvaluateAtom` at `:100`
and `ResolveArgValue` at `:148` — with the plan 01 `BindingOutcome` carrying
`EvidenceStatus.Unknown`. `ResolveArgValue` currently returns `object?`; change it to a small
private try-shape (`bool TryResolveArg(AtomArg, BindingRow, out object? value)`) so the caller in
`EvaluateBuiltin` can return an `Unknown` outcome rather than having a throw propagate. Name the
try-method after the existing `TryResolveVariableValue` in the same file so the file stays internally
consistent; both are net7.0-safe `Try*` shapes already in production here.

The Detail on an `Unknown` outcome uses the What+Where+How-to-fix wording pattern from
`ErrorMessageTemplates`: what (a variable the rule body references has no value in this binding row),
where (the variable name and the atom), how to fix (supply the value for that variable in the
binding source, or accept the typed non-verdict).

With both of these done, the `catch (Exception ex)` block is now reachable only by a genuinely
unexpected fault. Tighten its doc-comment to say so explicitly and to name the four outcomes that
used to flow through it and no longer do. Keep it emitting `EvidenceStatus.Error` — a fault of the
evaluation mechanism, per the contract's `error` semantics — and keep it catching, because
converting an unexpected fault into a crash inside a Grasshopper-hosted process would be a
regression.

Extend `RuleEvaluatorTests.cs` with one `[Fact]` per behavior bullet.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1201-03 | Denial of Service | RuleEvaluator.EvaluateAtom / ResolveArgValue | medium | mitigate | Two `InvalidOperationException` throw sites reachable from incomplete graph data are replaced in task 1 with typed `unknown` outcomes, so missing binding data can no longer raise inside a host process. |
| T-1201-04 | Repudiation | ValidationPublishPackageBuilder missing-result branch | medium | mitigate | A rule silently published as `Passed=false` is indistinguishable from an evaluated violation, so an unevaluated rule can be later claimed as checked.
