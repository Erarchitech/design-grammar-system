### V8 shared-surface activation gate

Before v9.1 is activated, the shared v9.0 surfaces must pass a lightweight V8 compatibility preflight: `cgContextJson` and serializer terminology are compatible with the declared V8 layer contract; operational and non-verdict states are distinct from validation verdicts; provenance identifies tagged, recognized, runtime, and formal-artifact evidence; publication filenames/version markers are consistent; and the propose → preview → confirm → apply/publish trust sequence remains intact without broadening its evidential meaning. This gate does not import the full v11.0 bundle or renumber Phases 910–917.

## Overview

v9.0 gave the architect a canvas-intelligence pipeline spread across five components, each driven by a boolean toggle and wired inputs: **DG CANVAS LISTENER** (`Run` + `Port`), **DG ENTITY TAG** (`Kind`/`Name`/`ProcIndex`/`Tag`), **DG OBJECT MARKER**, **DG STRUCTURE CONFIRM** (`Accept`/`Reject`/`Apply`), **DG COMPUTGRAPH PUBLISH** (`Project`/`DataServiceUrl`/`Publish`). It works, but the architect assembles a small control panel before doing any actual work.

v9.1 collapses that into **one node you drop and talk to** — the shape validated by [Ant](https://rhino-ant.ai/): a canvas widget, a dockable chat window, selection-as-context, and proposals previewed on canvas before they commit. DG's two differentiators over Ant are a real `/dg-` command namespace mapped to deterministic handlers (Ant documents only `/feedback`) and a visible, architect-chosen LLM (Ant documents no model selection at all).

Build order runs **substrate → surface → language → commands → closeout**:

1. **Substrate** (910): the node exists and listens on its own, with the singleton and port discipline that dropping a `Run` toggle demands.
2. **Surface** (911–912): the chat window opens on double-click, shows LLM / project / listener status in its header, and treats the canvas selection as context — all without ever blocking `SolveInstance` or touching UI off-thread.
3. **Language** (913): the `/dg-` registry, autocomplete, risk classification, and undo.
4. **Commands** (914–915): tagging, marking, recognition, confirmation, publishing — each routed to the v9.0 service it re-fronts, not reimplemented.
5. **Closeout** (916–917): deprecate the five superseded components without breaking a single saved `.gh`, then prove the whole chain live in Rhino.

The trust model is inherited verbatim from v9.0: **propose → preview on canvas → confirm → apply/publish**, all undoable, tagged entities as ground truth, nothing in Neo4j without an explicit confirmation.

**8 phases (910–917), 41 requirements, estimated ~10–14 implementation sessions.**

## Phases

### Phase 910: Chatbot Node and Auto-Listening Lifecycle

**Goal:** The architect drops one node and it is already listening — no `Run` toggle, no `Port` wiring — and it stays well-behaved when there are several of them, several documents, or a legacy listener alongside.

**Requires:** v9.0 Phase 33 (DG Canvas Bridge — the listener and its wire protocol already exist; this phase changes how its lifetime is owned).

**Requirements:** CHTN-01, CHTN-02, CHTN-03, CHTN-04, CHTN-05

**Deliverables:**
- New `ChatComponent` in `DG/src/DG.Grasshopper/Components/` with a fresh, verified-unique `ComponentGuid`; no `Run` or `Port` input params
- Listener ownership extracted out of `CanvasListenerComponent` into a process-wide singleton service (start / attach / refcount / stop), so `ChatComponent` and the legacy `CanvasListenerComponent` share one listener instead of competing for the port
- `AddedToDocument` → start-or-attach; `RemovedFromDocument` → detach and stop on last release; `DocumentContextChanged` (unloaded/closed) → release
- Port-unavailable path: degraded non-listening state with a What+Where+How-to-fix message via `ErrorMessageTemplates`, chat still usable for non-canvas questions
- Component-level status surface (output + canvas rendering) replacing the information the old `Status` output carried
- xUnit coverage for the singleton refcount state machine (start/attach/release/stop, double-add, double-remove) driven without the Grasshopper SDK

**Success Criteria:**
1. Dropping the node on an empty canvas results in a listening bridge with zero further architect gestures
2. Adding a second DG CHAT node, opening a second document, and adding a legacy DG CANVAS LISTENER all attach to the one running listener — no bind error is ever raised by a DG component against another DG component
3. Occupying the port from outside Rhino before dropping the node yields a labelled degraded state with an actionable message, and Rhino stays responsive
4. Deleting every DG component releases the port; re-adding one in the same session listens again

**Watch out for:** starting the listener from `AddedToDocument` removes the architect's manual serialisation of port binding — the singleton guard is the whole safety story here. Do not do heavy work in GH event handlers; they fire constantly.

### Phase 911: Eto Chat Window and Session Shell

**Goal:** Double-clicking the node opens a native chat window whose header always tells the architect which LLM is answering, which project they are in, and whether the canvas is connected — and using it never freezes Rhino.

**Requires:** Phase 910 (the node and its listener status) plus the V8 shared-surface activation gate above.

**Requirements:** CHTW-01, CHTW-02, CHTW-03, CHTW-04, CHTW-05, CHTW-06

**Deliverables:**
- `ChatComponentAttributes : GH_ComponentAttributes` overriding `RespondToMouseDoubleClick` → opens the window; a context-menu entry as a secondary trigger
- Eto.Forms chat surface (modeless `Form`, dockable via `Rhino.UI.Panels.RegisterPanel` registered at plugin `OnLoad`), message list + input box + send/cancel
- Header binding three live values: LLM provider+model from `GET /llm/settings`, active project from the CONNECTOR platform token, listener status from Phase 910's singleton — each refreshed on change, not only on open
- HTTP client in the plugin calling data-service `/llm/generate` (following the existing `ValidationPublishClient` pattern), fully off the UI thread
- All chat/canvas updates marshalled via `RhinoApp.InvokeOnUiThread`; `SolveInstance` reduced to reading shared state
- Panel ↔ component communication through a plugin singleton / shared service, never direct object references
- In-session transcript store surviving window close/reopen; request cancellation
- Unset/unreachable states (no API key, unresolved project, platform down) rendered specifically in the header with sending disabled and a reason

**Success Criteria:**
1. Double-clicking the node opens the chat window; the header shows the same provider/model the Design Grammars AI Engine screen shows, the active project name, and a live listener indicator
2. A deliberately slow or hanging LLM request leaves Rhino fully interactive — canvas pan/zoom and other components keep solving — and can be cancelled from the window
3. No Eto control or Grasshopper document object is mutated off the UI thread (verified by review and by an assertion/guard in the marshalling layer)
4. Closing and reopening the window preserves the conversation
5. With no API key configured, the header says so and sending is disabled with an actionable reason

**Watch out for:** blocking `SolveInstance` on the LLM call is the highest-severity pitfall in this milestone — it stalls the entire Grasshopper solution loop and can freeze Rhino. Mutating Eto UI from a background thread hard-crashes Rhino on macOS.

### Phase 912: Selection Context and Free-Form Ask

**Goal:** Selecting components on the canvas *is* the context — the architect asks about what they highlighted and gets an answer grounded in the real serialized structure.

**Requires:** Phase 911 (the window and its LLM path).

**Requirements:** CTXS-01, CTXS-02, CTXS-03, CTXS-04, CTXS-05

**Deliverables:**
- Selection capture from `GH_Document.SelectedObjects`, marshalled on the UI thread, feeding the existing v9.0 serialization path (`CanvasAnnotationParser` + `ComputgraphContextSerializer` → `cgContextJson v1`) — **no second serializer**
- Selection indicator in the window: object count plus a readable summary (tagged vs untagged, kinds present)
- Prompt assembly for the free-form Ask path, combining the serialized selection with the Computgraph concept catalog from `dg_context.py` / `/context/assemble`
- Whole-definition fallback on empty selection, announced explicitly in the chat
- Token budget with explicit truncation reporting (reusing the `output_token_budget` precedent from `cg_topology.py`)
- Tests: selection → context payload shape; empty-selection fallback; over-budget truncation is reported not silent

**Success Criteria:**
1. Selecting a group of components and asking "what is this?" returns an answer that names the actual entities, their tags, and their relationships — verifiably drawn from the serialized structure, not invented
2. The window shows what was captured before the message is sent
3. Asking with nothing selected works and states that the whole definition is in scope
4. A selection exceeding the token budget produces an explicit truncation notice naming what was dropped

### Phase 913: `/dg-` Slash Command Framework

**Goal:** Typing `/` gives the architect a discoverable, deterministic command language — commands do exactly what they say, mutating commands ask first, and one Ctrl+Z undoes any of them.

**Requires:** Phase 911 (the chat input surface).

**Requirements:** SCMD-01, SCMD-02, SCMD-03, SCMD-04, SCMD-05, SCMD-06

**Deliverables:**
- Schema-driven command registry (name, description, typed argument list with required/optional and choices, risk level) — one source driving autocomplete, argument hints, validation, and `/dg-help`; modelled on Discord's application-command option schema and Slack's slash-command style guide
- Autocomplete dropdown triggered on `/`, filtering as the architect types, inserting the command with its argument hint
- Parser + dispatcher: input starting with `/` routes to a registered handler, never to the LLM; unknown commands and argument errors are rejected pre-execution with a usage line
- `/dg-help` (no args → list; with a command name → full usage)
- Risk classification with three tiers — read-only (immediate), preview-only (temporary canvas artefacts only), mutating/publishing (summary + explicit confirm, cancel leaves no trace)
- Undo integration: every canvas mutation from a command wrapped in a `GH_UndoRecord`, following the existing `EntityTagComponent` precedent
- Tests: registry-driven autocomplete filtering, argument validation matrix, determinism (same command + same canvas → same result), risk gating, undo reverts a whole command

**Success Criteria:**
1. Typing `/` lists every command with descriptions and narrows as the architect types
2. Adding a new command to the registry surfaces it in autocomplete and `/dg-help` with no chat-UI edits
3. A mutating command shows exactly what will change and does nothing until confirmed; cancelling leaves the canvas byte-identical
4. One Ctrl+Z reverts an entire command's canvas effect
5. A malformed command reports usage and executes nothing

### Phase 914: Tagging and Marking Commands

**Goal:** `/dg-tag` and `/dg-mark` do from the chat exactly what DG ENTITY TAG and DG OBJECT MARKER do from the canvas — same code, same names, same undo.

**Requires:** Phase 913 (the registry), v9.0 Phase 34 (the components being re-fronted).

**Requirements:** TAGX-01, TAGX-02, TAGX-03, TAGX-04, TAGX-05

**Deliverables:**
- Tagging/marking logic extracted from `EntityTagComponent` and `ObjectMarkerComponent` into shared services; both components refactored to call the services (behaviour-preserving, existing tests must stay green)
- `/dg-tag <kind> [name] [procIndex]` over the live selection — auto-index assignment, Pattern nesting, convention colouring, undoable
- `/dg-mark <objectName> [algorithmIndex]` — idempotent `OBJECT - <NAME>` / `<n>_ALGORITHM` scribbles, optional `dg:Class` IRI binding
- `CanvasAnnotationNameFactory` remains the single source of truth for names — consumed, never forked
- Natural-language tagging intent → a proposed command with arguments pre-filled, executed only on confirm
- Tests: chat-created tags and component-created tags produce identical `cgContextJson` (`source: tagged`) and re-parse identically

**Success Criteria:**
1. `/dg-tag Proc MyProc 11` on a selection produces a group indistinguishable from the one DG ENTITY TAG produces for the same inputs
2. `/dg-mark Frame 1` is idempotent — running it twice leaves one pair of scribbles
3. The existing Phase 34 component tests pass unchanged after the service extraction
4. Asking "tag these as a procedure" proposes the command with arguments filled and waits for confirmation

### Phase 915: Recognition, Confirm and Publish Commands

**Goal:** The architect runs recognition, reviews what the AI found, accepts what is right, and publishes — all from the chat, with nothing reaching Neo4j unconfirmed.

**Requires:** Phase 914 (command patterns + services), v9.0 Phases 35 and 36 (recognition pipeline, `PreviewRegistry`, publish endpoint).

**Requirements:** RCMD-01, RCMD-02, RCMD-03, RCMD-04, RCMD-05, RCMD-06

**Deliverables:**
- `/dg-recognize [scope]` → existing Tier-0/Tier-1 pipeline (`cg_topology.py` + `cg_recognition.py`) over the selection or whole definition; preview groups rendered via the v9.0 `PreviewRegistry`; proposals listed in chat with kind, name, member count, confidence
- Volunteered recognition: when the architect asks about a selection, surface candidate entities with rationale as proposals on the same preview→confirm path
- `/dg-confirm` / `/dg-reject` with individual, bulk, and partial selection — accepted proposals become permanent convention groups with `source: recognized`; rejected ones removed cleanly (re-fronting `StructureConfirmComponent`'s service)
- `/dg-publish` → `POST /computgraph/publish` with a pre-publish summary (entity counts by kind, target project, stale entity ids) and explicit confirm; result reported in chat
- `/dg-status` → listener state, LLM, project, selection summary, pending proposals, last publish result in one message
- Unrecognised blocks reported with member ids, never invented or dropped

**Success Criteria:**
1. `/dg-recognize` on an untagged region produces on-canvas previews and a chat list matching them one-for-one
2. Partially accepting proposals converts exactly the accepted ones and removes exactly the rejected ones
3. `/dg-publish` shows what will be written and writes nothing until confirmed; the published structure appears in Neo4j under the active project with correct provenance
4. `/dg-status` answers every "where am I?" question in one message
5. Entities the pipeline cannot classify are listed as unrecognised with their member ids

### Phase 916: Legacy Component Deprecation

**Goal:** The five superseded components step aside without breaking a single saved definition.

**Requires:** Phases 914–915 (their replacements must actually exist first).

**Requirements:** DEPR-01, DEPR-02, DEPR-03, DEPR-04

**Deliverables:**
- DG CANVAS LISTENER, DG ENTITY TAG, DG OBJECT MARKER, DG STRUCTURE CONFIRM, DG COMPUTGRAPH PUBLISH keep their GUIDs (`B0F26347-…`, `C1E7B4A9-…`, `D3A9F41C-…`, `A4C1F7E2-…`, `E2D4A9F1-…`) and full behaviour
- Each marked deprecated and hidden from the ribbon (`Exposure.hidden`), still placeable via search, still loadable from saved files; each emits a remark naming DG CHAT as the replacement
- `docs/RELEASE-NOTES-v9.1.md` — command↔component mapping table, explicit "no GUID changed, no canvas breaks" statement, contrasted with the v7.0 CLASSIFICATOR removal and the v8.2 Phase 825 CONNECTOR GUID break
- CLAUDE.md, `spec/GRASSHOPPER.md`, and a new ui-v2 DG API Documentation content module covering DG CHAT and the full `/dg-` reference (the `import.meta.glob` auto-registration means zero viewer-code changes)

**Success Criteria:**
1. A `.gh` file built against the five components opens and solves with zero missing-component placeholders
2. None of the five appears in the ribbon; all five are still findable by search and still work
3. Release notes state the command↔component mapping and the no-breakage guarantee
4. The `/dg-` command reference is browsable in the ui-v2 DG API Documentation region

**Watch out for:** this milestone's whole compatibility promise lives here. Any temptation to re-GUID or delete must be re-decided with the user, not absorbed silently — see the v7.0 canvas-breakage precedent in CLAUDE.md's Known Gotchas.

### Phase 917: Integration and E2E

**Goal:** The whole chain works live in Rhino from one dropped node, and every failure path degrades legibly.

**Requires:** Phases 910–916.

**Requirements:** CHIN-01, CHIN-02, CHIN-03, CHIN-04

**Deliverables:**
- Live-Rhino E2E: drop DG CHAT → listening → double-click → header verified → select → ask → `/dg-mark` → `/dg-tag` → `/dg-recognize` → confirm → `/dg-publish` → structure visible in the ui-v2 Computgraph layer for the active project
- Provider-switch check: changing provider/model on the AI Engine screen reflects in the chat header and subsequent answers with no Rhino restart
- Legacy-path regression: a component-built `.gh` produces the same tags, proposals, and published Computgraph as the chat-driven flow
- Failure-path matrix exercised live: platform unreachable, no API key, port occupied, LLM timeout, publish rejected — each with an actionable What+Where+How-to-fix message and a responsive Rhino
- UAT document following the established `NNN-UAT.md` format; `graphify update .` refresh

**Success Criteria:**
1. The full chain completes from one node with no other DG component on the canvas
2. Switching provider on the platform changes the chat header and the answering model without a restart
3. Chat-driven and component-driven flows produce equivalent published Computgraph structures
4. Every failure in the matrix produces an actionable message with Rhino left usable
