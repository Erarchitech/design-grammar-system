<planner_decisions>
**P-15 — The publish leg is a separate, separately-marked test module, and the flag is reset in teardown.**
Keeping it out of `test_dsav_live_loop.py` means a routine integration run can never accidentally mint Speckle versions. The module carries both `integration` and `live` markers; the `live` marker is deselected by default by `data-service/tests/conftest.py` unless an explicit `-m` expression is supplied, which is precisely the "must not fire by accident" property this leg needs. Teardown sets `publishEnabled` back to false and deletes the `provider:'AutoValidation'` row for the fixture project.

**P-16 — If the dev stack has no working Speckle write configuration, the plan stops at a blocking checkpoint rather than faking the data point.**
D-11 requires a working Speckle config in the dev stack. `publish_validation` already surfaces the two precise failure modes: no `provider:'Speckle'` `IntegrationConfig` row, and no Speckle write token. The task probes for both before attempting anything. If either is absent, the executor must not synthesize a number, must not mock Speckle, and must not silently skip — it records the blocker, marks the D-11 data point as `blocked` with the specific reason in the evidence artifact, and the checkpoint asks the operator to either configure Speckle and re-run or accept the estimate. An unmeasurable measurement recorded as measured is worse than an acknowledged gap.
</planner_decisions>
