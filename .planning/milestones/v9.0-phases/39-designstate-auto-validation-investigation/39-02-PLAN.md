<planner_decisions>
**P-01 — Capture-endpoint authentication: inline Bearer check calling `connectors.authenticate_token()`. This resolves the one item 39-CONTEXT.md left open for the planner.**

Mechanism: the route reads the `Authorization` header, extracts a `Bearer ` value, requires it to start with `connectors.TOKEN_PREFIX`, and resolves it through `connectors.authenticate_token(token)` — **not** `connectors.record_heartbeat(token)`. `record_heartbeat` stamps `last_connection` on the credential, which would misrepresent capture traffic as connector liveness; that is a category error the analog itself warns about. The route then compares the returned credential's bound `project` against the request body's `project` with strict equality.

Why inline rather than a shared `Depends()` wrapper: `connector_heartbeat` (`data-service/app.py:1150-1178`) is the only existing caller of this pattern and it inlines the same three lines; no `Depends()`-wrapped auth dependency exists anywhere in `data-service` today. Extracting one for a second call site would factor out three lines of header parsing while the security-relevant half — the project-binding comparison — necessarily stays route-local, because the heartbeat has no caller-supplied project to compare against. Under D-B (spike quality) the smaller diff on the existing style wins. Extracting `require_connector_token()` when a third call site appears is named as ADR follow-up scope in Plan 05.

Rejected alternatives, recorded for the ADR: a new API-key table (duplicates security-relevant code Phase 825 already ships, with a revoke path already built); leaving the endpoint unauthenticated behind the off-by-default flag (the flag gates the *watcher*, not the *endpoint* — an anonymous POST would still write unbounded rows into ValidGraph); and IP allowlisting (no meaningful boundary inside a compose network).

**P-06 — No configuration route. The `provider:'AutoValidation'` row is written out-of-band.**
39-CONTEXT.md § Integration Points states that `POST /designstate/capture` is "the phase's only new public surface". Adding a config route would create a second unauthenticated write surface for a spike whose config is set once by an operator. Enabling auto-validation for a project therefore means calling `dsav_watcher.upsert_auto_validation_config()` — from the Wave 3 test driver, or from a one-off `docker compose exec data-service python -c ...` invocation. A config route is named as follow-up scope in the ADR.

**P-07 — Auto-publish runs AFTER completion, best effort, and never reverts a verdict.**
The manual path (`publish_validation`, `data-service/app.py:1818`) mints a Speckle version *before* persisting and 404s outright with `SPECKLE_CONFIG_MISSING` when Speckle is unconfigured. Auto-runs invert that ordering: the verdict is completed and persisted first, then publish is attempted only if `publishEnabled` is on. Any failure — missing Speckle config, missing write token, Speckle unreachable — is swallowed and surfaced in the poll summary. The run stays `completed`. This is what makes D-09's no-flood guarantee structural and removes the Speckle hard dependency, so auto-validation works on projects with no Speckle wiring at all.

**P-10 — D-10 is enforced by a pinned source hash, not by inspection.**
`store_validation_run` must stay byte-for-byte untouched. Its AST-extracted source (currently `data-service/app.py` lines 455-562, 4036 characters) hashes to `db6615b823d3247c313b3f5f4cc1bfb7302f33012f79cf92323e9147d11c2b01` (sha256, computed at planning time 2026-07-27). A test pins that value. If a future intentional change to that function is ever approved, the test fails loudly and the hash is re-pinned deliberately — which is exactly the review gate D-10 wants.
</planner_decisions>
