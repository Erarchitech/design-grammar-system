# Phase 36 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope note (read first)

This phase's only real frontend surface is **`ui-v2/`** (React 18 + Vite 5, the orbital "datascape" Graph screen). The Grasshopper plugin's **DG COMPUTGRAPH PUBLISH** trigger (CGPD-05) is not a web UI — it is out of scope for this contract per the objective brief; its status/output ports should follow the existing `ValidationPublishClient` pattern (plain text status, no new visual system).

This phase **adds a 7th set of node/relationship labels to an existing, working viewer** — it does not introduce new screens, panels, or components. The entire design contract below is about correctly wiring the new Computgraph layer into the existing ring-mapper (`ui-v2/src/graph/buildRings.js`) and existing detail/hover panels, and about one real display bug this phase must not ship into: a **naming mismatch** between the placeholder layer key already in the codebase and the exact `graph:'Computgraph'` string CGPD-01 requires.

| Token | Value | Usage |
|-------|-------|-------|
| `--spacing-4` | 4px | Icon gaps, inline padding |
| `--spacing-8` | 8px | Compact element spacing (frosted-panel internal gaps) |
| `--spacing-12` | 12px | Card padding (small panels) |
| `--spacing-16` | 16px | Default element spacing |
| `--spacing-20` | 20px | `--card-padding` (standard panel padding) |
| `--spacing-24` | 24px | Section padding |
| `--spacing-48` | 48px | Major section breaks |

Exceptions: the project scale is **not** the GSD-default 4/8/16/24/32/48/64 set — it already has 12 and 20 in active use (frosted panel padding) and has no 32 or 64 step. This is the existing, shipped scale; Phase 36 must match it, not "correct" it. No new exceptions needed for this phase — every new node/label added to the ring mapper renders through the same `dg-frost` panels, `PropertiesTable`, and `Chip` primitives already spaced per the table above.

## Color

Reuse existing tokens (`ui-v2/src/styles/tokens/colors.css`) exactly. **Hard constraint carried from DSYS-01 (standing decision):** this system is monochromatic with exactly one chromatic hue (Signal Red), reserved for selection/failure/destructive. **The Computgraph layer must NOT be given its own accent color.** "Distinct styling" for CGPD-04 is satisfied structurally — by ring position, orbit grouping, and label text — never by a new hue.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `var(--color-canvas)` #f5f5f5 (light) / #111111 (dark) | Canvas background behind all rings, including Computgraph |
| Secondary (30%) | `var(--frost-bg)` rgba(255,255,255,0.78) via `.dg-frost` | Layer list panel, orbit legend panel, hover/detail panels — identical treatment to every other layer |
| Accent (10%) | `var(--color-signal)` #e7000b | Selection halo, selected-layer index number/dot, hover ring, edge highlight — reused unchanged; **never assigned to Computgraph nodes at rest** |
| Destructive | `var(--color-signal-ink)` #b8000e | N/A this phase — no destructive UI action added |

Accent reserved for: the active-layer index number + dot in the Layers panel, the selected-node fill/halo on canvas, the hover ring, cross-edge highlight lines, and edge property-label tags. Computgraph nodes at rest render in `TH.ink`/`TH.dim` exactly like OntoGraph/Metagraph/ValidGraph nodes today — no exception.

## Computgraph Ring-Mapper Contract (the real deliverable of this phase's UI work)

`ui-v2/src/graph/buildRings.js` already has a **placeholder** stub for this layer that predates this phase's requirements and does not match them. This section is the binding contract for correcting it — treat every item below as a locked spec, not a suggestion.

### 1. Layer key — fix the casing mismatch (blocking)

The current stub uses `"ComputGraph"` (capital G, no lowercase "put"+"graph" split) in both `LAYER_ORDER` and `ORBITS`. CGPD-01 / Phase 36 CONTEXT.md lock the published property to **`graph:'Computgraph'` exactly** (matches `spec/DG-ID.md`, `CLAUDE.md` schema tables, and the CLAUDE.md gotcha about getting graph-name strings right once — this is the same class of bug as the historical `ValidationGraph`→`ValidGraph` migration pain).

```js
// buildRings.js — LAYER_ORDER: rename "ComputGraph" → "Computgraph", same position
const LAYER_ORDER = ["OntoGraph", "Metagraph", "KnowledgeGraph", "SpecGraph", "Computgraph", "ValidGraph"];
```

If this rename is skipped, published Computgraph nodes will render as an unlabeled/misordered extra layer (they'd fall through to the `ia<0?99:ia` catch-all sort, landing after ValidGraph) instead of matching this contract's intended position between SpecGraph and ValidGraph.

### 2. Orbit assignment — 7 labels across 3 orbits

The ontology chain is `Object → Behavior → Algorithm → Procedure → Pattern → Parameter/Interface` (per Phase 36 CONTEXT.md §1). Bucket it the same way every other layer buckets identity/structure/leaf (compare Metagraph: `Rule` core, `Atom` mid, `Var/Literal/Builtin` outer):

```js
ORBITS.Computgraph = {
  Object: 0, Behavior: 0, Algorithm: 0,   // orbit 0 — identity chain
  Procedure: 1, Pattern: 1,               // orbit 1 — structural decomposition
  Parameter: 2, Interface: 2              // orbit 2 — leaf entities
};
```

### 3. Captions — display property per label

Per Phase 36 CONTEXT.md §6, node display properties are `objectName` / `algorithmName` / `procedureName` / `patternName` / `parameterName` / `interfaceName`. `Behavior` carries no dedicated display property (it is a pure structural passthrough node in the ontology chain) — let it fall through to the existing `captionOf()` fallback (`props.label || props.name || props.id || label`), which will show the literal string `"Behavior"`. This is intentional, not a gap — do not invent a `behaviorName` property.

```js
CAPTIONS.Object = ["objectName"];
CAPTIONS.Algorithm = ["algorithmName"];
CAPTIONS.Procedure = ["procedureName"];
CAPTIONS.Pattern = ["patternName"];
CAPTIONS.Parameter = ["parameterName"];
CAPTIONS.Interface = ["interfaceName"];
// Behavior: no entry — falls through to existing generic fallback, renders "Behavior"
```

### 4. Per-project filter (CGPD-04) — already satisfied, no new UI

`GraphScreen`'s existing `project` prop already scopes `fetchGraph(project)` to one project end-to-end (Cypher `WHERE n.project = $project`). Once items 1–3 above are done, the Computgraph layer is automatically project-filterable through the same mechanism every other layer uses — **do not build a separate per-layer or Computgraph-specific filter control.**

### 5. Large-property guard — `contextJson` on `Algorithm` nodes (new risk this phase introduces)

Per Phase 36 CONTEXT.md §"Open for planning", the full `cgContextJson` document is stored as a `contextJson` string property on `Algorithm` nodes (raw canvas substrate is not persisted per-node in v9.0). `PropertiesTable` (`ui-v2/src/components/display/PropertiesTable.jsx`) currently renders every property value verbatim in a table cell with only `overflowWrap: anywhere` — no length clamp. A multi-KB JSON blob rendered this way will visually break the frosted detail panel (which is capped at `70vh` but not internally virtualized for cell content).

**Contract:** in `GraphScreen.jsx`'s `rowsOf()` (the function that turns a selected node's `props` into `PropertiesTable` rows), any property value whose string length exceeds **200 characters** must render as a truncated preview (`value.slice(0, 200) + "…"`) rather than the raw string. This is a generic guard (benefits any future large-property node, not just `contextJson`) and requires no new component — it's a one-line change inside the existing `rowsOf` mapper. Do not add a "view full JSON" modal or copy button this phase; truncation alone satisfies "the panel doesn't break," and CGPD-03's provenance query requirement is already satisfiable via direct Cypher / the data-service, not the ui-v2 detail panel.

### 6. Provenance properties — no new chrome needed

CGPD-03 provenance fields (`source`, `provider`, `model`, `confidence`, `definitionId`, `fileName`, `publishedAt`) are ordinary node properties and will appear automatically in the existing `PropertiesTable` rows (hover panel shows the first 6 props, the double-click detail panel shows up to 24) — no new field, badge, or panel is needed. If `source` needs visual emphasis (tagged vs. recognized), that is a `Chip`/text-color decision **within the existing monochrome+signal-red palette** (e.g. `source: recognized` rows may use `var(--text-muted)` vs `var(--color-ink)` for `tagged` — a weight/tone distinction, never a new hue) — left to executor discretion, not mandated.

### Interaction note — inline property editing on Computgraph nodes (flag, not a block)

`PropertiesTable`'s existing double-click-to-edit path (`onEdit` → `updateNodeProp` → raw Cypher `SET n[$key] = $value`) will work unmodified on Computgraph nodes once they're wired in, since it operates generically on any selected node. This means a user could inline-edit `dgId`, `cgId`, or `source` — identity/provenance fields whose consistency other Phase 36/32.1 systems depend on (MERGE keys, cross-platform binding). This phase does not need to add a confirmation dialog or field-level lock (no other layer has one either, so it would be an inconsistent new pattern) — but the planner should be aware this generic edit path now reaches provenance-carrying fields, and may want a follow-up (not blocking Phase 36 ship).
