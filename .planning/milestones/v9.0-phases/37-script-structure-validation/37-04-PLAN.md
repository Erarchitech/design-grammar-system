  <action>
Add the evaluation side to `data-service/cg_structure_checks.py`.

`_OPERATION_TEMPLATES` is a module-level dict mapping each of the four operation names to one static, triple-quoted, parameterized Cypher template, each ending in its own trailing `// op=RULE_` tag. A template is never built or edited at runtime - the mapping entry supplies bound parameter values only. Semantics:

- `requiresProcedure` - for the algorithms scoped to project and definitionId, collect the Procedures whose `procedureName` contains the bound name pattern. The rule passes when at least one Procedure matched. `namePattern` is a case-sensitive substring bound as a Cypher parameter, never a glob and never a regex; the asterisks in the phase context prose are emphasis, not syntax.
- `requiresParameter` - collect the Parameters scoped to project and definitionId whose `parameterName` or whose cgId-derived convention token contains the bound name pattern, and which additionally match the bound `paramKind` and `dataType` when those params are supplied. Because the published display name carries only the bare name while the convention token lives in the cgId, the template must consider both - a mapping naming the convention token must still match. The rule passes when at least one Parameter matched.
- `requiresInterface` - for the Procedures scoped to project and definitionId, collect their Interfaces, filtered by the bound `ifaceType` when supplied. The rule passes when every Procedure has at least one matching Interface; the offending entities are the Procedures that have none. This is a for-all requirement, unlike the two above, which are exists requirements - state that difference in a comment so a future contributor does not "fix" it into an exists check.
- `forbidsOrphan` - collect the nodes of the bound `label` scoped to project and definitionId that have no incoming ownership relationship. Restrict the bound label to an allow-list of the Computgraph entity labels; a label outside that list makes the mapping invalid rather than injecting an arbitrary label into the query. The rule passes when the collected list is empty.

`evaluate_rule_mappings(session, project, definition_id, payload=None) -> list[dict]` loads the payload when not supplied, runs it through `valid_structure_mappings`, and for each accepted mapping:
- Runs one Metagraph existence probe scoped by `Rule_Id` and `project`, tagged `// op=RULE_EXISTS_METAGRAPH`, setting `ruleExists`. A Rule node that does not exist is NOT an error and does not skip evaluation - the structural requirement is still evaluated and reported, with `ruleExists` false. The mapping references an existing Rule as a foreign key; it must not require one to be ingested first.
- Runs the operation's template with the mapping's params bound, plus project and definitionId.
- Emits one result dict with exactly the normative keys from `spec/API.md`: `ruleId`, `operation`, `passed`, `ruleExists`, `message`, `satisfyingEntities`, `offendingEntities`. Both entity lists use the same `_entity()` shape the SVAL-01 findings use. The message follows the same What + Where + How-to-fix composition, built through the shared finding-message helper rather than inline.
- For a mapping rejected by `valid_structure_mappings`, emit a result with `passed` false and a message explaining which validation rejected it, so a malformed mapping is visible in the report rather than silently absent. Give these a distinct, obvious signal in the message; do not let them look like a genuine structural failure.

Return the results sorted by ruleId then operation, so repeated calls are byte-identical. Add a docstring stating that this function performs reads only, writes nothing, and consults no model.

| Boundary | Description |

| structure_rules.json -> Cypher | A file-supplied `operation`, `label` or `namePattern` reaches a query; a label reaching the query text rather than a parameter would be an injection vector |
