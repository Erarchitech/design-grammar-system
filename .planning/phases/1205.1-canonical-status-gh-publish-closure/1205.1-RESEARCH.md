RED assertion завершилась exit 1: `AssertionError: Production-wire regression: expected unsupported, got passed`. [VERIFIED: research-probe/Program.cs:1-28; research-probe/probe_wire.py:1-36; выполненный probe 2026-09-30]

Нужен additive typed binding result, затем rollup по точной паре rule/object и передача через существующее backend-поле `canonicalStatuses`. [VERIFIED: DG/src/DG.Core/Validation/RuleEvaluator.cs:23,61-134; DG/src/DG.Core/Models/RuleEvaluationResult.cs:19-30; data-service/app.py:377-392]

Конкретные schema/models/read compatibility должен проверить plan-checker; повторный owner checkpoint на саму коллекцию не нужен. [VERIFIED: spec/EVIDENCE-CONTRACT.md:195-198; spec/evidence-contract.schema.json:62-174]

**Рекомендация:** сначала один production-wire tracer с Unsupported и mixed supported outcomes; versioned zero-row контракт в утвержденном D-01 направлении; legacy booleans сохранить как non-authoritative, не переписывая их поведение молча.

## Architecture Patterns

```text
Bindings + Rule
  → EvaluateBody per binding
  → typed binding outcomes ───→ rule StatusRollup (rule summary only)
  → group contributing bindings by (ruleId, objectId)
  → pair StatusRollup
  → package canonical map + unchanged legacy compatibility surfaces
  → shared production mapper + geometry adapter
  → production JSON
  → Pydantic request → supplied canonical precedence / old-client fallback
  → schema-valid envelope → project/run scoped persistence
  → Python view + C# BuildPerObjectVerdicts

Zero bindings → rule NoPopulation; NO synthetic object row
Missing result → rule NotEvaluated; object association must be specified
```

Это рекомендуемая архитектура, а не уже внесенная реализация.

### 1. Preserve before aggregate

Рекомендуется expose additive list of binding+typed-status(+detail) на RuleEvaluationResult. Сопоставлять по binding identity/явному стабильному association, не по значению и не только по позиции; не делать second evaluation в builder. Для каждого объекта брать outcomes только bindings, действительно содержащих этот объект. Несколько переменных с тем же object ID в одном binding не должны создавать duplicate pair; несколько bindings одного объекта агрегируются StatusRollup до единственной evidence row. Разные object ID сохраняются, даже если scalar values одинаковы.

Нормативный vocabulary, цитата: `Passed`, `Failed`, `Unknown`, `NotEvaluated`, `NoPopulation`, `Unsupported`, `Indeterminate`, `Error`; wire: `passed`, `failed`, `unknown`, `not_evaluated`, `no_population`, `unsupported`, `indeterminate`, `error`. [VERIFIED: DG/src/DG.Core/Contracts/EvidenceStatus.cs:11-20; EvidenceStatusNames.cs:39-51]

Единственный shipped precedence, цитата: `Error`, `Failed`, `Indeterminate`, `Unsupported`, `Unknown`, `NotEvaluated`, `NoPopulation`, `Passed`. Не использовать enum ordinal/max или второй switch при group rollup. [VERIFIED: DG/src/DG.Core/Contracts/StatusRollup.cs:27-65]

### 2. Rule aggregate не является object verdict

Пример рекомендуемой regression: один supported comparison rule, три объекта с числовым binding, отсутствующим variable и некорректным literal/числовым conversion fault. Проверять каждую пару отдельно; общий Error не должен размножаться на passed/failed объекты. Еще fixture: numeric-comparison atom перед unsupported atom — первый объект short-circuits Passed, второй доходит до Unsupported. Это доказывает, почему даже rule с unsupported construct не дает один статус всем объектам. Семантика short-circuit уже существует; не изменять ее в closure. [VERIFIED: RuleEvaluator.cs:137-156,234-298,391-448]

### 3. Reuse production mapper, isolate geometry

Предпочтительный plan slice: вынести status/request mapping и DTO в Rhino-free production seam, вызываемый GH Publish, и вынести/передать только geometry serialization как adapter. Tests должны вызывать тот же seam и те же JsonOptions, которыми JsonContent.Create пользуется в Publish. Альтернатива минимального tracer — source-link неизмененных GH файлов, как исследовательский probe. Не заменять BuildRequest копией в test; не заменять DTO самодельным anonymous JSON.

Основание: GH mapper private и guarded; DG.Tests reference только DG.Core. Geometry serializer импортирует Rhino, тогда как null geometry возвращает null до любой Rhino-операции. [VERIFIED: ValidationPublishClient.cs:1-26,37-46,115-177; ValidationPublishContract.cs:1-113; ValidationGeometryPayloadSerializer.cs:1-27; DG.Tests.csproj:22-24]

### 4. Canonical transport уже частично принят backend

Backend property: `canonicalStatuses: dict[str, str] | None = None`; supplied value выигрывает у failed/passed lists. Однако row discovery — union `ruleIds`, `failedRuleIds`, `passedRuleIds`, **не keys canonicalStatuses**. Новый producer обязан заполнять RuleIds одновременно с map; regression должна это доказать. Предпочтительнее закрепить producer invariant, чем молча расширять серверную область неизвестными map keys. [VERIFIED: data-service/app.py:377-392,2555-2588]

Malformed/absent status сейчас падает обратно в legacy path, а не отвергает publish. Сохранить старый client fallback и протестировать отсутствие, null, invalid string, recognized canonical against contradictory lists. Строгое отклонение старых payloads — отдельное решение, не скрытая часть bug fix. [VERIFIED: app.py:2514-2529,2564-2575]

## Attainable Outcomes and Empty-Population Boundary

| Outcome | Реальная достижимость сейчас | Нужная проверка |
|---|---|---|
| Passed / Failed | Builtin matching в violation inversion | Оба объекта одного rule, не aggregate duplication |
| Unsupported | ObjectPropertyAtom; unsupported atom/builtin; numeric-only comparison с nonnumeric input | Реальный evaluator → actual wire |
| Unknown | Missing/unresolvable variable после attempted resolution | ElementRef присутствует, variable отсутствует: entity есть, status unknown |
| Error | Genuine exception внутри binding loop, например invalid typed integer literal | Не выдавать Error за Failed из FailingBindings |
| NoPopulation | `bindings.Count == 0`, возврат до parser/body | Zero entities, zero object rows; rule outcome должен сохраниться |
| NotEvaluated | Builder не находит result для in-scope rule | Непустой known population отдельно от truly zero-object request |
| Indeterminate | В прочитанном RuleEvaluator нет emitting branch | Contract/transport injection, честно помеченный как не natural evaluator case |
| No ElementRefs | Bindings nonempty, но невозможно назвать object | Это не NoPopulation; только rule summary, не выдуманный ID |

[VERIFIED: RuleEvaluator.cs:38-59,67-134,177-212,234-298,391-448; ValidationPublishPackageBuilder.cs:35-62,168-213]. Не использовать NaN как гарантированный Indeterminate: текущий conversion/catch может вернуть Error, а не такую семантику.

### Обнаруженный разрыв zero-row representation

1. Spec §4 требует rule `no_population` без EvidenceRow и без silent omission. [VERIFIED: spec/EVIDENCE-CONTRACT.md:195-198]
2. Request ruleResults имеет только `ruleId`, `passed`, `failedEntityIds`, `passedEntityIds`; Python build_rules_summary оставляет `ruleId`, `ruleName`, `ruleDescription`, `passed`. [VERIFIED: app.py:357-361,1072-1085]
3. Envelope имеет `rows`, но не rule result collection; `additionalProperties: false`, а Pydantic `extra="forbid"`. [VERIFIED: spec/evidence-contract.schema.json:62-174; data-service/evidence_contract.py:160-192]
4. Python empty-row fallback — `CanonicalStatus.NO_POPULATION`; C# empty StatusRollup — `EvidenceStatus.NotEvaluated`. Оба factories поддерживают explicit rollup override. Не менять глобальные defaults как попутный fix. [VERIFIED: evidence_contract.py:199-216,239-265; StatusRollup.cs:46-53; EvidenceEnvelopeFactory.cs:33-40,58-71]
5. Поэтому zero rows может означать пустую evaluated population, missing result или populated bindings без resolvable object identity. Один fallback не способен корректно описать все три. [VERIFIED: перечисленные producer branches + factory defaults]

**Утверждено D-01:** rule-level collection хранится именно в versioned envelope, включая несколько zero-row rules. Отдельный persisted summary может быть compatibility surface, но не заменой коллекции; один aggregate и warnings-as-map неприемлемы. Planner выбирает exact shape, token, model/schema dispatch, emission policy и матрицу чтения, checker проверяет совместимость. Это техническая работа внутри approved scope, не новый общий decision checkpoint. [VERIFIED: 1205.1-CONTEXT.md:38-41; 1205.1-PATTERNS.md:126-170,296-335]

Missing-result при известных objects: рекомендуемый смысл NotEvaluated по каждому in-scope объекту, но builder сейчас делает continue и не связывает объекты. Planner должен явно закрепить association/coverage и не маркировать все посторонние entities правилом. [VERIFIED: ValidationPublishPackageBuilder.cs:35-49; spec/EVIDENCE-CONTRACT.md:86-88]

## Compatibility and Security

**Минимальное сохранение совместимости:** добавить authoritative map/outcomes, сохранить legacy Passed, ValidStatus и старые lists/OverallStatus как non-authoritative; documented contradiction у старого представления допустима только если новые gates/readers реально используют canonical. Перевод legacy lists на canonical-to-boolean, где каждый non-pass попадает в failed, снова семантически ложно обозначит violation. Изменение старых lists/ValidStatus на иную логику требует отдельного решения. [VERIFIED: spec/EVIDENCE-CONTRACT.md:202-241; ValidationPublishEntity.cs:11-18; ValidatorComponent.cs:97-107]

Также старые callers создают RuleEvaluationResult с Passed/FailingBindings и без явного Status: enum default равен Passed. Новые typed fields должны различать «не предоставлены» и «пустая population», не интерпретировать default как доказанный verdict и не восстанавливать canonical из bool. D-02 закрепляет explicit unavailable typed data → `unknown` + diagnostic, сохранив legacy surface. Planner определяет только association и путь диагностики, не выбирает verdict по bool. [VERIFIED: RuleEvaluationResult.cs:19-30; EvidenceStatus.cs:11-20; ValidationPublishPackageBuilderTests.cs:39-46,79-85,116-123]

### Рекомендуемая форма решения (proposal, не готовая реализация)

**Предпочесть A: version-specific models + единый schema union.** Сохранить старую shape отдельной ветвью, новую rule collection — в новой ветви. Root schema принимает обе через непересекающиеся exact version discriminators; общий status enum остается единственной authority. Python использует отдельные strict models и явный dispatcher; C# — version guard и соответствующие DTO/reader branches. Старый token `"1"` закрепить как явный read-compat alias старой shape с сохранением самого token, не как новый writer token. Точный новый token и имена моделей/полей выбирает planner и проверяет checker; здесь они не объявляются shipped values.

**Допустим B: отдельные versioned schemas/models + общий dispatcher.** Выделить старую и новую schema, но сохранить единый публичный validation entry либо root union для прямых schema consumers. Плюс — явная изоляция v1, минус — риск сломать DE-01, который валидирует dict напрямую через schema loader, минуя model factory. Разрозненные version checks в каждом caller не подходят.

Оба варианта — технические способы уже утвержденного D-01, не альтернативы envelope collection. Один permissive superset с optional collection без version-specific запретов не рекомендуется: он допускает новую shape под старым token и теряет strict validation. `extra="allow"`, silent stripping неизвестных полей и угадывание версии по наличию collection запрещены как обход совместимости. Основания для выбора: explicit strict shape выше и PATTERNS P2/P5; работоспособность новой реализации еще должна быть доказана тестами.

### Writer policy и обязательная матрица

Рекомендация: сохранить явный old-v1 construction/serialization path, новый closure producer направить на новую версию с rule collection. Не повышать общий constant вслепую: existing factories и DE-01 связаны с ним. Допустим global default bump только при сохраненном явном old-output path, точном inventory affected callers и independent check; совместимость старого output не обеспечивается переписыванием expected fixtures. Новая publish emission должна быть проверена на actual producer JSON и persisted bytes, не только direct model unit test.

| Input / output | Требование к совместимости / validation |

| Old v1 `"1.0.0"` без collection | Читается C# и Python; проходит old schema branch; старый fixture output сохраняет token, shape и значения, без добавления пустой collection или переписывания timestamp |

| Old token + new collection | Отвергать на strict validation, а не silently drop/upgrade |
