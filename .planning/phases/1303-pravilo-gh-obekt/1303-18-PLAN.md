<objective>
The human half of D-54 (DGOPN-05; decisions D-54, D-55, D-56, D-57, D-58, D-59, D-60), plus delivery and live acceptance.

The operator reviews a generated calculator in the Web UI Mapping panel: its code, its values on real boxes, the rule verdicts. They confirm it into the company catalogue, reject it, or (as owner) retire a catalogue entry. The change is then deployed to the running stack and accepted live (V13): generate → run → confirm → reuse in a second project without the LLM → isolation from another company → retire.

Purpose: D-57 puts confirm and reject in human hands in the Web UI. The owner expects stack fixes deployed and re-tested live, not only committed.

Server side: the store comes from plan 1303-16 and the resolver, vocabulary and routes from plan 1303-17. This plan adds no server code.

**Retire rights and confirming again (D-59, owner decision 2026-10-21):** an owner of any project in the company may retire a catalogue entry. The retire cascades to the copies in the other company projects, deletes nothing and keeps history. A retired calculator may be confirmed again later: the review card lists it as retired with a Confirm again button.

**Only an owner confirms a retired calculator again (D-60, owner decision 2026-10-21).** The card shows Confirm again only when the response's `canRetire` is true (the owner check of plan 1303-17); a non-owner sees an owner-only hint instead. A retired calculator has no Reject button and no regenerate action, since a reject would turn its paused hash into a permanent rejection; the server refuses both anyway (plans 1303-16 and 1303-17). Task 3 records `retirePolicy: "D-59"` and the PROTOCOL line «Право отзыва»; it asks the owner no question about it.

Server contract from plans 1303-16 (store) and 1303-17 (routes); read both SUMMARYs for the final shapes:
- `GET /scripts/property-calculators/candidates?project&runId` → `{project, companyAssigned, canRetire, run, candidates, blocked, catalogue}`. Each candidate carries its own `run {runId, createdAt}|null`, `retired` and `catalogueId`. A retired copy (D-59) is a candidate with `retired: true`, whose run may be its `sourceRunId` run when the selected run holds no values for it. `blocked` holds rejected rows only; a retired copy is never in it (D-60). `canRetire` is the owner check of the requesting project.
- `POST /scripts/property-calculators/confirm` with body `{project, dataPropertyIri, sha256, runId, meaning, unit?}` → `{catalogueId, entry, alreadyConfirmed, reconfirmed, reactivatedCopies}`. On a retired copy it confirms the entry again (D-59) for an owner only; a non-owner gets 403 `CATALOGUE_RECONFIRM_OWNER_REQUIRED` (D-60). An absent or blank unit keeps the stored calculator unit.
- `POST .../reject` with body `{project, dataPropertyIri, sha256, reason, regenerate}`. A retired copy is refused with 409 `CALCULATOR_IN_CATALOGUE`, with or without regenerate (D-60).
- `POST .../retire` with body `{project, catalogueId, reason}` (owner role of the requesting project, D-59).
- Error codes (twelve; nine store codes of plan 1303-16 and three route-level codes of plan 1303-17):
  - `CALCULATOR_NOT_FOUND`, `CALCULATOR_NOT_PENDING`, `CALCULATOR_CHANGED`, `CALCULATOR_INTEGRITY`;
  - `CALCULATOR_RUN_NOT_FOUND`, `CALCULATOR_RUN_INVALID`, `CALCULATOR_INPUT_INVALID`, `CALCULATOR_IN_CATALOGUE`;
  - `CATALOGUE_COMPANY_REQUIRED`, `CATALOGUE_PROPERTY_TAKEN`, `CATALOGUE_ENTRY_NOT_FOUND`;
  - `CATALOGUE_RECONFIRM_OWNER_REQUIRED` (D-60).
- Log line `property calculator LLM generation requested: <iri>`, written to stderr by the logger `dg.property_calculator_generation` (plan 1303-16 attaches its own handler, because data-service configures no root logging). It appears in `docker logs data-service`.
