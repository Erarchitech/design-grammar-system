<objective>
Close JOIN B — which Computgraph parameters a Metagraph rule actually constrains, and whether the rule's limit can be checked from parameters alone — as a loadable binding artifact plus a determinability classifier and a SWRL threshold reader.

Purpose: a rule like `R_URB_HEIGHT_MAX_75_V` names a *metric* (height), not a parameter. Without an explicit binding, the generator either guesses which sliders matter or asks the model to guess, and both produce confident nonsense. Worse, without a determinability classification the system will claim a rule is satisfied when the metric depends on geometry the model never evaluated — 38-CONTEXT.md names overclaiming here as the phase's credibility risk (D-09).

Output: `data-service/cg_input_bindings.py` exposing binding load, parameter selection with architect override, determinability classification, and SWRL limit extraction; plus the `inputBindings` key populated in `llm/structure_rules.json`.
</objective>

- `class RuleNotFoundError(ValueError)`.
- `read_rule_limit(session, rule_id, project) -> RuleLimit | None`.

`read_rule_limit` runs one parameterized read query matching the Rule by `Rule_Id` and `project`, traversing `HAS_BODY` to Atoms of `type = 'BuiltinAtom'`, and for each collecting the builtin `iri`, the `ARG {pos:1}` target's `Var.name`, and the `ARG {pos:2}` target's `Literal.lex` and `Literal.datatype`. Order by the `HAS_BODY.order` property so the result is deterministic.

Resolution rules:
- **No Rule node with that `Rule_Id` in that `project`** → raise `RuleNotFoundError`. The caller turns this into 422 `COMPUTGRAPH_GENERATE_INPUTS_RULE_NOT_FOUND`.
- **Rule exists but has no comparison BuiltinAtom** → return `None`. A rule with no numeric limit is not an error; it simply has nothing for the sampler to bound against.
- **Exactly one comparison BuiltinAtom whose iri is in `BODY_BUILTIN_TO_CONSTRAINT` and whose pos-2 arg is a `Literal` parsing to a float** → return the `RuleLimit` with the *inverted* operator.
- **More than one such atom** → return `None` and log one warning naming the `Rule_Id` and the competing builtins. A conjunction of bounds is real and legitimate, but this phase samples against a single limit; claiming to honour the first of several would be exactly the overclaim D-09 forbids. Returning `None` demotes the rule to unbounded sampling, which under-claims.
- A pos-2 arg that is a `Var` rather than a `Literal`, or a `lex` that does not parse as a float, → `None` with a warning.

Every query must be parameterized (`$ruleId`, `$project`) — never string-interpolated. The function performs no write.

`classify_rule(session, rule_id, project, bindings, parameter_overrides=None) -> RuleClassification`:
- Calls `read_rule_limit` first, so `RuleNotFoundError` surfaces before any binding work.
- Looks up the binding. **No binding → `determinability="geometry-required"`, empty `parameterNames`, `limit=None`, `source="default"`** (D-08's safe direction).
- A binding → carry its `determinability`, `parameters`, `metricExpression`, `monotoneIn`, with `source="binding"`.
- `parameter_overrides` non-empty → replace `parameterNames` with the override list and set `source="override"` (D-06). The override changes *which* parameters, never the determinability class: an architect may say which sliders matter but cannot declare a geometry-level rule checkable.
- **Force `limit=None` whenever `determinability == "geometry-required"`.** A limit the system cannot legitimately check must not be carried forward where a downstream prompt or validator could act on it. This is the single line that makes D-09 structural rather than aspirational.

`select_parameters(classification, published_parameters) -> tuple[list[dict], list[dict]]` returns `(bound, excluded)` over the published `:Parameter` rows:
- When `parameterNames` is non-empty, only parameters whose `parameterName` matches are considered; the rest are simply out of scope and appear in neither list.
- When `parameterNames` is empty (the `geometry-required` default), **every** eligible published parameter is considered — a geometry rule still gets candidates, it just gets no satisfaction claim.
- A considered parameter is **excluded with a reason** when: `paramKind != "Variable"` → `non-variable-kind` (D-05); `dataType` not in `{Float, Integer, Boolean}` → `unsupported-datatype` (GHIN-02); `domainMin`/`domainMax` null for a Float or Integer → `missing-domain` (RESEARCH R2 — never guess a domain); `reinstateParameterId` absent or blank → `unresolved-reinstate-id` (D-04).
- Each `excluded` entry carries `cgId`, `parameterName`, `reason`. Each `bound` entry carries the full row plus a `stateType` field holding the mapped ParamState type: `Float→Number`, `Integer→Integer`, `Boolean→Boolean`.
- Order both lists by `parameterName` so responses are deterministic.

A `Boolean` parameter legitimately has no numeric domain — it must not be excluded as `missing-domain`. Handle that explicitly rather than relying on the check order.
