Decisions made at planning time that the executor must implement as written. 39-CONTEXT.md left exactly one item open (capture-endpoint auth, resolved in Plan 02 as P-01); the rest below are implementation refinements required to make the locked decisions executable, not reversals of them.

**P-02 — ValidStatus derivation rule (implements D-05 and D-07).**
The verdict source is the existing SHACL / dg-reasoner path per **D-05** — `dg-reasoner/valid_graph_export.py` builds its ABox directly from `run.statePayloadJson`, so a `status:'captured'` row is SHACL-validatable with zero new export work. The watcher calls the existing `_call_shacl_validate` helper unchanged (injected as `shacl_fn`); no second evaluator is written, and no rule evaluation happens in Python.

`dg-reasoner`'s SHACL envelope is deliberately sanitized: `reasoning._enrich_shacl_result` emits `{severity, what, where, howToFix, focusLabel, shapeId}` and its own docstring states that no raw focus-node IRI ever appears in the result. So a focus node cannot be joined back to an ObjState by IRI. The only available join key is `focusLabel`, which `valid_graph_export._state_label` stamps for `objStates` as `label or objectRef or stateId`. Therefore:
- Build an index map from the capture envelope's `objStates`, keyed by `label or objectRef or stateId` → list index.
- `conforms` truthy → `ValidStatus` is all-true, length == `len(objStates)`.
- `conforms` falsy → start all-true; each finding with `severity == "violation"` whose `focusLabel` hits the map sets that index false; every violation that does not hit the map increments an `unmapped` counter.
- `unmapped > 0` → set every entry false. Rationale: an unattributable violation must not be reported as a passing state. This is the conservative reading of D-07's "where resolvable".
- Empty or unparseable `statePayloadJson` → return an empty list. The function never raises.

**P-03 — Fixture project string: `p39-autoval`.**
Per the Phase 37-01 convention in `data-service/tests/README.md` ("any test that publishes into a live Neo4j must scope itself to a project string no other suite uses"), Phase 39 pins `p39-autoval` — distinct from `p37-structure` (`cg_fixtures.py`), `p1` (`test_computgraph_publish.py`) and `default-project`. Defined once in `data-service/tests/dsav_fixtures.py` and imported everywhere else in the phase.

**P-04 — Debounce quiescence is read off the row, not off a wall-clock timer.**
D-15's in-memory guardrail state holds the per-project rate-limit window (a list of completion timestamps). The debounce decision itself compares an injected `now` against the newest row's `capturedAt`, so it is fully deterministic under a fake clock and survives a process restart correctly. No timer thread, no `time.sleep` in the pure path. This satisfies D-14's trailing-edge semantics: the project is only validated once it has been quiet for `debounceWindowSeconds`.

**P-05 — The poll loop is fully synchronous and blocking per tick.**
One SHACL call is in flight at most, ever. `poll_once()` returns before the next tick begins. This closes RESEARCH.md Open Question 1 (poll interval vs. `DG_SHACL_HTTP_TIMEOUT_SECONDS`) by construction rather than by tuning: a slow SHACL call simply delays the next tick, it can never overlap one. It also makes RESEARCH.md Pitfall 4 moot — a transitional `status:'processing'` claim state is unnecessary at single-worker uvicorn and is named as ADR follow-up scope in Plan 05, not built here.

**P-09 — Corrections to the `[ASSUMED]` Cypher shapes proposed in 39-RESEARCH.md §Code Examples.**
Those four shapes are researcher proposals, explicitly not existing code, and two of them are defective as written. The corrections below are mandatory; the corrected forms still require live-Neo4j confirmation in Plan 03.
- `COALESCE_QUERY` as proposed uses `UNWIND runs[1..]`, which yields zero rows when there is exactly one captured row — the whole query then returns nothing and the caller loses `keptRunId`. Use a `FOREACH` over the tail instead, which always returns its row.
- `FAIL_QUERY` as proposed reads `run.attempts` twice inside one `SET` clause (once to increment, once inside the `CASE`), which is order-dependent. Compute the next value in a `WITH` first, then `SET` from that binding.

<assumption_delta_decision>
**Noun now primary:** `:ValidationRun` — unchanged as the label, but its semantics widen in three directions at once: `status` becomes a state machine (`captured` → `completed` | `superseded` | `failed`) where a row can exist having never run; `trigger` gains `'auto'` where manual was previously the only case; `verdictSource` gains `'shacl'` alongside the SWRL verdict every existing reader implicitly assumes.

**Decision: `add-alongside`.** Reuse the existing `:ValidationRun` label, key `{graph, project, runId}`, and property vocabulary; add `trigger`, `verdictSource`, `capturedAt`, `completedAt`, `attempts`, `lastError` as additive properties. Do not promote a new `:DesignStateCapture` or `:CaptureEvent` noun. Rationale: D-01 chose row reuse precisely to avoid the ~10-file schema-propagation sweep CLAUDE.md mandates, and an investigation phase must not spend its budget on a schema migration it may recommend against.

**Accepted debt.** Three specific costs, all of which belong in the DSAV-03 ADR (Plan 05):
1. A row with `status:'captured'` is a "run that has not run" — semantically muddy, conceded by D-01 itself.
2. `list_validation_runs` (`data-service/app.py:691-713`) has **no status filter** and orders by `run.createdAt DESC`. Verified this session. D-12 accepted run-list pollution for completed auto-runs; this finding widens it. So `captured`, `superseded` and `failed` rows all surface in `GET /validation/runs/{project}`, the VALIDATION GRAPH component, and the ui-v2 Model screen — with null Speckle identifiers and (pre-verdict) null `ValidStatus`. This is broader than D-12's "auto-runs stay visible": **non-completed rows are visible too.** The mitigation in this phase is that `createdAt` is stamped at capture time so ordering stays sane, plus the tolerance invariant below.
3. A `verdictSource:'shacl'` verdict answers "is this captured state well-formed?", not "does this design comply?" (D-06). Readers cannot tell the difference without inspecting `verdictSource`.

**What would force a later `promote`.** Any one of: (a) a second non-SWRL verdict source arrives, making `verdictSource` a genuine dimension rather than a flag; (b) a reader needs to page or filter runs and the `captured`/`superseded` rows become a correctness problem rather than noise; (c) the Phase-29-flagged first-class `:DesignState` node lands, at which point the capture event has a natural home and no longer needs to squat on `:ValidationRun`.

**Invariant test (implemented as `test_list_runs_tolerates_auto_rows`, Plan 03 Tier 2):** with `captured`, `superseded`, `failed` and `completed`/`verdictSource:'shacl'` rows all present for one project, `list_validation_runs(project)` returns without raising and every row it returns carries a `runId`.
</assumption_delta_decision>

  <behavior>
    Expected behavior of the pure poll body, driven entirely through an injected session and an injected clock. Each bullet becomes at least one assertion in Task 2.
    - No enabled project rows → `poll_once()` returns a summary reporting zero projects and performs no writes. An always-running thread is therefore harmless when nothing is opted in.
    - One enabled project whose newest captured row is younger than `debounceWindowSeconds` → project is skipped with reason `debounce_wait`; no coalesce, no SHACL call, no writes.
    - One enabled project whose newest captured row is older than `debounceWindowSeconds`, with 5 captured rows total → coalesce keeps the newest `runId` and reports 4 superseded; exactly one SHACL call is made, for the kept run only.
    - Rate limiter: with `rateLimitPerMinute` completions already recorded inside the trailing 60 seconds for that project, the tick is skipped with reason `rate_limited` and no SHACL call is made.
    - `shacl_fn` returns `{"status":"ok", "conforms": true, ...}` → the complete path runs with `trigger='auto'`, `verdictSource='shacl'`, an all-true `ValidStatus` of length `len(objStates)`, and a `completedAt` timestamp; the completion timestamp is appended to the project's in-memory rate-limit window.
    - `shacl_fn` returns `{"status":"timeout"}` or `{"status":"unavailable"}`, or is `None` → the fail path runs: attempts increments, status stays `captured` while attempts < `maxAttempts`, and flips to `failed` on the `maxAttempts`-th failure, with `lastError` recording the reason. **This is the D-08 departure**: the analog caller in `publish_validation` treats the same status dict as non-fatal and completes the run anyway (Phase 823 degrade-never-raise). The watcher must not inherit that policy — an auto-run that silently completes with no verdict is worse than a manual one because nobody clicked anything to watch it.
    - `conforms` false with a violation whose `focusLabel` matches an ObjState key → only that index is false.
    - `conforms` false with a violation whose `focusLabel` matches nothing → every index is false (P-02 conservative fallback) and the summary reports the unmapped count.
    - `publish_fn` is only invoked when the project's config has `publishEnabled` true AND the run completed; it is wrapped so that any exception it raises is swallowed and reported in the summary — a publish failure never reverts or fails an already-persisted verdict.
    - `derive_valid_status()` never raises on malformed input and returns an empty list for an unparseable or objState-less envelope.
  </behavior>

Cypher constants, all plain (non-prefixed) triple-quoted string literals with every value passed as a bound parameter — no interpolated or concatenated query construction anywhere:
- `ENABLED_PROJECTS_QUERY` — matches `IntegrationConfig {graph:$graph, provider:'AutoValidation'}` where `cfg.enabled = true`, returns `cfg.project AS project`.
- `CONFIG_READ_QUERY` — matches the same node additionally keyed on `project:$project`, returns `enabled`, `publishEnabled`, `debounceWindowSeconds`, `rateLimitPerMinute`, `maxAttempts`.
- `CONFIG_UPSERT_QUERY` — `MERGE` on `{graph:$graph, provider:'AutoValidation', project:$project}` then `SET` those five fields plus `cfg.updatedAt = $updatedAt`. Mirrors `upsert_integration_config` exactly except for the provider literal and the field list. Absent row means disabled (D-13) — never create the row implicitly, and do not extend `_auto_configure_integration`'s implicit-create precedent to this provider.
- `CAPTURE_QUERY` — `MERGE (run:ValidationRun {graph:$graph, project:$project, runId:$runId})` then `SET` `run.statePayloadJson = $statePayloadJson`, `run.status = 'captured'`, `run.trigger = 'auto'`, `run.capturedAt = $capturedAt`, `run.createdAt = $capturedAt`, `run.SendStatus = false`, `run.attempts = 0`. `createdAt` is mandatory because `list_validation_runs` orders by it; `SendStatus` is false because auto-runs are persist-only by default (D-09).
- `NEWEST_CAPTURED_QUERY` — matches captured rows for the project, orders by `capturedAt` descending, collects, and returns `runId`, `capturedAt`, `coalesce(attempts, 0)` and the captured-row count of the newest row (nulls when the project has no captured rows).
- `COALESCE_QUERY` — matches captured rows for the project, orders by `capturedAt` descending, collects into `runs`, binds `runs[0]` as the kept row and `runs[1..]` as the stale tail, uses a `FOREACH` over the tail setting `status = 'superseded'`, and returns the kept `runId` plus the tail size. Per P-09 do **not** use `UNWIND` for the tail — an empty tail would suppress the entire result row. Scope the initial match strictly to `status:'captured'` so a row a prior tick already completed can never be superseded (39-RESEARCH.md Pitfall 5).
- `COMPLETE_QUERY` — matches the run by `{graph, project, runId}` and sets `status = 'completed'`, `trigger = 'auto'`, `verdictSource = 'shacl'`, `shaclReportJson = $shaclReportJson`, `ValidStatus = $validStatus`, `completedAt = $completedAt`. Modelled on `_persist_shacl_report`'s `SET`-in-place shape (D-10: a `SET` in place, no new persist function, `store_validation_run` untouched).
- `FAIL_QUERY` — matches the run, binds `coalesce(run.attempts, 0) + 1` as `nextAttempts` in a `WITH`, then sets `attempts` from that binding, sets `status` via a `CASE` comparing `nextAttempts` against `$maxAttempts` (`failed` at or above, `captured` below), sets `lastError = $reason` and `trigger = 'auto'`, and returns `nextAttempts` and the resulting status. Per P-09 the `WITH` binding is mandatory — reading `run.attempts` twice inside one `SET` is order-dependent.

Config value object: a `@dataclass` `AutoValidationConfig` with fields `enabled: bool`, `publish_enabled: bool`, `debounce_window_seconds: float`, `rate_limit_per_minute: int`, `max_attempts: int`, each defaulting to the module constants (`enabled` defaults false). A `from_row` classmethod coerces nulls to defaults so a partially-populated config row is still usable.

Nothing is written to Neo4j for guardrail bookkeeping — no write amplification against the database being polled. Add a module docstring line recording that a process restart resets this window, which is accepted for this spike and is an explicit ADR line (D-15).
