<planner_decisions>
**P-11 — Evidence lands at `/app/data/dsav-evidence.json` inside the container, then is copied to the phase directory.**
`docker-compose.yml` mounts the repository into `data-service` as `.:/mnt/repo:ro` — **read-only**, verified this session. An in-container test therefore cannot write into `.planning/`. The writable bind mount is `./data-service/data:/app/data`. The driver writes to the path in env `DSAV_EVIDENCE_PATH`, defaulting to `/app/data/dsav-evidence.json`; the host sees it at `data-service/data/dsav-evidence.json`; the executor copies it to `.planning/phases/39-designstate-auto-validation-investigation/39-EVIDENCE.json` and commits only the copy. Do not commit anything else out of `data-service/data/` — that directory also holds connector credentials and encrypted LLM settings.

**P-12 — The driver drives HTTP against the running service, not the app object.**
SC1's claim is that the loop closes *hands-off on live Docker*. A `TestClient`-driven capture would exercise the route but bypass the real uvicorn process whose lifespan owns the watcher thread — the loop would not actually be closed by the daemon. The driver therefore posts with `httpx` to `http://localhost:8000/designstate/capture` when run from the host, or `http://data-service:8000/...` when run inside the compose network, selected by env `DSAV_TARGET_BASE_URL` (default `http://localhost:8000`). Read-back assertions go straight to Neo4j through the `neo4j` driver.

**P-13 — Timings come off the row, never off a stopwatch.**
Latency is `completedAt − capturedAt` parsed from the row's own ISO-8601 properties. 39-RESEARCH.md's measurement methodology is explicit that these are the authoritative, auditable numbers; an in-process timer would also fold in the poll interval's phase offset in a way that is not reproducible. The poll interval is recorded alongside the latency so the note can state that observed latency is bounded below by capture-to-next-tick and is dominated by the debounce window.

**P-14 — Guardrail parameters for the measured runs are pinned so the numbers are reproducible.**
The SC1 loop-closure run uses `debounceWindowSeconds` 2.0, `rateLimitPerMinute` 30, `maxAttempts` 3, `publishEnabled` false, with `DSAV_POLL_INTERVAL_SECONDS` at its 2.0 default. The SC2 burst run uses `debounceWindowSeconds` 5.0 and `rateLimitPerMinute` 3 so the limiter actually binds and produces a non-trivial runs-per-minute figure rather than a number that merely reflects how fast the loop happens to be. Every parameter is written into the evidence artifact next to the measurement it produced — a measurement without its configuration is not evidence.
</planner_decisions>
