<objective>
Fix the two Python-side defects Phase 1200's DE-01 run routed into this phase: the dg-reasoner leg's
false `no_population`, and the null `inputHash`/`outputHash` at the live service boundary.

These are independent of the C# work in plans 01–04 — different language, different files, no shared
edits — so this plan runs in wave 1 alongside plan 01.

**The D-09 root cause is diagnosed and independently verified. Do not re-diagnose it, and do not
rewrite `ontology/dg-shapes.ttl` on a guess.**

- `tools/de01/legs.py:333` calls `POST /shacl/validate` with `json={"project": project}` only. It
  never passes `run_id`.
- `dg-reasoner/reasoning.py:473-479` — `run_shacl`'s own docstring states that **without** `run_id`
  it validates the project-level Metagraph/OntoGraph export only; the run's ValidGraph ABox
  (`build_valid_graph`) is unioned in **only when `run_id` is supplied**.
- The seeded golden `Object` nodes live in that ValidGraph/Computgraph ABox. `dgc:ObjectShape`
  therefore targets a class absent from the graph pySHACL actually validates → zero focus nodes →
  `conforms=true` → the leg reports `no_population` on every row.

It is a missing argument at a call site, not a shapes-authoring defect.

**The expected consequence, planned for explicitly.** Passing `run_id` will make the leg genuinely
evaluate — and then surface a *new*, different disagreement. SHACL still cannot express "height >
75": `spec/RULE-PARTITION-POLICY.md` reserves quantitative rules to the SWRL VALIDATOR. So
`OBJ_GOLD_FAIL` will be structurally conforming (`passed`) while the other legs correctly report
`failed`. And `passed` is **not** in `report.py`'s `_DECLARABLE_STATUSES`, so that difference would
classify as `silent_disagreement` and fail D-11's gate.

The handling is fixed by decision, not left open: the leg adapter maps "SHACL has nothing meaningful
to say about this business rule" to **`not_evaluated`**, which is already declarable.
**Do not widen `_DECLARABLE_STATUSES` to include `passed`** — that weakens the gate for every future
run, which D-10 forbids. Adding a height-checking SHACL shape to force agreement is equally
forbidden: it would encode the same business rule twice and violate the partition policy.

**D-12 fix shape — decided, with the reasoning recorded.** RESEARCH offered two options and asked the
planner to pick. The choice is **(b): `report.py` falls back to the envelope-level hash when a row
carries none.** Reasoning: the C# harness already computes a real envelope-level hash
(`DG/tools/DG.De01Harness/Program.cs:284,294` via `CanonicalJsonWriter.HashCanonical`), so the hash
exists and is correct — what is broken is only that `report.py:127-128` reads a row-level field no
call site populates. D-12's stated goal is that "the envelope must carry real hashes where the legs
actually meet", and the meeting point is the DE-01 report. Option (a) would populate row-level
hashes across three call sites in two languages to add genuine per-row granularity — real value, but
value this phase's gate does not need, and `spec/EVIDENCE-CONTRACT.md` § 3 already defines the
row-level hash as **optional** ("where the envelope-level hash is insufficiently granular"), not as
a required field. The remaining per-row granularity gap is recorded as a declared, documented
limitation rather than silently closed — consistent with this milestone's governing sentence.

Output: a dg-reasoner leg that genuinely evaluates, a declarable status for what SHACL cannot say,
and non-null hashes in the report.
</objective>
