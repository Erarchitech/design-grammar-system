<objective>
Ship the harness-side LLM sample outcome taxonomy and provenance guards: a new `outcome_taxonomy.py` module exposing the D-14 closed outcome-label set (`valid` / `valid_after_retry` / `invalid` / `abstained` / `truncated` / `refused` / `provider_error`), an oracle-free `classify` (D-18), the D-15 first-attempt-vs-final + attempts distribution inputs, and D-16 explicit-channel-only abstention (G6 excluded; rule-ingest = "not supported by output contract"); plus the D-19 sibling provenance field tuple and void guard in `corpus.py`, and `test_outcome_taxonomy.py` + `test_provenance.py` covering both. Harness-side only — no production/envelope change (D-23).

Purpose: 1204's LLM-sampling arm must classify every sample into the D-14 proposal taxonomy and record a complete D-19 provenance block, without ever borrowing the frozen 1200 verdict vocabulary or comparing against expected labels. Today that classification logic is spread across `cg_recognition.py`'s guard stack and `dg_context.py`'s `validate_cypher` codes, and the only provenance guard (`assert_provenance`) covers result rows, not LLM samples. This plan centralises the taxonomy and adds the sample-provenance void guard in isolation, so the later sampling sweep emits a well-typed `valid_after_retry`/violation_code record and rejects any sample whose provenance block is incomplete or credential-carrying.

Output: new `data-service/tests/recognition_eval/outcome_taxonomy.py`, `test_outcome_taxonomy.py`, `test_provenance.py`, and additive sibling constants/functions in `data-service/tests/recognition_eval/corpus.py`.
</objective>
