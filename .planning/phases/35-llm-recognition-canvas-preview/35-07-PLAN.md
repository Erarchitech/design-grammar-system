<objective>
Extend `data-service/llm_gateway.py` with the generation controls recognition needs: an internal-only `GenerationOptions`, per-provider structured-output capability negotiation, per-provider max-token spelling, pinned temperature, and a `truncated` signal on the response.

Purpose: three of the phase's blockers live in the gateway — uncontrolled temperature (D6, a reproducibility defect), a hardcoded 4096 output cap (the direct cause of UAT F1), and no way to detect that the cap was hit. None of the recognition work can be measured until these are fixed.
Output: a backward-compatible gateway that recognition can drive precisely, with the public `/llm/generate` attack surface unchanged.
</objective>

<plan_decisions>
- **`GenerationOptions` is internal-only and never reaches FastAPI.** `GenerateRequest` is literally the request body of the public `POST /llm/generate` route in `app.py`. Any field added there is attacker-controllable. `GenerationOptions` is a separate Pydantic model, constructed only by in-process callers, passed as `options=` keyword.
- **`options` is optional with today's defaults.** `LLMAdapter.generate(self, req, api_key, options: GenerationOptions | None = None)`. When `options is None`, each adapter reproduces its current behaviour exactly — `max_tokens: 4096`, Ollama `temperature: 0.1`, no `response_format`/`output_config`. This keeps `/llm/generate`, the two n8n workflows and `dg_context.generate_validated_cypher()` bit-compatible; only recognition opts in.
- **Three spellings, hidden in the adapters.** Anthropic `max_tokens` (required by the Messages API), OpenAI `max_completion_tokens` (`max_tokens` is deprecated and **rejected** by o-series and GPT-5.x — the current body at `:232` would 400 against those), Ollama `options.num_predict`. Callers pass one `GenerationOptions.max_tokens`.
- **`negotiate_structured_output()` lives in `llm_gateway.py` and takes/returns plain data.** It must not import `cg_schemas`, or the gateway acquires a dependency on the recognition layer. Its capability object exposes `mode` and `schema_for(schema_dict)`, where the caller has already run `cg_schemas.to_strict_json_schema()`; `schema_for` returns the dict or `None` depending on `mode`. Dependency arrow stays recognition -> gateway.
- **Detection heuristic is conservative and table-driven** (AI-SPEC §4 *Detection heuristic*): anthropic + 4.5-or-later family ⇒ `json_schema_strict`; openai with unset-or-`api.openai.com` baseUrl ⇒ `json_schema_strict`; openai with any other baseUrl (DeepSeek, Groq, Together, Azure) ⇒ `json_object`; ollama at/after the structured-output release ⇒ `json_schema_strict`; **everything else ⇒ `none`**.
- **DeepSeek gets the `json_object` nudge, not strict.** It reaches us through `OpenAIAdapter` via `baseUrl` (`llm_gateway.py:337`), so it *looks* like OpenAI but supports only `response_format: {"type":"json_object"}`, requires the literal word "json" in the prompt, and its docs warn it "may occasionally return empty content" — which is very likely UAT F3's `deepseek-v4-pro` empty-text-×3. Never branch on `provider == "openai"` to decide strictness; branch on the negotiated mode.
- **Ollama version probe is best-effort and cached.** `GET /api/version` with a short timeout; any failure ⇒ `none`. A local Ollama being down must degrade the mode, never raise into recognition.
- **No async conversion.** AI-SPEC §4b *Async-First Design* is explicit: the adapters stay synchronous `httpx.Client`, the handlers stay plain `def` so FastAPI keeps using its threadpool. Converting handlers to `async def` while leaving sync `httpx.Client` inside would move a 120 s blocking call onto the event loop — strictly worse than today.
</plan_decisions>
