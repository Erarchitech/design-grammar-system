<plan_decisions>
- **The system prompt is a file, not a string constant.** `data-service/prompts/recognition_system.md`, loaded at runtime. Diffable in review, pinnable by the eval harness, and it is the natural provider-prompt-cache prefix because it is byte-identical across every call.
- **`PROMPT_VERSION` starts at `r35.4`** and is declared in a YAML front-matter block at the top of the markdown file so both a human and the loader read the same value. `r35.1`–`r35.3` are treated as the as-shipped lineage graded by arm A0; the fixed prompt is a new version, not an edit to an old one. AI-SPEC §4b.5: without a version, *"recognition got worse"* is unattributable.
- **The grammar double-framing is stated as two separate headed sections, and the negative is stated explicitly.** Not one balanced paragraph. AI-SPEC §4b.2 supplies the wording; the key sentences are that untagged components *never* match the convention (that is the definition of untagged), that every candidate is therefore eligible, and that **a rationale citing the naming grammar as a reason to reject is a wrong answer even if the JSON is well-formed**.
- **The fixture is replaced wholesale, and every harmful property is inverted** per AI-SPEC §4b.3's table: conforming input nicknames → non-conforming; `suggestedName` identical-modulo-prefix → visibly different; grammar-citing rationales → graph-evidence-only rationales; 2 homogeneous Interface examples → ≥ 4 heterogeneous kinds; all-accepted → includes an honest abstention.
- **Ordering is fixed in the file and is an eval variable, not an accident.** Lu et al. (ACL 2022) show permuting the same demonstrations swings accuracy from near-SOTA to near-chance with no ordering transferable across models. The abstention example is placed in the middle of the list, and the file carries a comment saying the order is deliberate and that 35-13 sweeps 3 permutations of it.
- **Example member ids are drawn from the Frame fixture's real id vocabulary** (`n-spanscount`, `n-linesdl`, `n-divide-curve`, `n-topchord`, `n-parsplit`, `n-untagged-01`) so the demonstration is recognisably the same world as the corpus — but the demonstrated *nicknames* are rewritten to non-canonical forms, because the whole point is that the model must not read the answer off a name.
- **No code changes here.** `_load_frame_fewshot()` and `_build_recognition_prompt()` are edited in 35-12. Splitting authoring from wiring keeps this plan parallel-safe in Wave 1 and keeps the arm-A1/A2 diff clean.
</plan_decisions>

  <action>
    Create `data-service/prompts/recognition_system.md`. Open with a YAML front-matter block declaring `prompt_version: r35.4` and a one-line `purpose:`. Then write the system prompt body with these sections, in this order:

    **Role and task statement** — the model is classifying untagged components on a Grasshopper canvas into Computgraph entities; the architect has already tagged what they know and those tags are immutable ground truth; the job is to propose entities for what remains so the architect can accept them with one click instead of drawing them by hand.

    **`### The naming convention is an OUTPUT TARGET`** — quote the token forms from `dg_knowledge.py` and state that these are the forms to WRITE INTO `suggestedName`, that the model GENERATES a conforming name rather than looking one up.

    **`### The naming convention is NOT A FILTER`** — state the negative explicitly: untagged components never match the convention, that is the definition of untagged and the reason they need classifying; every candidate is eligible; NEVER reject a candidate, and never write a rationale, on the grounds that its existing name does not match the grammar; a rationale mentioning the naming grammar as a reason is a WRONG answer even if the JSON is well-formed.

    **`### Decide from graph evidence, not from names`** — use wiring direction and degree, group membership, widget kind, and which tagged procedure a node is wired to. Nicknames are a weak hint about MEANING, never about KIND.

    **`### Abstaining is a good answer`** — unsupported ids go to `unrecognized` with a short reason naming the missing evidence; a confidently wrong proposal costs the architect more time than an honest abstention; do not pad the list.

    **`### Output contract`** — the JSON object shape only, matching `cg_schemas.ProposedStructure`: `proposals[]` with `kind`/`suggestedName`/`procedureIndex`/`memberIds`/`confidence`/`rationale`, and `unrecognized[]` with `memberIds`/`reason`; rationale ≤ 30 words; the literal word "json" must appear in this section (DeepSeek's JSON mode requires it in the prompt).

    Do not include the concept catalog, the few-shot, the anchors or the candidate list — those are the per-call user half and stay in `_build_recognition_prompt`.
  </action>
