# AI-SPEC — Phase 35: LLM Recognition and On-Canvas Proposal Preview

> AI design contract generated by `/gsd-ai-integration-phase`. Consumed by `gsd-planner` and `gsd-eval-auditor`.
> Locks framework selection, implementation guidance, and evaluation strategy before planning begins.

**Status:** Remediation spec — Phase 35 shipped (RCGN-01..04 all `[x]`) but **ROADMAP SC1 /
UAT Test 1 is `blocked`**: recognition *quality* was never validated and, on the only live model

## 1. System Classification

**System Type:** Extraction — **hybrid**: deterministic topology pre-classifier + LLM structural
grouping over the ambiguous residue. (Was: pure LLM extraction. The architecture change is the
substance of this spec.)

**Description:**
The recognition pipeline classifies *untagged* nodes on a Grasshopper (visual dataflow / parametric
CAD) canvas into Computgraph ontology entities — `Procedure`, `Pattern`, `VariableParam`,
`ConstantParam`, `EmergentParam`, `Interface` — using the architect's manually tagged entities as
ground-truth anchors. Output is a schema-valid proposed-structure object (kind, suggested
convention name, member component ids, confidence, rationale) that renders on the canvas as
desaturated preview groups for the architect to accept, partially accept, or reject. **Nothing
reaches Neo4j without on-canvas confirmation (RCGN-04).** The user is a single architect working
inside Rhino/Grasshopper; "good" is that the majority of proposed member sets match what that
architect would have drawn by hand, so that confirming is faster than tagging from scratch.

The system is an *accelerator for a human annotator*, not an autonomous classifier. Its economic
value is `time_saved_by_correct_proposals − time_wasted_reviewing_wrong_ones`. A confidently wrong
proposal therefore costs more than an honest `unrecognized` entry — this asymmetry drives the whole
evaluation strategy.

**Critical Failure Modes:**

1. **Grammar-as-filter inversion (LIVE, root cause of the SC1 block).** The model reads the
   annotation-convention naming grammar (`<NN>_IntF_<Name>`) as a *filter* to test untagged
   candidates against, rather than as the *target vocabulary* to generate names in. Since untagged
   nodes never match the grammar by definition, the model rejects everything with circular "does
   not match grammar" rationales. **Verified cause:** the sole few-shot example
   (`fixtures/frame_recognition_fewshot.json`) supplies input group nicknames that already conform
   (`11_IntF_ParSplitAt`) and justifies each proposal with *"matches the Interface naming grammar"*.
   The demonstration teaches filter behaviour; DeepSeek executed it faithfully. Compounded by the
   total absence of a system prompt or task statement (`recognize_structure()` never sets
   `req.system`, though all three adapters support it).

2. **Silent double-ownership / ground-truth corruption.** A proposal that claims nodes already owned
   by a tagged entity, or that two proposals both claim, would destroy the architect's manual work
   once accepted. Currently guarded by validator codes `tagged_overlap` and `duplicate_member`
   (`cg_recognition.py:222-262`) — these are load-bearing and must survive the refactor.

3. **Invented member ids.** A hallucinated component GUID in `proposals[].memberIds` or
   `unrecognized[].memberIds` would produce preview groups referencing nonexistent canvas objects.
   Guarded by `unknown_member_id` as a *validator* check rather than a prompt instruction — that
   distinction must be preserved.

4. **Miscalibrated confidence.** `confidence` is currently a free-form model-asserted float with
   nothing calibrating it, yet it renders directly on-canvas as `[?] <name> (90%)` and is the
   architect's primary triage signal. An overconfident wrong proposal is the single most expensive
   output this system can produce.

5. **Silent scope widening → truncation.** `_filtered_untagged_node_ids` falls back to *all*
   untagged nodes when the requested `procedure_index` has no members (UAT F2), turning an intended
   14-node prompt into 214 nodes, which then exceeds the hardcoded `max_tokens: 4096` and yields
   unterminated JSON with no actionable hint (UAT F1). The user who most needs the "scope to one
   procedure" advice is precisely the one who never sees it.

6. **Over-segmentation / under-segmentation.** Proposing many trivial single-node entities, or one
   giant catch-all group, can both score deceptively well on naive per-node accuracy while being
   useless to the architect. Member-set boundaries are the actual deliverable.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** **Computational / parametric architectural design** — specifically, ontology-
driven annotation of Grasshopper (Rhino) visual dataflow definitions, inside a PhD research system
for architectural design-rule compliance checking. This is deliberately *not* filed as "developer
tooling": the artefact being annotated is a **design model**, and the vocabulary being applied
(`Algorithm` / `Procedure` / `Pattern` / `Parameter` / `Interface`) comes from an
architectural-design-theory ontology — the `dgc:` layer of `ontology/DesignGrammar-V7.owl` — not
from a software ontology. A `Pattern` here means *"the atomic unit of parametric computation… a
single operation"*, in the Woodbury sense of a named, reusable device of design intent; it does not
mean a software design pattern.

**User Population:** **n = 1.** One architect / computational designer, working inside Rhino 8 /
Grasshopper on their own definitions, who is simultaneously the author of the ontology, the author
of the annotation convention, the author of the reference annotation, and the sole judge of output.
Expert in parametric modelling and in this specific ontology; not an ML practitioner. There is no
second reviewer between the model and persistence, no multi-tenant population, no support queue to
sample from. Everything an eval would normally resolve by "ask another user" must instead be
resolved here by frozen references, blind scoring, and behavioural logs (see *Domain Expert Roles*).

**Stakes Level:** **Medium at recognition time · High for research validity.**

Honest accounting of why it is not higher and not lower:

- **Not Critical/High at recognition time.** RCGN-04 is a real containment boundary: proposals render
  as desaturated preview groups, nothing reaches Neo4j without explicit on-canvas confirmation, and
  a single Ctrl+Z removes every trace (UAT tests 2/5 pass). A wrong proposal cannot silently corrupt
  the graph. No safety, no money, no personal data, no third party is exposed by a bad proposal.
- **Not Low.** Four things genuinely are at stake. (1) **The architect's manual tags** are the
  reference annotation for the whole thesis; a proposal that absorbs, splits or renames one destroys
  the only ground truth the system can be graded against. (2) **Accepted proposals are durable and
  indistinguishable from manual work** — they become permanent convention groups that survive save +
  reopen and parse identically to hand tags, separated only by a `source: recognized` flag (UAT test
  4); a wrong grouping accepted today is indistinguishable ground truth in a month. (3) **Confirmation
  bias is a documented, measured effect** in exactly this human-in-the-loop-annotation setting — one
  tired expert clicking Accept is a thinner guard than the architecture diagram suggests. (4) **The
  economics can go negative**: pre-annotation research shows an assistant below a certain
  correct-to-incorrect ratio produces *no* net benefit, because correcting and deleting spurious
  suggestions costs more than annotating from a blank canvas.

**Output Consequence:** proposal → on-canvas preview → architect accepts → permanent convention group
(`source: recognized`, `dg.recognized.<guid>` marker, survives save/reopen) → Phase 36 publish →
`Procedure` / `Pattern` / `Parameter` / `Interface` nodes plus `PATTERN_HOST_TO` and `PARAM_LINK`
relationships in Neo4j → the design-side model that the DG compliance pipeline and the dissertation's
worked examples cite. Two consequences are already observed rather than hypothetical:

1. **One bad proposal can block a whole publish.** An accepted `Const` on a bare Number component
   yields a null `dataType` with no parse warning, and Phase 36's SHACL-backed publish then 422s the
   *entire* payload — 11 valid entities could not land because of 1 invalid one (UAT F5). The
   architect experiences this as *"the AI made me break my publish"*, three phases away from the
   proposal that caused it.
2. **Published structure is what later work cites.** Misattributed structure does not produce a wrong
   building-height verdict directly (compliance verdicts run over Metagraph rules and ValidGraph
   design states, not over the Computgraph), but it does corrupt the provenance and traceability
   chain that the research claims to provide.

### What Domain Experts Evaluate Against

> Five rubric ingredients, in the language a computational designer would use while looking at a
> proposed decomposition of their own script. Ordered by what the architect notices first when the
> answer is wrong. Where a claim is reasoning from this repo rather than external literature, the
> Source line says so.

**Dimension 1 — The architect's own tags are untouched**
- **Good:** No proposal contains a component already owned by a tagged entity; no proposal renames,
  splits or absorbs a tagged Procedure or Pattern; tagged entities are used only as anchors. Every
  `memberId` appears verbatim in the submitted canvas.
- **Bad:** A proposal whose member set overlaps a tagged group; two proposals claiming the same
  component; a member id that is not on the canvas. Any single instance is disqualifying — the
  architect stops trusting the whole run.
- **Stakes:** **Critical.**
- **Source:** `35-CONTEXT.md` constraint *"Tagged entities are immutable ground truth — the LLM may
  not rename, split, or absorb them"*; RCGN-04. Already enforced by `tagged_overlap`,
  `duplicate_member`, `unknown_member_id` in `validate_proposed_structure()`. The *domain* reason the
  code-level guard is not sufficient reassurance: these tags are the thesis's reference annotation,
  so a breach is a research-integrity event, not a UX bug.

**Dimension 2 — Block boundaries: one whole operation, nothing else**
- **Good:** A proposed `Pattern`'s member set is exactly the components that implement **one named
  geometric or parametric operation** — the operation together with the helper components that exist
  only to serve it. A proposed `Procedure` contains the consecutive Patterns that together produce
  one named design step. The architect can accept it with one click and no boundary edit.
- **Bad:** A boundary that cuts a logically atomic operation in half (a `Divide Curve` separated from
  the count input that only feeds it; a `Line SDL` separated from its direction constructor), or that
  fuses two operations related only by canvas adjacency — **even when every individual member is a
  plausible member**. Equally bad: proposals that are technically acceptable only after the architect
  redraws the boundary, i.e. the partial-accept path becomes the normal path.
- **Stakes:** **Critical.** This is the deliverable. Kind and name are one-click fixes on canvas;
  member sets are not — redrawing a group boundary is the single most expensive correction in the
  confirm UI, and it is precisely the correction RCGN-03's partial accept exists to absorb.
- **Source:** `DesignGrammar-V7.md` — `dgc:Pattern` = *"the atomic unit of parametric computation — a
  single operation node"*, `dgc:Procedure` = *"a grouped sequence of Patterns within an Algorithm —
  an organizational unit of computation"*; Woodbury, *Elements of Parametric Design* (patterns as
  named units of design intent, and "clear, meaningful, short names for objects"). Note for the
  eval-planner: the practitioner-meaningful unit here is **edits required to accept**, not per-node
  accuracy.

**Dimension 3 — Kind decided on graph evidence, using the ontology's real discriminators**
- **Good:** `Var` = a designer-manipulable input the architect actually turns during design (slider,
  value list, toggle) with nothing upstream. `Const` = a fixed source set once and left alone —
  including ordinary source components, not only widgets (`11_Const_ptZero` is a point constructor).
  `Emg` = a computed terminal output with nothing downstream. `IntF` = a connector **at a procedure
  boundary**, carrying data between procedures, with an Input/Output direction. The `rationale` cites
  degree, wiring, group membership or the adjacent tagged procedure.
- **Bad:** `IntF` proposed on a relay or bare `Param` that sits *inside* a single procedure (that is
  wire tidiness, not an inter-procedure connector); `Emg` proposed on a node that in fact feeds
  another procedure; `Var` vs `Const` decided from the nickname; a rationale that restates the
  instructions or the naming grammar instead of citing evidence.
- **Stakes:** **High** — with an internal cost gradient the architect genuinely feels and the eval
  should respect: `Var`↔`Const` is a one-click flip *and is partly unresolvable from topology at all*,
  because the ontology defines `ConstantParam` by an **intent** predicate (*"not intended for user
  adjustment"*) that lives in the architect's head; whereas a spurious `IntF` is expensive because
  relays are numerous and each one pollutes the published graph with a meaningless `PARAM_LINK`.
- **Source:** `ontology/DesignGrammar-V7.md` class comments for `VariableParam`, `ConstantParam`,
  `EmergentParam`, `Interface` (*"an inter-procedure connector — exposes data between Procedures…
  maps to Grasshopper connection points at procedure boundaries"*); Grasshopper practice — ALT-drag
  *Insert Relay* is explicitly a wire-management/readability device with no semantics.

**Dimension 4 — The name says what the thing does, and is filed under the right procedure**
- **Good:** `11_Pat_DivideLine`, `11_Var_SpansCount`, `11_IntF_ParSplitAt` — the `<Name>` half names
  the operation or quantity in the architect's own design vocabulary, and the `NN` half matches the
  procedure the entity is actually wired into (first digit = algorithm, remainder = procedure
  ordinal).
- **Bad:** Convention-shaped but semantically empty — `11_Pat_1`, `11_Var_Number`, `11_Emg_Panel`, or
  the bare component type used as the name. Worse, and much harder to spot: a *well-named* entity
  filed under the wrong `NN`, which misplaces it in the published Computgraph while looking
  completely valid on canvas.
- **Stakes:** **Medium** for the `<Name>` half — cheap to retype, but the entire point of annotating
  is that a human or a Cypher query can read the model afterwards. **High** for `NN`: it is
  structural attribution, it is silently wrong, and it persists into Neo4j.
- **Source:** the grammar in `data-service/dg_knowledge.py:156-184`, read directly. Critical
  observation for the eval-planner: the Pattern grammar is `<NN>_Pat_<k>[ <name>]` — the name part is
  **optional**, so `11_Pat_1` is fully conformant. **Syntactic conformance is therefore nearly free
  and is not a quality signal**; only semantic content and correct `NN` are. Practitioner backing for
  the naming standard: Woodbury (clear, meaningful, short names) and the Grasshopper documentation
  best-practice guidance to label groups and params so purpose stays legible.

**Dimension 5 — Honest abstention; coverage is not the goal**
- **Good:** Nodes the system cannot ground in graph evidence appear in `unrecognized[]` with a reason
  that names the missing evidence ("isolated: no wires in or out — cannot distinguish a constant from
  an abandoned experiment"). Confidence spreads across its range and tracks the observed accept rate,
  so the architect can triage top-down and stop at a floor.
- **Bad:** Full coverage at uniformly high confidence (the synthetic UAT payload used a flat `0.9` and
  nothing objected); a confident proposal whose rationale is circular; a node that appears in neither
  `proposals[]` nor `unrecognized[]` — silently dropped.
- **Stakes:** **Critical**, and this is the dimension domain literature speaks to most directly. Machine
  pre-annotation of expert corpora only pays when the correct-to-incorrect ratio is high: a
  high-accuracy pre-annotator (a 93.25% UAS parser) delivered ~1.7× faster annotation *with no loss of
  quality and improved consistency*, and dictionary pre-annotation in clinical NER gave 14-21% time
  savings with no measurable bias; but a low-quality assistant offers **no net gain**, because
  modifying, adding and deleting spurious annotations costs more than starting from blank — and an
  assistance system with only ~10% correct pre-annotations improved nothing on any dimension. This
  system's break-even sits somewhere between those points and is currently unknown. That is the
  quantitative justification for Section 1's asymmetry claim, and it means **precision and honest
  abstention must be graded ahead of coverage**.
- **Source:** Mikulová et al., LREC 2022; Lingren et al., JAMIA 2014; South et al., *J. Biomed. Inform.*
  2014; DALPHI (arXiv 1808.05558); Clark et al., *PeerJ* 2014 — whose rank-and-confirm bioassay
  annotator works *because* "human experts recognize and skip incorrect proposals", a guarantee that
  weakens exactly as proposals become more plausible. Plus RCGN-04: *"never invented, never silently
  dropped"*.

### Known Failure Modes in This Domain

> How generic model failure actually manifests on a Grasshopper canvas. Section 1 already owns the
> live grammar-as-filter inversion; these are the domain-shaped failures an eval must be able to
> *detect*, because each of them produces output that looks correct to a casual reader.

**FM-1 — Grouping by canvas geography instead of dataflow.**
Architects lay components out left-to-right and cluster them visually; `position` is in the context
and is fed to the prompt today, while in/out degree is *not* computed at all (defect D5). Spatial
proximity is therefore the most available signal and the most seductive one — and it is unreliable
in both directions. Relays inserted for tidiness route wires far from their logical partners, hidden
("wireless") connections remove the visual link entirely, and one operation is often spread across
the canvas while two unrelated ones sit side by side. The resulting proposals are the *hardest class
for the architect to catch*, because a spatially-tidy box looks exactly like how they draw boxes
themselves. **Eval implication:** the reference set must contain at least one case where the correct
grouping is spatially interleaved, or this failure is untestable.

**FM-2 — A relay or jumper `Param` read as an `Interface`.**
The ontology is specific: an `Interface` is an *inter-procedure* connector at a procedure boundary,
with an Input/Output direction. Grasshopper users insert relays (ALT-drag) and bare `Param` nodes
freely, anywhere, purely for wire management. Topologically the two are identical — single-in,
single-out, no widget — which is exactly the Tier-0 R4 signature. The discriminator is not degree but
**whether the wire crosses a procedure boundary**. Failure mode in practice: a canvas sprouts a dozen
individually-plausible `IntF` proposals, each defensible in isolation, that together fill the
published Computgraph with meaningless `PARAM_LINK` edges. This is the one failure that scales with
canvas tidiness — the better organised the definition, the more relays, the worse it gets.

**FM-3 — Abandoned and experimental branches annotated as real structure.**
Real definitions accumulate dead matter: trial components left disconnected, disabled or
preview-off branches, half-finished alternatives kept "just in case". Topologically these are
indistinguishable from legitimate structure — a disconnected trial slider looks like a `Var`, a
dead-end branch looks like an `Emg`. Annotating them mints ontology entities for design ideas the
architect *abandoned*, which is the worst kind of noise because it is silently plausible and
survives into Neo4j. The correct answer for a fully isolated node is `unrecognized` with the reason
stated (this is already Tier-0 rule R5's abstention, and the eval must reward it rather than count
it as a miss).

**FM-4 — Over-segmentation into one entity per component (and its mirror, the catch-all).**
The ontology text itself pulls toward this: `dgc:Pattern` is defined as *"a single operation node…
maps to a Grasshopper Component"*, while the shipped convention tags Patterns as **groups** with
multiple members and nesting (`hostPatternId`, `PATTERN_HOST_TO`; UAT test 4 accepted `11_Pat_2
SUBPLOT` with 3 members). A literal reading yields 200 single-member Patterns — technically
defensible against the class comment, useless to the architect, and it would **score well on any
per-node kind-accuracy metric**. The mirror failure is one giant catch-all group covering the
untagged remainder. Both are metric-gaming risks, which is why Dimension 2 is scored on member sets
and edit distance, not per-node labels.

**FM-5 — Taking the surface name as the semantic signal, in either direction.**
Grasshopper nicknames are idiosyncratic and often meaningless (`TARGET SCR`, `Num`, `H` — all real,
from the UrbanBlock UAT run). Two symmetric failures follow from the same root error of reading names
instead of the graph: **over-trust** — adopting `Num` as the entity name, or inferring kind from a
nickname; and **the live inversion** — treating the absence of convention-shaped names as evidence
*against* classification, which is UAT F3 and Section 1 failure mode 1. In a domain where the
ontology is carried *in the names*, this conflation of "names to read" with "names to write" is the
characteristic failure, not an incidental one.

**FM-6 — A plausible proposal that is structurally unpublishable.**
Domain-specific and already observed (UAT F5): a `Const` proposed on a bare `Number` component is a
perfectly reasonable classification that the parser cannot assign a `dataType` to, producing a silent
null that only detonates three phases later at publish — and takes the whole payload with it. The
architect's read of this is not "an edge case in dataType inference"; it is "the AI's suggestion
broke my publish". Any proposal whose kind the accept-time parser cannot fully realise should be
treated by the eval as a **failure**, even though the classification itself was defensible.

### Regulatory / Compliance Context

**No binding external regulation applies at recognition time.** This is a single-user PhD research
system operating on the researcher's own Grasshopper definitions; recognition produces on-canvas
proposals only, touches no personal data, and by RCGN-04 persists nothing without explicit human
confirmation. Listing HIPAA/GDPR/FCA-style constraints here would be padding. Four genuinely
applicable constraints, in decreasing directness:

1. **Academic integrity and reproducibility (binding, and the real constraint).** SC1 is a claim in a
   dissertation. Any reported recognition-quality number must be reproducible: pinned prompt version,
   pinned model + provider, pinned temperature, and a reference annotation frozen in git *before* the
   run that grades against it. The current uncontrolled temperature on the cloud adapters (defect D6)
   is a reproducibility defect first and a quality defect second. Disclosure of AI assistance in the
   research workflow is expected by most institutions and journals — worth recording which parts of
   the published Computgraph carry `source: recognized`, which Phase 36 CGPD-03 already does.
2. **Third-party design IP / confidentiality (latent, activates on first non-own canvas).** A
   recognition prompt contains the architect's full canvas topology and component nicknames. Today
   the canvases are the researcher's own, so this is a non-issue; the moment a collaborator's or
   client's definition is pulled, sending it to a hosted LLM API becomes a disclosure decision. This
   is why §4b's rule *"never log the prompt body verbatim in production"* is a domain requirement and
   not just hygiene, and why the Ollama local-provider path retains value beyond cost.
3. **Downstream regulatory compliance checking (indirect).** The system's ultimate output feeds
   checking of architectural designs against building regulations (height limits and similar). Two
   honest qualifications: recognition errors do not directly produce wrong compliance verdicts —
   verdicts are computed by SWRL rules over Metagraph/ValidGraph design states, while the Computgraph
   is the design-side structural model — and in any professional use the verdict would be advisory,
   with a licensed architect retaining responsibility. The real exposure is **provenance and
   traceability**: a misattributed Parameter degrades the audit chain the research claims to provide.
4. **Ontology conformance as the de-facto internal standard.** The nearest thing to a "regulation"
   this phase must satisfy is `ontology/dg-shapes.ttl` / the SHACL publish gate and
   `spec/RULE-PARTITION-POLICY.md`. FM-6 above is exactly a compliance failure against that internal
   standard, discovered late.

### Domain Expert Roles for Evaluation

**The n=1 problem, stated plainly.** The same person authored the ontology, derived the annotation
convention from it, produced the reference annotation, wrote the prompt, and judges the output. There
is no second annotator, so classical inter-annotator agreement is unavailable and every quality
number is, by default, self-graded. This must be designed around rather than apologised for.

| Role | Responsibility in Eval |
|------|----------------------|
| **Architect-researcher (primary, and the only true domain expert)** | Authors the frozen reference annotation for each eval canvas; authors and owns the Dimension 1-5 rubric; adjudicates disagreements between arms; reviews every `unrecognized[]` entry for whether abstention was correct. |
| **Architect-researcher, inter-temporally (test–retest)** | Re-annotates one held-out canvas from scratch ≥ 4 weeks later without consulting the earlier annotation. Yields a **self-agreement ceiling** — the system cannot honestly be reported as scoring above the architect's own reproducibility on the same task. This is the single cheapest mitigation available and it costs one afternoon. |
| **A second computational designer (external, occasional — a peer or supervisor's student)** | One calibration session on a 10-20 block subset. Even a single session converts "the author says these boundaries are right" into a measured agreement floor, and will surface where the convention is ambiguous rather than where the model is wrong. Prioritise Dimension 2 (boundaries) and Dimension 3 (`Var` vs `Const`), the two most intent-laden. |
| **PhD supervisor / thesis committee** | Face validity of the rubric and of the SC1 claim; academic-integrity review of the frozen-reference protocol. Not per-example labelling. |
| **The accept / reject / partial-accept log (behavioural, not a person)** | The least-biased ground truth available, because it is a record of what the architect *did* under normal working conditions rather than what they assert when grading. Partial accepts are the highest-signal record of all — the boundary the architect redrew *is* the correction. Section 4's Tier-2 JSONL capture is therefore an evaluation instrument, not only a future training instrument. |

**Concrete bias mitigations to hold the eval to (all cheap, all mechanical):**

- **Freeze the reference before the run.** Reference annotations live in
  `fixtures/recognition_eval/*.expected.json` and are committed in a *separate* commit from any prompt
  or Tier-0 change. If the reference file and the prompt change in the same commit, the run is void.
- **Exploit the accidental pre-registration.** The Frame reference annotation already exists as
  worked-example individuals inside `DesignGrammar-V7.owl` (`Proc_11`, `Pat_11_DivideLine`,
  `Var_11_SpansCount`, `Const_11_ptZero`, `Emg_11_LineSDL`, `IntF_11_ParSplitAt`), authored *before*
  the recognition pipeline existed. It is the strongest anti-bias asset the project has. The honest
  caveat: the annotation convention was itself *derived from* that same example, so reference and
  target vocabulary share an origin — it protects against post-hoc reference tuning, not against
  a convention shaped to fit one canvas. A second, differently-authored canvas (UrbanBlock) is
  required before SC1 can be claimed to generalise.
- **Score by code, adjudicate by eye.** Member-set agreement, kind agreement and `NN` attribution are
  computed by the harness. The human only looks at disagreements — and looks at them **blind to which
  arm produced them** (shuffle and strip provider/model labels before review).
- **Report self-agreement alongside system agreement.** One number without the other is not
  interpretable at n=1.
- **Prefer behavioural over self-reported evidence** wherever both exist: an accept-rate curve against
  asserted `confidence`, drawn from the flywheel log, is worth more than any post-hoc quality rating.

## 2. Framework Decision

**Selected Framework:** **No LLM orchestration framework.** Pydantic v2 output schemas +
provider-native structured outputs layered onto the existing `data-service/llm_gateway.py` adapter
strategy, plus a **deterministic topology pre-classifier** in front of the LLM call. Eval harness =
**pytest** extending `data-service/tests/`.

**Version:** Pydantic v2 (already a transitive FastAPI dependency — no new package); `httpx`
(already present); pytest (already present). Net new runtime dependencies: **zero**.

**Rationale:**

The architecture decision (user-confirmed at the framework gate) is **Hybrid + labeling flywheel**:

| Tier | Owner | Scope |
|---|---|---|
| **0** | Deterministic Python, no LLM | Topology features → `Var` / `Const` / `Emg` / most `IntF`. In-degree 0 + widget kind ⇒ Variable/Constant; out-degree 0 ⇒ Emergent; pure pass-through ⇒ Interface. |
| **1** | LLM, tightened prompt | Only the semantically loaded residue: `Procedure` / `Pattern` grouping, and adjudication of Tier-0 low-confidence cases. |
| **2** | Flywheel (accrues passively) | RCGN-03's accept/reject decisions captured as labelled examples → dynamic few-shot retrieval. **No model training in this phase.** |

Three reasons this shape, and not a framework:

1. **The failure is not an orchestration failure.** It is a demonstration-design failure plus a
   missing task statement. LangChain/LlamaIndex/DSPy would each add a dependency and an idiom
   without touching the actual defect. The fix is a better fixture, a system prompt, and moving
   topologically-determined roles out of the LLM's hands entirely.

2. **Codebase discipline.** `cg_recognition.py`'s module docstring is explicit that it "mirrors
   `dg_context.py`'s `generate_validated_cypher()`/`validate_cypher()` structure verbatim — this is
   NOT a new idiom." The bounded-retry + violation-list contract already works and is proven by the
   UAT (`valid:true, attempts:1`). Introducing a framework would fork the service into two
   competing LLM idioms for no functional gain.

3. **SOTA guidance for this data scale.** Perplexity research (weak-supervision / programmatic-
   labelling literature; GNN node-classification surveys) is unambiguous: with tens-to-low-hundreds
   of labelled nodes, encode graph invariants deterministically and reserve the learned component
   for what topology genuinely cannot decide. Quoting the research: *"That makes a deterministic
   feature layer the right first move, because it encodes domain invariants that an LLM should not
   have to relearn from a handful of annotated canvases."*

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| **Frontier model swap only** (Claude/GPT on the existing prompt) | The default reflex, and insufficient. The few-shot actively demonstrates the failure mode; a strong model may *partially* override a bad demonstration but is still pulling against it. Costs API budget to rediscover a defect already provable by inspection. Keep as a *comparison arm in the eval*, not as the fix. |
| **DSPy** | Genuinely tempting — programmatic prompt optimisation is the right long-term home for the labeling flywheel. Ruled out **for now**: it needs the labelled corpus that Tier 2 has not yet accumulated, and it would own prompt construction, displacing the deterministic `_build_recognition_prompt` contract mid-remediation. Revisit once the flywheel has produced a few hundred labelled decisions. |
| **Instructor / PydanticAI** | Would give typed outputs + retries — but the retry loop and violation-list contract already exist and are UAT-proven. Provider-native structured outputs (Anthropic strict tool use, OpenAI `json_schema` strict) deliver the schema guarantee directly at the adapter layer, which is where this codebase already abstracts providers. |
| **LangChain / LlamaIndex** | Heavy orchestration for a single-call classification task with no retrieval, no agent loop, and no chain. Pure overhead. |
| **GNN (node classification)** | Not sample-efficient at this scale — surveys flag overfitting on small graphs as the core issue, and only one reference annotation exists today. The engineered topology features of Tier 0 capture the same signal without a training corpus. Reconsider only after many canvases accumulate. |
| **LoRA / SetFit sub-model now** | User's explicit question, and the research answer is *premature*: expect embeddings+classical to beat LoRA "until you have a few hundred to low thousands of clean labels per class." Today there is **one** reference annotation and **no Frame `.gh` on disk**. Tier 2's flywheel is the precondition — this spec builds the instrument that would make a sub-model justifiable later, without pretending the data exists now. |
| **promptfoo / Arize Phoenix** (eval) | promptfoo adds a Node toolchain to a Python service; Phoenix adds a docker-compose service and is aimed at production tracing rather than the offline scoring SC1 needs. pytest reuses the existing `data-service/tests/` suite and `test_cg_recognition.py`. Phoenix stays the candidate for *production* tracing (Section 7). |

**Vendor Lock-In Accepted:** **No.** The provider-agnostic gateway is a deliberate v9.0 Phase 28
invariant and must survive. Structured-output support differs sharply by provider — OpenAI
`json_schema` strict and Anthropic strict tool use *guarantee* schema conformance; DeepSeek JSON
mode guarantees only parseability — so structured output must be a **capability negotiated per
adapter with graceful degradation**, never an assumption. The existing prose-instruction +
`_extract_json` + validator + bounded-retry path remains the floor for providers lacking native
support (notably Ollama and DeepSeek).

**Deliberate non-goal:** this phase does **not** train a model. It builds the deterministic layer,
fixes the prompt, and stands up the eval + labelling instrument that a future training decision
would require evidence from.

### Entry Point Pattern

The two-tier call shape. Deliberately recognisable as the same loop as
`dg_context.generate_validated_cypher()` (`dg_context.py:880-922`) — provider resolved **once**
before the loop, `adapter.generate()` called **in-process** each attempt, never a re-POST to
`/llm/generate`, corrective feedback appended to the **original** prompt.

```python
# data-service/cg_recognition.py -- revised recognize_structure()

def recognize_structure(
    cg_context: dict, procedure_index: int | None = None, max_retries: int = 2
) -> dict:
    # ── Tier 0: deterministic. No LLM, no network, no cost, no nondeterminism. ──
    scope = cg_topology.scope_untagged(cg_context, procedure_index)
    if scope.empty_procedure:                    # UAT F2 fix: NEVER silently widen scope
        return {"valid": False, "attempts": 0, "violations": [{
            "code": "empty_procedure_scope",
            "message": (
                f"procedure_index {procedure_index} resolves to a tagged procedure with "
                f"no members, so per-procedure scoping is impossible. Where: request."
                f"procedure_index. How to fix: tag that procedure's members first, or "
                f"omit procedure_index to run whole-canvas."),
            "path": "procedure_index"}]}

    features = cg_topology.extract_features(cg_context, scope.node_ids)
    tier0 = cg_topology.classify(features)       # -> .decided: list[Proposal], .residual: list[str]

    if not tier0.residual:                       # topology settled everything -- skip the LLM
        return {"valid": True, "attempts": 0, "tier": "0",
                "proposal": cg_schemas.ProposedStructure(
                    proposals=tier0.decided, unrecognized=[]
                ).model_dump(mode="json")}

    # ── Tier 1: LLM over the semantic residue ONLY. ────────────────────────────
    system_prompt = build_recognition_system_prompt()          # NEW -- req.system was never set
    base_prompt = _build_recognition_prompt(cg_context, scope, features, tier0)

    master_secret = os.getenv("LLM_MASTER_SECRET", "")
    settings = load_persisted_llm_settings()
    provider, model, api_key = resolve_active_provider(settings, master_secret)
    adapter = get_adapter(provider, settings.get("baseUrl"))    # unchanged gateway idiom
    caps = negotiate_structured_output(provider, model, settings.get("baseUrl"))  # NEW

    options = GenerationOptions(                               # NEW -- see Pitfall 3
        temperature=0.0,                                       # classification task: pin it
        max_tokens=cg_topology.output_token_budget(tier0.residual),   # sized, not hardcoded 4096
        output_schema=caps.schema_for(cg_schemas.ProposedStructure),  # None when unsupported
    )

    current_prompt, violations = base_prompt, []
    for attempt in range(max_retries + 1):
        req = GenerateRequest(prompt=current_prompt, system=system_prompt,
                              model=model, provider=provider)
        response = adapter.generate(req, api_key, options=options)

        if response.truncated:      # stop_reason == "max_tokens" / finish_reason == "length"
            return {"valid": False, "attempts": attempt + 1, "violations": [{
                "code": "output_truncated",
                "message": (
                    f"The model hit its {options.max_tokens}-token output cap mid-JSON on "
                    f"{len(tier0.residual)} candidates. Where: LLM output. How to fix: "
                    f"re-run with procedure_index set, one procedure at a time."),
                "path": None}]}     # do NOT retry: identical scope truncates identically (F1)

        parsed, parse_error = _extract_json(response.text)     # still the floor for DeepSeek/Ollama
        if parse_error:
            violations = [{"code": "bad_json", "message": parse_error, "path": None}]
            current_prompt = append_recognition_feedback(base_prompt, violations)
            continue

        # Re-join Tier-0 rows BEFORE validation, so duplicate_member also catches a Tier-1
        # proposal that tries to claim a node Tier 0 already decided.
        merged = cg_topology.merge(tier0.decided, parsed)
        result = validate_proposed_structure(merged, cg_context)   # UNCHANGED safety contract
        if result["valid"]:
            return {"valid": True, "proposal": merged,
                    "attempts": attempt + 1, "tier": "0+1"}
        violations = result["violations"]
        current_prompt = append_recognition_feedback(base_prompt, violations)

    return {"valid": False, "violations": violations, "attempts": max_retries + 1}
```

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| **Topology feature extractor** — `cg_topology.extract_features()` | Per-node record derived purely from `cgContextJson v1`: `in_degree`, `out_degree`, `widget_kind`, `component_guid`, `nickname`, `group_id`, `adjacent_tagged_procedures`. Computed from `wires[]` + `nodes[]`; no LLM. | Once per recognition call, before any prompt is built. Its output feeds **both** Tier 0 and the Tier-1 prompt (the LLM stops having to infer degree from a flat wire list — defect D5). |
| **Tier-0 rule classifier** — `cg_topology.classify()` | Pure-Python decision table over those features producing `(decided, residual)`. Emits `confidence=1.0` and a *mechanical* rationale ("in-degree 0, out-degree 3, widget=NumberSlider"). | Always, before the LLM. Anything it cannot decide with certainty goes to `residual` — **abstaining is free, guessing is not**. |
| **Scoped prompt builder** — `build_recognition_system_prompt()` + `_build_recognition_prompt()` | Split of the existing single-blob prompt into a **system** half (role, task statement, grammar-as-target + grammar-anti-filter, output contract) and a **user** half (catalog, counterexample few-shot, tagged anchors, residual-only node/feature lines). | **Structured-output capability negotiation** — `negotiate_structured_output(provider, model, base_url)` | Returns a small capability object: `mode ∈ {"json_schema_strict", "tool_strict", "json_object", "none"}` plus `schema_for(Model)` which returns a provider-shaped schema dict or `None`. Guarantees the prose + `_extract_json` + validator path stays the floor for DeepSeek and older Ollama models. |
| **Violation-list contract** — `validate_proposed_structure()` (`cg_recognition.py:95-360`, unchanged) | `{"valid": bool, "violations": [{"code","message","path"}]}`. This survives the refactor untouched; the Pydantic layer sits *in front* of it, never instead of it. |

### Common Pitfalls

1. **The few-shot teaches the failure (the actual root cause).**
   `data-service/fixtures/frame_recognition_fewshot.json:6-9` feeds the model input group nicknames
   that *already* conform (`11_IntF_ParSplitAt`), and every `expected.proposals[].rationale`
   (lines 27, 35) justifies the proposal with *"matches the Interface naming grammar
   `<NN>_IntF_<Name>`"*. The single demonstration in the prompt therefore teaches: *propose only
   when the surface name already matches the grammar.* On a genuinely untagged canvas nothing
   matches, so faithful imitation yields zero proposals with "does not match grammar" rationales —
   exactly UAT F3. **DeepSeek did not fail; it executed the demonstration.** Fixing the fixture is
   strictly cheaper and strictly more effective than buying a better model. See 4b.3 for the
   replacement's required shape.

2. **`req.system` exists on all three adapters and is never set.**
   `GenerateRequest.system` is declared at `llm_gateway.py:40` and honoured by
   `AnthropicAdapter` (`:174-175`, top-level `system` field), `OpenAIAdapter` (`:228-229`, prepended
   `role: "system"` message) and `OllamaAdapter` (`:287-288`, top-level `system`). Yet
   `recognize_structure()` constructs `GenerateRequest(prompt=…, model=…, provider=…)` at
   **`cg_recognition.py:653`** with no `system=`. The assembled prompt has no role, no task
   statement, and no statement that the grammar is an *output* target — the model must infer the
   task from data layout, and (per pitfall 1) infers the wrong one.

3. **`max_tokens: 4096` is hardcoded in every adapter** —
   `llm_gateway.py:171` (Anthropic), `:232` (OpenAI), `:284` (Ollama `num_predict`). This is the
   direct cause of UAT **F1**: a 214-node whole-canvas proposal set exceeds 4096 output tokens,
   the JSON terminates mid-object, `_extract_json` returns `bad_json`, and all three attempts burn
   on the same truncation. Two sub-traps when fixing it:
   - **Do not add `max_tokens`/`temperature`/`output_schema` to `GenerateRequest`.**
     `GenerateRequest` is the FastAPI request body for the public `POST /llm/generate`
     (`app.py`), so any field added there becomes attacker-controllable — `max_tokens: 1000000` is
     a cost-DoS and a raw `output_schema` dict is an unvalidated pass-through to the provider.
     Put them in a separate internal-only `GenerationOptions` model passed as a keyword to
     `adapter.generate(req, api_key, options=…)`.
   - **OpenAI: `max_tokens` is deprecated in favour of `max_completion_tokens`** and is *rejected*
     by o-series and GPT-5.x models. The current `OpenAIAdapter` body (`:232`) will 400 against
     those. Anthropic's Messages API still requires `max_tokens`; Ollama uses `options.num_predict`.
     Three different spellings — the adapter is the right place to hide that.

4. **DeepSeek JSON mode guarantees *parseability*, not *schema conformance*.**
   DeepSeek is reached through `OpenAIAdapter` via `baseUrl` (`llm_gateway.py:337`), so it *looks*
   like OpenAI but supports only `response_format: {"type": "json_object"}` — no `json_schema`, no
   `strict`. Its docs additionally require the literal word "json" in the prompt, recommend showing
   a format example, and warn the API "may occasionally return empty content" — which is very
   likely UAT F3's `deepseek-v4-pro` empty-text-×3 on the large prompt. Never branch on
   `provider == "openai"` to decide strictness; branch on the negotiated capability. Treat any
   `json_object`-only provider as "prose path with a nudge" and keep the validator in the loop.

5. **The silent scope-widening fallback.**
   `_filtered_untagged_node_ids` (`cg_recognition.py:466-489`) returns **all** untagged node ids
   when `_procedure_member_ids(procedure_index)` is empty. The caller believes it scoped to 14
   nodes and actually sent 214 (UAT **F2**), which then triggers pitfall 3 / F1. An empty
   procedure is a *user-actionable condition*, not a default. Return a distinct signal (the
   `empty_procedure_scope` violation in the entry-point pattern above, or a 422 at the endpoint) —
   never widen silently.

6. **Re-POSTing to `/llm/generate` on retry is an explicit anti-pattern in this module.**
   Called out in both module docstrings (`cg_recognition.py:5-7`, `dg_context.py:887-891`): resolve
   the provider **once** before the loop, then call `adapter.generate()` in-process. A retry that
   goes back out over HTTP re-reads settings, re-decrypts the key, and re-resolves the provider —
   so a settings change mid-retry silently switches models between attempts, destroying eval
   reproducibility. Any new structured-output plumbing must stay inside the adapter, not become a
   second endpoint.

7. **`componentGuid` is present in the context and dropped on the way to the prompt.**
   `_trimmed_node_lines` (`cg_recognition.py:500-513`) emits only `name`, `nickname`, `position`.
   The serializer *does* carry `componentGuid`, `slider {min,max,step}` and `isIntegerSlider`
   (`DG/src/DG.Core/Models/Computgraph/CgNode.cs:9-23`,
   `ComputgraphContextSerializer.cs:209-221`). `componentGuid` is stable per Grasshopper component
   *type* and is the single most reliable widget-kind signal available — dropping it forces the
   model to guess widget kind from a display name. Tier 0 must read it; the Tier-1 prompt should
   show a derived `widget=` token rather than the raw GUID (cheaper, and more legible).

### Core Pattern — the two-tier hybrid

**Tier 0 runs first, on features computed from `cgContextJson v1` alone.** The exact fields
available (verified against `DG/src/DG.Core/Models/Computgraph/CgNode.cs:9-23` and
`ComputgraphContextSerializer.cs:209-250`, and the shapes in `tests/test_cg_recognition.py:31-76`):

| Source | Fields |
|---|---|
| `nodes[]` | `instanceId`, `componentGuid`, `name`, `nickname`, `position[2]`, `slider {min,max,step}` *(present only on number sliders)*, `isIntegerSlider` |
| `wires[]` | `fromNode`, `fromParam`, `toNode`, `toParam` |
| `untagged` | `nodeIds[]`, `groups[{nickname, memberIds}]` — note: **no `nestedGroupIds`** on untagged groups (the raw canvas has it; the serialized untagged DTO does not, `ComputgraphContextSerializer.cs:243-250`) |
| `algorithms[].procedures[]` | `id`, `index`, `name`, `source`, `memberIds[]`, and nested `patterns[]` / `parameters[]` / `interfaces[]` each with `id`, `label`/`name`, `memberIds[]`, `source` |

Derived features: `in_degree` / `out_degree` (count `wires` where the node is `toNode` / `fromNode`),
`widget_kind`, `group_id` (from `untagged.groups`), `adjacent_tagged_procedures` (one-hop wire
neighbours that are tagged procedure members — the same signal
`_filtered_untagged_node_ids` already computes at `cg_recognition.py:481-489`).

**`widget_kind` must mirror C# `ClassifyNodeKind` exactly** (`CanvasAnnotationParser.cs:490-515`):
`slider is not null` ⇒ Slider; else `name` contains "Value List" ⇒ ValueList; "Panel" ⇒ Panel;
"Toggle" ⇒ Boolean; else None. Mirroring is load-bearing, not cosmetic: if Python proposes a
`Const` on a component C# classifies as `None`, accept-time `InferParameterDataType` returns a null
`dataType` with no warning and Phase 36's publish 422s the whole payload — that is exactly UAT
**F5**. Where Python and C# disagree, Tier 0 should **abstain**, not propose.

**Tier-0 rule table.** Each rule states its own uncertainty honestly; anything not `high` goes to
`residual` for the LLM.

| # | Signal | Verdict | Confidence | Honest caveat / when it must defer |
|---|---|---|---|---|
| R1 | `in_degree == 0` **and** `widget_kind ∈ {Slider, ValueList, Boolean}` | `Var` (VariableParam) | high | Solid: an interactive widget with no upstream *is* an architect-driven input. Only failure mode is a widget the architect intends as a fixed constant — cheap to reject in preview. |
| R2 | `in_degree == 0` **and** `out_degree > 0` **and** `widget_kind ∈ {Panel, None}` | `Const` (ConstantParam) | medium | Frame's constants are Panels *and* ordinary components (`Construct Point`, `Unit Y` — `frame-cg-context.json:71-72`), so `widget_kind == None` must not disqualify. But a source-only *geometry* component may be the head of a Pattern, not a Constant. **Defer when the node shares an untagged group with ≥1 other node** — that is Pattern evidence. |
| R3 | `out_degree == 0` **and** `in_degree > 0` | `Emg` (EmergentParam) | medium-high | The clean sink rule. Caveat: a genuine terminal *geometry* node (Frame's `11_Emg_LineSDL`, a Line SDL) and a terminal *reporting* Panel are both `Emg` here, which is correct — but a sink that is the last node of a multi-node Pattern belongs to the Pattern. Same group-membership deferral as R2. |
| R4 | `in_degree == 1` **and** `out_degree == 1` **and** `widget_kind == None` **and** `name` starts with `Param` (a GH bare parameter) | `IntF` (Interface) | high | This is the Frame Interface signature exactly (`n-parsplit`, `n-trussconfig-intf`: `name: "Param"`, single in, single out). Restricting to bare `Param` components keeps it tight; a general "pass-through" rule would swallow ordinary single-in/single-out compute nodes, which are Pattern members. |
| R5 | `in_degree == 0` **and** `out_degree == 0` (fully isolated) | **abstain** | — | Cannot distinguish `Const` from `Emg` from scratch-note-to-ignore. Send to Tier 1 with the group nickname and widget kind, and accept `unrecognized` as a good answer. |
| R6 | anything remaining | **abstain** → `residual` | — | Procedure / Pattern grouping and all multi-node structure. This is the LLM's actual job. |

> **Hard, uncomfortable caveat about the reference fixture.**
> `DG/tests/DG.Tests/Fixtures/frame-cg-context.json` contains **34 nodes and exactly one wire**
> (line 97). It is a *serialization* fixture, not a *topology* fixture. On it, every Tier-0 degree
> rule collapses into R5 (abstain) and Tier 0 would decide almost nothing. Any eval built on that
> file as-is will measure the LLM alone and score Tier 0 as useless. **The eval fixture must be
> extended with the Frame's real wiring** (or built from a live UrbanBlock pull, which does have
> wires) before Tier 0 can be graded. Section 5 owns this; flagging it here because it changes what
> "implement Tier 0" means for the plan — write the rules, but expect the first honest measurement
> to come from a re-wired fixture.

**Tier 1 then sees a much smaller, much richer prompt:** only `residual` nodes, each rendered with
its derived features rather than raw geometry —

```
=== CANDIDATES (residual after deterministic pre-classification) ===
- n-topchord   widget=none  in=1 out=0  group="loose group A"  adj_proc=[11]  name="Line SDL"  nick="TopChord"
- n-divpoints  widget=panel in=0 out=0  group=none             adj_proc=[]    name="Panel"     nick="DivPoints"

=== ALREADY DECIDED BY TOPOLOGY (do not re-propose these ids) ===
- n-spanscount -> Var  (in=0, widget=slider)
- n-parsplit   -> IntF (in=1, out=1, bare Param)
```

Listing the Tier-0 decisions explicitly does two things: it stops the LLM double-claiming a node
(which `duplicate_member` would reject anyway, wasting a retry), and it acts as an *in-context
worked example generated from the user's own canvas* — the strongest few-shot available, and free.

### Tool Use — provider structured-output negotiation

Capability detection, never assumption. `negotiate_structured_output()` returns a mode; the adapter
translates it. Verified syntax as of 2026-07-26:

**Anthropic — `output_config.format`, GA, no beta header.** `AnthropicAdapter.generate`
(`llm_gateway.py:169-176`) adds:

```python
body = {
    "model": req.model,
    "max_tokens": options.max_tokens,
    "temperature": options.temperature,
    "messages": [{"role": "user", "content": req.prompt}],
}
if req.system:
    body["system"] = req.system            # already implemented at :174-175 -- just start USING it
if options.output_schema:
    body["output_config"] = {"format": {"type": "json_schema",
                                        "schema": options.output_schema}}
```

The response still arrives as JSON text in `content[0].text`, so the existing extraction at
`llm_gateway.py:182-185` needs no change. (The older top-level `output_format` parameter and the
`structured-outputs-2025-11-13` beta header still work during a transition period — prefer
`output_config.format`.) Strict tool use (`"strict": true` on a tool's `input_schema`) is the
alternative shape; it is **not** needed here because there is exactly one output and no tools —
using `output_config.format` avoids inventing a fake tool.

**OpenAI — `response_format.json_schema` with `strict: true`.**

```python
body = {"model": req.model, "messages": messages,
        "max_completion_tokens": options.max_tokens,      # NOT max_tokens (deprecated)
        "temperature": options.temperature}
if options.output_schema:
    body["response_format"] = {"type": "json_schema",
                               "json_schema": {"name": "proposed_structure",
                                               "strict": True,
                                               "schema": options.output_schema}}
```

Then check `choices[0].finish_reason == "length"` → set `GenerateResponse.truncated`, and
`choices[0].message.refusal` → surface as a distinct violation rather than `bad_json`.

**DeepSeek (OpenAI-compatible via `baseUrl`) and Ollama — degrade gracefully.**
DeepSeek: `response_format: {"type": "json_object"}` only, plus the literal word "json" somewhere in
the prompt (its docs require it) and a format example. That buys parseability, nothing more —
`_extract_json` + `validate_proposed_structure` + bounded retry remain the enforcement.
Ollama: `/api/generate` accepts a top-level `format: <json schema>` object, so newer local models
*can* be schema-constrained; negotiate it from the Ollama version rather than assuming, and fall
back to `format: "json"` or plain prose.

**Detection heuristic (recommended, and deliberately conservative):**

| Condition | Mode |
|---|---|
| `provider == "anthropic"` and model id starts with a 4.5-or-later family | `json_schema_strict` via `output_config.format` |
| `provider == "openai"` and `baseUrl` is unset or `api.openai.com` | `json_schema_strict` via `response_format` |
| `provider == "openai"` and `baseUrl` points anywhere else (DeepSeek, Groq, Together, Azure) | `json_object` |
| `provider == "ollama"` and `/api/version` ≥ the structured-output release | `json_schema_strict` via `format` |
| anything else / unknown | `none` |

Unknown must fall to `none`, not to strict: a provider that rejects an unknown body key returns 400
and the whole recognition fails, whereas the prose path merely performs worse. **Log the negotiated
mode on every call** — without it, an eval result is uninterpretable.

### State Management — the Tier-2 labelling flywheel (design-level only)

**This phase trains nothing.** It builds the instrument.

Every architect decision in `DG STRUCTURE CONFIRM` is already a labelled example with provenance:
accept ⇒ "this member set and kind were correct"; reject ⇒ "wrong"; partial accept ⇒ the most
informative label of all, because the boundary the architect redrew *is* the correction. UAT test 4
passes, so the instrument works today; nothing captures its output.

- **Where the label already half-exists:** Phase 36 **CGPD-03** persists `source: recognized` plus
  provider/model on published entities, and the canvas carries the `dg.recognized.<guid>` ValueTable
  marker that survives save + reopen (UAT test 4). So *accepted* proposals are already durable and
  attributable. **Rejections are the missing half — and rejections are the higher-signal class.**
- **Minimal capture (recommended for this phase):** append one JSONL record per confirm decision to
  `data-service/data/recognition_labels.jsonl`: `{ts, project, definitionId, procedureIndex,
  proposalId, decision ∈ {accept, reject, partial}, proposedKind, proposedMemberIds,
  finalKind, finalMemberIds, confidence, tier, provider, model, promptVersion}`. Local file, same
  `DATA_DIR` convention as `llm-settings.json` (`llm_gateway.py:410-411`). No schema migration, no
  Neo4j write — recognition still never persists to the graph (RCGN-04 intact).
- **What it unlocks, in order:** (1) *calibration* — plot accept-rate against asserted `confidence`
  to find out whether 0.9 means anything (today it does not: the synthetic UAT payload used a flat
  0.9 and nothing objected); (2) *dynamic few-shot retrieval* — pick the k nearest accepted
  examples from the same project instead of one hardcoded fixture; (3) *only if the data ever
  justifies it*, a trained sub-model. Research is explicit that (3) is premature below a few
  hundred clean labels per class, and today there is one reference annotation.
- **In-request state stays as-is.** `recognize_structure()` is stateless per call; the retry loop
  keeps its state in `current_prompt`. Do not introduce a session or conversation object — there is
  no multi-turn interaction here.

### Context Window Strategy

The prompt has three parts with very different growth behaviour. Budget them separately.

| Part | Size | Growth | Strategy |
|---|---|---|---|
| Concept catalog + annotation convention (`cg_recognition.py:572-577`) | ~2-4 k tokens, constant | none | Constant across every call → make it the **cache prefix** (see 4b.5). Also: it is currently dumped as three raw `json.dumps` blobs; a rendered, deduplicated form would cut it materially. Measure before optimising. |
| Few-shot fixture (`:579-580`) | ~400 tokens | none | Replace, do not enlarge (4b.3). |
| Tagged anchors + candidate nodes + wires (`:582-591`) | **unbounded** | linear in canvas size | This is the part that blew the budget in F1. Three controls, applied in order. |

1. **Tier 0 removes candidates for free.** On a canvas with real wiring, R1-R4 should absorb most
   parameter-role nodes — precisely the numerous, boring ones. The LLM sees the Procedure/Pattern
   residue. This is the primary defence against F1, and it costs no tokens because it happens before
   the prompt exists.
2. **Chunk by procedure.** `procedure_index` scoping already exists and works (UAT: `valid:true,
   attempts:1` when correctly scoped); it just fails open (pitfall 5). Once F2 is fixed, make
   per-procedure the *automatic* path above a node-count threshold — iterate procedures, merge the
   proposal lists, validate once at the end against the full context so `duplicate_member` and
   `tagged_overlap` still see everything. Whole-canvas stays available for small definitions.
3. **Trim the anchor block.** `_tagged_anchor_lines` (`:528-548`) prints every tagged entity's full
   `memberIds` list. On a mostly-tagged canvas that is the single largest section and most of it is
   irrelevant to the current procedure. When scoped, emit full detail for the target procedure and
   a one-line summary (`name`, `index`, member *count*) for the others.

Output-side: `output_token_budget()` sizes `max_tokens` to the residual, and the truncation guard
returns the scoping hint on the *first* truncation instead of burning three attempts (F1's actual
complaint was not the cap but the absent, unreachable advice).

### Structured Outputs with Pydantic

**The contract, in one sentence:** Pydantic guarantees the *shape*; `validate_proposed_structure()`
guarantees the *safety*. They are complementary layers and neither replaces the other.

```python
# data-service/cg_schemas.py  (NEW)
"""Pydantic v2 output contract for cg_recognition's proposed-structure object.

Shape only. The RELATIONAL rules -- a member id must exist in the submitted
context, must not already belong to a tagged entity, must not be claimed twice --
are not expressible in JSON Schema and stay in validate_proposed_structure().
"""
from __future__ import annotations

from typing import Annotated, Literal

from pydantic import BaseModel, ConfigDict, Field

# Both spellings, because ProposalDto.ToEntityTagKind() accepts both
# (PreviewRegistry.cs:110-123) and the catalog teaches the long ones.
ProposalKind = Literal[
    "Proc", "Procedure",
    "Pat", "Pattern",
    "Var", "VariableParam",
    "Const", "ConstantParam",
    "Emg", "EmergentParam",
    "IntF", "Interface",
]


class StructureProposal(BaseModel):
    model_config = ConfigDict(extra="forbid")  # -> additionalProperties: false

    kind: ProposalKind
    suggestedName: str = Field(
        description=(
            "The name to CREATE for this entity, written in the DG annotation "
            "convention, e.g. '11_IntF_ParSplitAt'. This is generated by you; it "
            "is NOT expected to match the node's existing nickname."
        )
    )
    procedureIndex: int = Field(
        description="Owning procedure index, e.g. 11 = algorithm 1, procedure 1."
    )
    memberIds: list[str] = Field(
        description="instanceId values copied verbatim from the submitted context."
    )
    confidence: Annotated[float, Field(ge=0.0, le=1.0)] = Field(
        description=(
            "0.0-1.0. Renders on canvas as a percentage and is the architect's "
            "triage signal. A confidently wrong proposal costs more than an "
            "honest 'unrecognized' entry -- prefer abstaining."
        )
    )
    rationale: str = Field(
        description=(
            "<= 30 words. Cite GRAPH EVIDENCE (degree, wiring, group membership, "
            "adjacent tagged procedure). Do NOT cite the naming grammar."
        )
    )


class UnrecognizedBlock(BaseModel):
    model_config = ConfigDict(extra="forbid")

    memberIds: list[str]
    reason: str


class ProposedStructure(BaseModel):
    model_config = ConfigDict(extra="forbid")

    proposals: list[StructureProposal]
    unrecognized: list[UnrecognizedBlock] = []
```

**Emitting a provider-acceptable JSON Schema.** `ProposedStructure.model_json_schema()` is *not*
directly usable by OpenAI strict or Anthropic. Both accept only a subset, and Pydantic emits things
outside it. Write one adapter function and unit-test it:

```python
def to_strict_json_schema(model: type[BaseModel]) -> dict:
    """Pydantic v2 JSON Schema -> the OpenAI-strict / Anthropic-compatible subset."""
    schema = model.model_json_schema()
    # 1. Inline $defs -- Anthropic rejects external $ref and OpenAI's handling of
    #    nested $defs is version-sensitive. Safer to flatten for a schema this small.
    # 2. Every object needs "additionalProperties": false (Pydantic emits it only
    #    with extra="forbid" -- set above, but assert it recursively anyway).
    # 3. Every key in "properties" must appear in "required" under OpenAI strict.
    #    Optionality is expressed as a null union, NOT by omission. So
    #    `unrecognized` MUST be required here even though it defaults to [] in Python.
    # 4. STRIP unsupported keywords. Neither provider supports numeric
    #    minimum/maximum, and OpenAI also rejects minLength/maxLength/pattern/
    #    minItems/maxItems. Pydantic's ge=0.0/le=1.0 on `confidence` emits
    #    "minimum"/"maximum" -> remove them from the wire schema.
    #    The bound is NOT lost: Pydantic still enforces it on model_validate().
    # 5. Anthropic tolerates minItems only when 0 or 1 -- simplest is to strip it too.
    ...
    return schema
```

That step-4 asymmetry is the important one and is easy to get wrong: **the emitted schema is
deliberately weaker than the Pydantic model.** Constrained decoding gives you the structure;
Pydantic re-checks the value ranges after parsing; the existing validator then checks the relational
safety rules. Three checks, three different jobs.

**Where Pydantic slots into the existing flow** — it goes *between* `_extract_json` and
`validate_proposed_structure`, and translates its own errors into the same violation dicts so the
retry loop is untouched:

```python
try:
    typed = cg_schemas.ProposedStructure.model_validate(parsed)
except ValidationError as exc:
    violations = [
        {"code": "schema_violation",
         "message": (f"{err['msg']}. Where: {'.'.join(str(p) for p in err['loc'])}. "
                     f"How to fix: return the documented proposal shape."),
         "path": ".".join(str(p) for p in err["loc"])}
        for err in exc.errors()
    ]
    current_prompt = append_recognition_feedback(base_prompt, violations)
    continue

merged = cg_topology.merge(tier0.decided, typed.model_dump(mode="json"))
result = validate_proposed_structure(merged, cg_context)   # relational safety -- UNCHANGED
```

**Retry policy.** Keep the existing bound: `max_retries=2` ⇒ **3 attempts total** (matches
`generate_validated_cypher`, and the UAT-proven loop). Refinements:

| Failure | Retry? | Why |
|---|---|---|
| `bad_json` (`_extract_json` failed) | yes | Transient formatting slip; feedback usually fixes it. Should become *rare* once strict mode is negotiated — if it does not, the negotiation is lying and that is a bug worth logging loudly. |
| `schema_violation` (Pydantic) | yes | Same. |
| `tagged_overlap` / `duplicate_member` / `unknown_member_id` | yes | These are *content* errors and the corrective feedback names the offending ids, which is genuinely actionable. |
| `output_truncated` | **no** | Deterministic in the scope. Retrying the same scope truncates identically — three attempts, one useless answer, triple cost (UAT F1). Return the scoping hint immediately. |
| `too_many_proposals` / `too_many_members` | **no** | Same reasoning: a DoS bound, not a formatting slip. Surface the scoping advice. |
| Provider 4xx/5xx | no (existing behaviour) | `map_provider_error` (`llm_gateway.py:573-624`) already handles this; do not add a retry storm on 429. |

**What to log per attempt** (structured, one record): `attempt`, `provider`, `model`,
`negotiated_mode`, `prompt_version`, `temperature`, `max_tokens`, `usage.*` (already normalised on
`GenerateResponse`), `finish_reason`, `tier0_decided_count`, `tier1_residual_count`,
`violation_codes[]`, `latency_ms`. Never log the prompt body verbatim in production (it contains the
architect's canvas) and never the API key — `map_provider_error`'s existing discipline (LLMC-06)
applies. **Surface to the user** only the final result: a valid proposal, or the final violation
list. Intermediate attempts stay internal (D-06), same as `generate_validated_cypher`.

### Async-First Design

**Honest position: do not make this async. Not in this phase.**

The service is FastAPI, so `async` is available, but every adapter is deliberately synchronous —
`AnthropicAdapter.generate` uses `with httpx.Client(timeout=120.0)` (`llm_gateway.py:177`), and so do
the OpenAI (`:234`) and Ollama (`:289`) adapters. The endpoint handlers are plain `def`
(`app.py:1313 def post_computgraph_recognize`), which FastAPI runs in its threadpool — so a slow
120 s recognition call **does not** block the event loop today. The current design is not a bug.

Reasons to leave it alone:

- **There is no concurrency to exploit.** One architect, one canvas, one recognition call at a time.
  The retry loop is inherently sequential (attempt *n+1* needs attempt *n*'s violations).
- **The one place async would pay is per-procedure chunking** (fan out N procedures in parallel).
  That is a real future win, but it is a *scalability* change, not a *quality* change, and this
  phase is graded on SC1 quality. Note it and move on.
- **The mistake to avoid if someone does convert:** turning the handlers into `async def` while
  leaving `httpx.Client` (sync) inside them. That is strictly worse than today — FastAPI stops using
  the threadpool for `async def` handlers, so the blocking HTTP call now runs *on the event loop* and
  stalls every other request for up to 120 s. The related classic is calling `asyncio.run()` from
  inside a running loop (`RuntimeError: asyncio.run() cannot be called from a running event loop`).
  If you convert, convert the whole column: `async def` handler → `httpx.AsyncClient` →
  `await adapter.agenerate()`, all three or none.

**Stream vs. await:** **await.** Streaming is for perceived latency on prose a human reads as it
arrives. Here the output is a JSON object that must be parsed, schema-validated, safety-validated
and possibly retried before a single pixel can render on the Grasshopper canvas — a partial stream
is worthless, and under constrained decoding a partial object is not even valid JSON. Await the
whole response. If recognition latency becomes a UX complaint, the answer is Tier 0 (which returns
in milliseconds and could render its decided proposals immediately while Tier 1 runs), not token
streaming.

### Prompt Engineering Discipline

**This is the heart of the fix.** Everything else in this spec is hygiene; this section is where the
SC1 block actually gets unblocked.

**1. System vs. user separation.** The system prompt carries the invariants; the user prompt carries
the data. Today there is no system prompt at all (`cg_recognition.py:653` — pitfall 2), so the model
reverse-engineers the task from a data dump. Split:

*System* (constant, versioned as `prompts/recognition_system.md`, cacheable):
role · task statement · the grammar double-framing · abstention licence · rationale rules · output
contract.
*User* (per call): concept catalog · few-shot · tagged anchors · Tier-0 decisions · residual
candidates with features.

**2. The grammar stated twice, in two different roles.** This is the specific technique that
addresses the specific failure. State it as an output form **and** as an explicit negative:

```markdown
You are classifying untagged components on a Grasshopper canvas into Computgraph
entities. The architect has already tagged what they know; those tags are immutable
ground truth. Your job is to propose entities for what remains, so the architect can
accept them with one click instead of drawing them by hand.

### The naming convention is an OUTPUT TARGET
`<NN>_IntF_<Name>`, `<NN>_Var_<Name>`, `<NN>_Pat_<k>[ <name>]`, ... are the forms you
must WRITE INTO `suggestedName`. You GENERATE a conforming name; you do not look one up.

### The naming convention is NOT A FILTER   <-- state the negative explicitly
Untagged components never match the convention. That is the definition of untagged and
the reason they need classifying. Every candidate is eligible. NEVER reject a candidate,
and never write a rationale, on the grounds that its existing name "does not match the
grammar". A rationale mentioning the naming grammar as a reason to reject is a WRONG
answer even if the JSON is well-formed.

### Decide from graph evidence, not from names
Use: wiring direction and degree, group membership, widget kind, and which tagged
procedure a node is wired to. Nicknames are a weak hint about MEANING, never about KIND.

### Abstaining is a good answer
If the evidence does not support a classification, put the ids in `unrecognized` with a
short reason. A confidently wrong proposal costs the architect more time than an honest
abstention. Do not pad the list.
```

**3. Counterexample-shaped few-shot — the fixture replacement.** The current fixture is the root
cause (pitfall 1). Its replacement must invert every property that made it harmful:

| Property | Current fixture (harmful) | Required in the replacement |
|---|---|---|
| Input group nickname | `"11_IntF_ParSplitAt"` — already conforms | **Must not conform.** e.g. `"param stuff"`, or no group at all. |
| Observed node nickname | `"ParSplitAt"` — reads like the answer | Something plainly non-canonical: `"pt"`, `"num2"`, `"copy of thing"`. |
| Relationship of `suggestedName` to observed name | Identical modulo prefix — invisible that a name was *generated* | **Visibly different.** `nickname: "at"` → `suggestedName: "11_IntF_SplitParameter"`. The generation step must be legible in the example itself. |
| Rationale | *"matches the Interface naming grammar `<NN>_IntF_<Name>`"* | Graph evidence only: *"bare Param, one input from procedure 11's tagged Divide Curve, one output — a pass-through boundary."* The word "grammar" must not appear in any demonstrated rationale. |
| Coverage | 2 examples, both Interface, both accepted | ≥ 4: one `Var` (source slider), one `Emg` (sink), one multi-node `Pat`, and **one honest `unrecognized`** so abstention is demonstrated rather than merely permitted. |
| Ordering | n/a | Do not put all accepted examples first and the abstention last. |

Two literature grounds for taking demonstration design this seriously, both cited in the diagnosis
brief: **Zhao et al., "Calibrate Before Use: Improving Few-Shot Performance of Language Models"
(ICML 2021)** — few-shot predictions are biased by the *majority label* and by *recency*, so a
demonstration set where every example shares an incidental property (here: "input name already
conforms") transfers that property as the latent rule; and **Lu et al., "Fantastically Ordered
Prompts and Where to Find Them" (ACL 2022)** — permutation of the same examples swings accuracy from
near-SOTA to near-chance, with no ordering transferable across models. Practical consequences: keep
the demonstration count small and *deliberately heterogeneous*, fix the order in the fixture file so
it is reproducible, and make example order an explicit variable in the eval sweep rather than an
accident.

**4. Few-shot: inline now, retrieved later.** Inline (one bundled fixture) is correct for this
phase — there is one reference annotation and no corpus. The Tier-2 flywheel is what makes dynamic
retrieval possible: once `recognition_labels.jsonl` holds accepted decisions, select the k nearest
accepted examples *from the same project* by widget kind and degree signature. Do not build the
retrieval path now; do make the fixture loader (`_load_frame_fewshot`, `cg_recognition.py:425-439`)
return a *list* of examples rather than one blob, so swapping in a selector later is a one-line
change.

**5. Version the prompt.** Add a `PROMPT_VERSION` constant next to the system prompt and stamp it
into every log record and every eval result. Without it, "recognition got worse" is unattributable.

**6. `max_tokens` explicitly, always.** Already covered in Section 4 — never unbounded in
production, never a hardcoded constant either. Size it to the scope and detect the cap being hit.

### Context Window Management

Extraction, not RAG — so the levers are scoping and feature compression, not retrieval or
summarisation. Full strategy is in Section 4 ("Context Window Strategy"); the short form:

- **Tier 0 is the primary lever.** Nodes it decides never enter the prompt as candidates — they
  appear as a one-line "already decided" fact. Removing the numerous, boring parameter-role nodes is
  what makes the F1 truncation class largely go away.
- **Chunk by procedure above a threshold.** `procedure_index` already scopes; fix its fail-open
  (F2), then make it automatic past a node count (start at ~60 candidates and tune against measured
  prompt sizes — do not guess the constant, log `usage.prompt_tokens` and set it from data).
  Validate the merged result once, against the full context, so the relational safety checks still
  see every proposal.
- **Compress features, do not dump raw data.** `widget=slider in=0 out=3` is a handful of tokens and
  carries more decision-relevant signal than `position=[10, 30]` plus a paragraph of wire lines.
  Prefer per-node derived tokens over the current flat `wires` list, which the model must mentally
  join.
- **Summarise the tagged-anchor block when scoped** (`_tagged_anchor_lines`, `:528-548`): full
  member lists for the target procedure, one-line counts for the rest.
- **Instrument before optimising.** Every response already carries normalised
  `usage.prompt_tokens`/`completion_tokens` (`llm_gateway.py:186-192`, `:244-249`, `:295-301`) and
  nothing reads them. Log them per call and per eval row; the token budget stops being guesswork.

### Cost and Latency Budget

Rough per-call arithmetic (list prices as of mid-2026 — **re-verify at implementation time**;
Anthropic Sonnet ≈ $3 / MTok in, $15 / MTok out; GPT-4o ≈ $2.50 / $10; DeepSeek ≈ an order of
magnitude cheaper):

| Scenario | Input tokens | Output tokens | ≈ Sonnet cost | Notes |
|---|---|---|---|---|
| Scoped procedure, **today's** prompt (14 candidates) | ~4-5 k (catalog ~3 k dominates) | ~1.5 k | **~$0.04** | The catalog, not the canvas, is most of the bill at this size. |
| Whole canvas, today's prompt (214 candidates) | ~10-12 k | 4 k (capped → truncates) | **~$0.09** | UAT F1's failing case. Pays full price for an unusable answer. |
| Scoped, **two-tier** (Tier 0 absorbs the parameter roles) | ~3-4 k | ~0.6 k | **~$0.02** | Tier 0 itself costs $0 and ~milliseconds. |
| Full eval sweep: 3 provider arms × ~20 fixtures | — | — | **~$2-4** | Cheap enough to run per-PR. Budget it; do not skip it to save $3. |

Expected volume is low — a single architect, a handful of recognition runs per working session — so
the daily spend is cents. **The cost risk is not the steady state, it is the failure modes:** three
retries on a truncated whole-canvas prompt is 3× the most expensive call for zero value, and an
unbounded `max_tokens` on a runaway generation is worse. The truncation guard and the sized budget
are cost controls as much as quality controls.

**Caching.**

- **Exact-match cache (recommended, cheap).** Key on
  `sha256(prompt_version | system | user_prompt | model | temperature | negotiated_mode)`, value the
  validated proposal. At `temperature=0` on an unchanged canvas this is a legitimate hit, and it
  makes eval re-runs and "I fat-fingered the confirm dialog, run it again" free. In-process dict
  bounded by size, or a file in `DATA_DIR` — nothing exotic. **Invalidate on canvas change**: the
  `cgContextJson` content hash is part of the user prompt, so this happens naturally.
- **Provider prompt caching (optional, the bigger win).** The system prompt + concept catalog +
  few-shot prefix is byte-identical across every call and is ~3-4 k tokens — comfortably over
  Anthropic's minimum cacheable prefix. Marking it with `cache_control: {"type": "ephemeral"}` cuts
  the dominant input cost by roughly 90 % on cache hits. **Cost:** `AnthropicAdapter` currently sends
  `content` as a plain string (`llm_gateway.py:172`); this requires switching to the content-block
  array form. Judgement call — **defer it**. It is an adapter change with no quality benefit, and at
  cents per day the payback is negligible. Revisit if per-procedure chunking multiplies call volume.
- **Semantic caching: no.** Two canvases that are "similar" are not interchangeable — member ids are
  identity, and a near-miss cache hit would return proposals referencing nodes that do not exist,
  which the validator would reject anyway. All cost, no benefit, real correctness risk.

**Cheaper models for sub-tasks.** The genuine routing win here is not a smaller model — it is
Tier 0, which handles the highest-volume, lowest-ambiguity decisions in pure Python at zero cost and
zero latency. Beyond that: if a triage step is ever added (e.g. "is this untagged cluster worth
proposing at all?"), route it to `claude-haiku-4-5-20251001` or `gpt-4o-mini` (both already in
`SEED_MODELS`, `llm_gateway.py:113-125`) and keep the frontier model for
Procedure-vs-Pattern adjudication, which is the judgement call that actually needs it. Do not split
the pipeline speculatively — measure first; a second model is a second thing that can silently
regress.

## 5. Evaluation Strategy

> **The problem this section exists to solve.** ROADMAP SC1 — *"recognition proposes entities whose
> member sets match the reference annotation for ≥ the majority of blocks"* — is currently
> **ungradeable**. There is no offline way to score recognition output against a reference, so
> "quality" has only ever been an anecdote (UAT test 1: `blocked`). Everything below exists to turn
> SC1 into a number that `pytest` computes, for free, on every commit.
>
> Dimensions are derived from Section 1b's five rubric ingredients, not from a generic metric menu.
> Three constraints from 1b are binding on the design and are honoured explicitly:
> **(a)** syntactic name conformance is scored **nowhere** — `<NN>_Pat_<k>[ <name>]` makes the
> semantic half optional, so `11_Pat_1` is fully conformant and a grammar-conformance metric would
> score near-free and flatter the system;
> **(b)** `Var`↔`Const` is *partly unresolvable from topology by definition* (the ontology defines
> `ConstantParam` by designer intent), so it is priced as a one-click flip, not as a boundary error;
> **(c)** the measurable unit is **edits required to accept**, not per-node accuracy — per-node
> metrics actively reward FM-4 over-segmentation.

### The unit of measurement

A **block** is one member set with one kind: a reference block in the annotation, or one entry in
`proposals[]`. Blocks, not nodes and not canvases, are the statistical *n* — SC1 says "blocks", the
architect accepts or redraws *blocks*, and per-node counting is the metric-gaming hazard 1b names.

**Matching rule** (deterministic; the harness must produce identical pairings on every run):

1. For every (proposal *p*, reference block *r*) pair compute Jaccard
   `J(p,r) = |M_p ∩ M_r| / |M_p ∪ M_r|` over member ids.
2. Drop pairs with `J = 0`.
3. Sort surviving pairs by `(-J, reference_block_id, proposal_index)`. The two tiebreakers make the
   ordering **total**, so the pairing is reproducible byte-for-byte.
4. Greedily accept top-down, skipping any pair whose proposal or reference block is already taken.
   The result is one-to-one by construction.
5. Reference blocks left over = **misses**. Proposals left over = **spurious**.

*Honest caveat:* greedy is not guaranteed optimal (Hungarian would be). It is chosen to keep the
harness stdlib-only — `scipy` would drag in numpy for a 60×60 assignment problem. At these sizes,
where most true matches are `J = 1.0`, greedy and optimal coincide; the harness **must log a warning
whenever ≥2 pairs tie on `J` for the same reference block**, and a unit test must assert
greedy == brute-force-optimal on small synthetic cases.

**Match thresholds.** A pair is *recorded* at any `J > 0` (needed to measure fragmentation), but
counts as:
- **exact** only at `J = 1.0` — set equality, order-insensitive. This is what SC1's word "match"
  means: the architect clicks Accept and edits no boundary.
- **near** at `J ≥ 0.5` — more than half the union is shared. For a 3-member reference this is
  "2 of 3 right, ≤1 spurious": one boundary edit, i.e. the partial-accept path. Recorded separately
  because 1b prices boundary redraws as *the most expensive correction in the confirm UI*.

### Tier 0 and Tier 1 are scored separately, then jointly

Tier 0 is deterministic. It deserves ordinary unit tests, not statistical evaluation, and its
precision is a **first-class metric in its own right** because an over-eager rule is invisible: its
output carries `confidence 1.0`, it is presented to the architect as settled, and the node it claims
never reaches the LLM to be second-guessed.

| Scope | What is scored | How | Gate |
|---|---|---|---|
| **Tier 0 alone** | R1–R6 correctness and abstention behaviour | `tests/test_cg_topology.py` — one PASS + one ABSTAIN test per rule over hand-built micro-contexts; `widget_kind` parity table vs C# `ClassifyNodeKind`; `merge()` order-stability (proposal array order **is identity across the bridge** — `p3` must mean the same entity on the confirm call as on the preview call) | **T0-precision ≥ 0.98** on decided blocks. **T0-contamination = 0** (never decides a node the reference marks `abstain_expected`). T0-coverage is *reported, not targeted* — a rule deciding 5% at 100% precision is honest; 80% at 85% is harmful. Where Python and C# disagree on `widget_kind`, Tier 0 must abstain, and there must be a test proving it does. |
| **Tier 1 alone** | The LLM over the residual only, with Tier-0 decisions supplied as context | The eval harness, arms A1–A5, scoring E2–E7 over `residual` reference blocks | No independent gate; this is the diagnostic view that separates "the prompt is broken" from "the rules are broken" |
| **Joint (0+1 merged)** | The pipeline the architect actually uses | The eval harness on the merged, post-`validate_proposed_structure` object | **This is where SC1 is decided.** E1/E5-silent-drop/E7-grammar/E9 are conjunctive hard gates; E2's M1 carries the threshold |

### SC1 pass threshold — and why this number

**Ship gate (what makes Phase 35 pass):**

> **M1 (exact member-set match rate) ≥ 0.60** on the evidence corpus, arm A3, **conjunct with**
> E1 violations = 0 · silent drops = 0 · `grammar_citation_rate` = 0.00 · confidence-spread check
> passes · E9 provenance complete.

**Why 0.60 rather than the ROADMAP's bare "majority" (> 0.50).** At the planned corpus size
(*n* ≈ 30 blocks on the evidence corpus) a 0.51 gate is decided by sampling noise: the Wilson 95%
interval around `p̂ = 0.60, n = 30` is roughly **[0.42, 0.75]**, so runs scoring 0.53 and 0.47 are
statistically indistinguishable. 0.60 is the smallest threshold that clears "majority" by more than
one block's worth of noise at that *n*. Setting it higher would assert a number the project has no
evidence it can reach; the honest position is that the true achievable rate is **unknown** — 1b's
literature brackets useful pre-annotation between "~10% correct helps on nothing" (DALPHI, South et
al.) and "93.25% gives 1.7× speed-up with no quality loss" (Mikulová et al.), and this system's
break-even sits somewhere in that gap and has never been measured.

**Claim threshold (what licenses writing "the majority of blocks" in the dissertation).** Distinct
from the ship gate, and stricter: the **Wilson 95% lower bound must exceed 0.50**. That requires
either **21/30 = 0.70** at *n* = 30 blocks, or **0.60 at n ≥ 100 blocks**. State in the thesis which
one is being claimed, or report the interval and claim nothing stronger than it supports.

**Reported alongside, or M1 is uninterpretable at n = 1** (1b, *Domain Expert Roles*): the
architect's **test–retest self-agreement ceiling** (one held-out procedure re-annotated blind
≥ 4 weeks later) and the **external-peer agreement floor** (one calibration session on 10–20 blocks).
The system cannot honestly be reported as scoring above the architect's own reproducibility on the
same task.

### Ablation arms — turning the spec's causal claims into evidence

This whole spec is a set of causal claims ("the few-shot is the root cause", "Tier 0 helps", "a
frontier model is not the fix"). UAT **F3** asks the question directly: *prompt defect or model
capability limit?* The arms are designed as a 2×2 that answers it, not as a feature list.

| Arm | Configuration | The claim it tests |
|---|---|---|
| **A0** | as-shipped: current few-shot, **no** system prompt, no Tier 0, `deepseek-chat` | **Negative control, and the harness's own validity test.** A0 must reproduce F3 — near-zero M1 with high `grammar_citation_rate`. *If A0 does not fail this way, the harness is wrong, not the model,* and no other arm's number can be trusted. Run this first. |
| **A0f** | A0's prompt, unchanged, on `claude-sonnet-5` | Completes the 2×2: does a frontier model override a bad demonstration on its own? |
| **A1** | A0 + counterexample-shaped few-shot (fixture replacement only) | Section 4b.3's central claim: fixing the demonstration is the highest-impact change. |
| **A2** | A1 + system prompt with grammar-as-target / grammar-anti-filter double framing | Isolates the `req.system` defect (D1/D2) from the fixture defect. |
| **A3** | A2 + Tier 0 (deterministic pre-classifier + feature-enriched candidate lines) | The shipping configuration. Also isolates D5 (impoverished node features). |
| **A4** | A3 + negotiated provider-native structured outputs | Whether constrained decoding buys anything once the prompt is sane, or only converts `bad_json` retries into content retries (D3). |
| **A5** | A3 on `claude-sonnet-5` | Cost decision: is the cheap deployed provider sufficient once the prompt is fixed? |

**Decision rule for F3, written before the data exists** (this is the point of pre-registering it):

- `A0f ≫ A0` **and** `A2 ≫ A0` → both prompt and model contribute; fix the prompt (cheap) first.
- `A2 ≈ A5` → the prompt was the whole story and DeepSeek suffices. **This is the cost-relevant
  outcome** and the one the diagnosis brief predicts.
- `A2 ≈ A0` but `A5 ≫ A0` → genuine capability limit; the frontier model is the fix and the spec's
  central claim was wrong. Record that.

**Example-order sub-sweep (required, not optional).** Section 4b cites Lu et al. — permuting the
same demonstrations swings accuracy from near-SOTA to near-chance. Run the winning arm over **3
fixed permutations** of the few-shot examples. If M1 varies by more than ~0.10 across permutations,
the headline number must be reported as a **range with the permutation spread**, not a point
estimate, and the fixture ordering must be pinned and justified in the file.

**Record / replay — how CI stays deterministic and free.**

Cassette key = `sha256(provider | model | promptVersion | system | userPrompt | temperature |
negotiatedMode | maxTokens)`. Because `promptVersion` and the prompt body are both in the key, **any
prompt change invalidates every cassette by construction** — the freeze discipline is enforced by the
hash, not by remembering.

Cassette contents: `{requestDigest, promptBody?, responseText, usage, finishReason, provider, model,
recordedAt, cassetteVersion}`. `promptBody` is stored **only** for corpora marked `ipClass: own`;
per 1b's third-party-IP constraint and §4b's *"never log the prompt body verbatim"*, a corpus derived
from anyone else's canvas stores the digest alone.

| `RECOGNITION_EVAL_MODE` | Behaviour | Where it runs | Cost |
|---|---|---|---|
| `replay` **(default)** | Reads cassettes only. A **cassette miss fails the test loudly**, printing the missing key and the refresh command — it never silently falls through to a live call, which is how CI quietly starts costing money. | every commit / CI | **$0** |
| `record` | Calls live, writes cassettes, then scores. Requires `LLM_MASTER_SECRET` + a configured provider. | manual, on demand | ~$2–4 per full sweep (§4b arithmetic) |
| `live` | Calls live, writes nothing. "Is it still true today?" spot check. | manual | per-call |

**Temperature must be pinned to 0.0 or none of this is reproducible** (defect D6 — currently
uncontrolled on both cloud adapters). Stated honestly: `temperature=0` is *near*-deterministic, not
deterministic — batching and MoE routing still introduce jitter. So **replay is exactly reproducible
(it is a file read); re-recording is not.** Never assert byte-identical model output anywhere. Every
cassette refresh is its own commit, carries its `recordedAt`, and must be reported with the metric
delta against the recording it replaced.

**CI/CD integration.** There is no GitHub Actions workflow in this repo today, so "CI" means the
suite gate below. The cassette design deliberately needs **no secrets**, so promoting it to a
workflow later is free.

```bash
# ── Fast gate: every commit. Replay only, no network, $0. ─────────────────────
docker compose exec -T data-service python -m pytest tests/ -q -m "not live"

# ── The SC1 gate specifically (fails the build below threshold) ───────────────
docker compose exec -T -e RECOGNITION_EVAL_MODE=replay data-service \
  python -m pytest tests/test_recognition_eval.py -q \
    --corpus=urbanblock_slice --arm=A3 --sc1-gate=0.60

# ── Full ablation sweep: manual, live keys, ~$2-4. Writes cassettes. ──────────
docker compose exec -T -e RECOGNITION_EVAL_MODE=record data-service \
  python -m pytest tests/test_recognition_eval.py -q -m live \
    --arms=A0,A0f,A1,A2,A3,A4,A5 --permutations=3

# ── Human-readable report (the artifact that goes in the thesis appendix) ─────
docker compose exec -T data-service python -m tests.recognition_eval.report \
  --out /data/recognition-eval-report.md
```

`--corpus` / `--arm` / `--sc1-gate` / `--arms` / `--permutations` are registered via
`pytest_addoption` in the existing (currently near-empty) `data-service/tests/conftest.py`. Markers:
`@pytest.mark.eval` and `@pytest.mark.live`, with `-m "not live"` as the default so a developer
running `pytest` bare never makes a paid API call by accident.

### Reference Dataset

> **This is the hard blocker, and it must be confronted rather than assumed away.**
> `DG/tests/DG.Tests/Fixtures/frame-cg-context.json` has **34 nodes and exactly one wire**
> (line 97) — and it is a **RawCanvas** fixture (`definition`/`scribbles`/`groups`/`nodes`/`wires`),
> *not* the serialized `cgContextJson v1` shape (`algorithms`/`untagged`) that recognition consumes.
> Every Tier-0 degree rule collapses to R5-abstain on it. Separately, UAT records that **no Frame
> `.gh` exists anywhere on disk** (whole-profile scan negative) and that UAT actually ran against
> UrbanBlock_V7 (233 nodes, 221 untagged) with a **synthetic** proposals payload that bypassed the
> LLM entirely. An eval built on the Frame fixture as-is would score Tier 0 as useless and measure
> Tier 1 alone.

**The asset that makes this tractable.** The Frame fixture is *fully tagged*: 34 convention groups
covering `Pat`×3 (one nested: `11_Pat_DivideLine` hosts `11_Pat_TopChord`), `IntF`×4, `Var`×6,
`Const`×8, `Emg`×9, plus a deliberately-misspelled `11_Emr_UpperChord`, a non-convention
`Scratch notes` group with 2 members, and one wholly untagged `n-untagged-01` loose panel.
**A complete reference annotation already exists in git, authored 2026-07-08, machine-readable, in
the exact member-id vocabulary** — stronger even than 1b's OWL-individuals observation, because it is
directly comparable to `proposals[].memberIds`. It predates the recognition pipeline, so it is a
genuine pre-registration.

**Options weighed, and the choice.**

| Option | For | Against | Verdict |
|---|---|---|---|
| **1. Enrich the Frame fixture with real wiring** | Reference already exists and is pre-registered; **tag ablation** makes the eval input mechanically derivable from it, so input and reference *cannot drift*; zero Rhino dependency; CI-runnable; $0 | **Fatal for Tier-0 evidence:** the wiring must be authored by the same person authoring the Tier-0 rules. Wire it so `Var`s have in-degree 0 and `Emg`s out-degree 0 and Tier 0 scores 100% **by construction**. Also: invented GUIDs (`guid-divide-curve`), so the `componentGuid`→`widget_kind` path (pitfall 7) is untestable; no relays, no spatial interleaving ⇒ **FM-1 and FM-2 untestable** | **ADOPT — as Corpus A, with a scope limit** |
| **2. Fresh `cgContextJson` pull from live UrbanBlock_V7 + hand-annotate** | Real wiring authored for *design* reasons; real relays, real dead matter, real GUIDs, real misleading nicknames (`TARGET SCR`, `Num`, `H`); differently-authored from Frame, which 1b says is **required before SC1 can claim to generalise**; the pull path already works (exercised repeatedly in UAT session 2) | Annotation cost — 221 untagged nodes is not an afternoon; the annotation is authored *after* the pipeline exists, by the same person, so it is **not** pre-registered | **ADOPT — as Corpus B, scoped to 2–3 procedures** |
| **3. Rebuild Frame as a real `.gh`** | Closes the UAT gap literally; real GUIDs; real wiring; makes test 1 runnable on the *intended* fixture | Same circularity as Option 1 (the researcher wires it knowing the labels), at ~10× the cost. Buys artifacts, not independence | **DEFER** — a UAT-closure task, not an eval prerequisite |

**Chosen: Options 1 and 2 together, with explicitly different jobs.** Not "both because both are
nice" — each is unsound alone and they answer different questions:

**Corpus A — `frame_ablated`.** *Job: regression net, harness validity, Tier-1 prompt ablation.*
Built by `scripts/build_frame_ablated.py`, which (a) serializes the tagged RawCanvas fixture through
the same path production uses, (b) **ablates** all entity tags — keeping only the `OBJECT - FRAME`
scribble, the `1_ALGORITHM` scribble and the 2 `_Proc` groups, exactly the condition ROADMAP SC1
names — demoting the stripped groups to `untagged.groups`, and (c) emits the stripped groups as the
`.expected.json` reference. Input and reference are generated by one script from one source, so they
**cannot** drift, and the script is the audit trail. Two required fixture repairs, each in its own
commit: **fill the two `_Proc` groups' `memberIds`/`nestedGroupIds`** (they are currently empty —
which is also the live trigger for UAT F2, so this doubles as F2 test coverage), and **add real
wiring**.

> **Corpus A is explicitly NOT evidence for Tier-0 precision, and the harness enforces this.**
> Its `.expected.json` carries `"tier0Evidence": false`; E0 metrics are computed and printed for
> Corpus A but stamped `evidence: false` in the report and excluded from any reported figure. The
> wiring must be derived from the *semantics of the named Grasshopper components* (a `Divide Curve`'s
> real output ports, a `Line SDL`'s real inputs) rather than from what would make a Tier-0 rule fire,
> and the wiring commit must land **before** `cg_topology.py` exists. That reduces the circularity;
> it does not eliminate it. Only Corpus B can.

**Corpus B — `urbanblock_slice`.** *Job: the SC1 evidence corpus. All headline numbers come from
here.* Captured via the existing `/computgraph/context/pull` bridge on UrbanBlock_V7, scoped to
**2–3 procedures (~60–80 nodes)** — which is not a shortcut but the correct unit, since per-procedure
scoping is the recommended production path (§4 Context Window Strategy) and the eval unit should
match the production unit.

|---|---|---|---|

| Nodes | 34 | ~60–80 | ~100–115 |

statistical sample; 2 canvases is the generalisation sample, and 2 is the honest minimum for a claim
of generality, not a comfortable one.

contain, at minimum:

| ≥ 2 disconnected / abandoned components marked `abstain_expected` | FM-3, and the positive case for E5 abstention recall |
| ≥ 1 multi-member `Pattern` **and** ≥ 1 nested `Pattern` | FM-4 and its catch-all mirror; nesting agreement in E2 |

**Labeling.**

| Corpus | Who / how |
|---|---|
| **A** | **Mechanically derived** by `build_frame_ablated.py` from tags the architect authored 2026-07-08. No new human judgement, therefore no new bias — the generator is the audit trail. |
| **B** | **Architect-researcher**, annotating **in Grasshopper through the normal tagging UI**, then pulling the tagged context — so the reference is produced by the *same instrument* that produces production ground truth, not by hand-editing JSON. Annotated **before** any arm is run. |
| **Ceiling** | **Test–retest**: one procedure of Corpus B re-annotated from scratch ≥ 4 weeks later, blind to the first pass. One afternoon; the single cheapest bias mitigation available (1b). Reported as the self-agreement ceiling. |
| **Floor** | **One external computational designer**, one session, 10–20 blocks, prioritising E2 boundaries and E3 `Var`/`Const` — the two most intent-laden. Converts "the author says these boundaries are right" into a measured agreement floor. |
| **Judged dimensions** | E4-name and E7-soft only, by an LLM judge from a *different* provider than the arm under test, blind and shuffled, and **excluded from SC1 until calibrated at ≥ 0.7 against ≥ 20 human labels**. |

**Freeze protocol — mandatory, and mechanically enforced.**

1. `*.expected.json` is committed in a **separate commit** from any change to
   `prompts/recognition_system.md`, `fixtures/frame_recognition_fewshot.json`, or `cg_topology.py`.
   **If the reference and the prompt change in the same commit, the run is void** — not
   "questionable", void. This is 1b's n=1 bias mitigation and it is the difference between a measured
   result and a tuned one.
2. Enforcement is not left to memory. A pre-commit check (plus an advisory pytest test) inspects the
   staged file list and rejects the combination. It is advisory only — a rebase or squash can defeat
   it — so the real guarantee is (3).
3. Every result row records `frozenAtCommit`, `contextSha256`, `promptVersion`, provider, model,
   `temperature` and `negotiatedMode`. The harness **refuses to score** a run whose provenance block
   is incomplete, and asserts the on-disk context hash matches `contextSha256`.
4. Growth is allowed; silent growth is not. Adding blocks to a reference bumps a `corpusVersion` and
   every historical number is re-stamped with the version it was measured against, because M1 across
   different corpora is not a time series.

## 6. Guardrails

> **What this section is not.** This is a single-user PhD research tool operating on the
> researcher's own Grasshopper definitions. There is no free-text user input, no third party, no
> personal data, and no autonomous action — RCGN-04 means nothing reaches Neo4j without an explicit
> on-canvas click. Toxicity filters, jailbreak detectors, PII scrubbers and content-safety judges
> would be **padding**, and are deliberately absent. The one latent privacy concern (1b Regulatory
> item 2: a recognition prompt contains the architect's full canvas topology, which becomes a
> disclosure decision the moment a collaborator's definition is pulled) is handled by the
> log-redaction rule in §4b and by keeping the Ollama local path viable — not by a guardrail.
>
> The real guardrails here are **integrity** guardrails, and half of them already exist and are
> load-bearing. The other half are the UAT findings, promoted from "known bug" to "enforced
> invariant".
>
> **Latency is not a constraint for these.** Every guardrail below is pure Python over an
> already-parsed object or over adapter response metadata — microseconds, no extra LLM call. The
> usual "be selective, guardrails add latency" caution does not bite; the reason to keep the list
> tight is comprehensibility, not cost.

### Online (Real-Time)

Ordered: existing-and-must-survive first, then the new ones. "Retry" means feed the violation back
into the existing bounded-retry loop (`max_retries=2` ⇒ 3 attempts) — not a new mechanism.

| # | Guardrail | Trigger | Intervention |
|---|-----------|---------|--------------|
| **G1** | `tagged_overlap` **(exists — `cg_recognition.py:222-262`)** | A proposal claims a component already owned by a tagged entity | **Block + retry.** The single most consequential rule in the system: these tags are the thesis's reference annotation (1b Dim 1). Must survive the two-tier refactor and be asserted **post-merge**, so a Tier-1 proposal colliding with the architect's tags is caught even when Tier 0 was clean. |
| **G2** | `duplicate_member` **(exists)** | Two proposals claim the same component | **Block + retry.** Post-merge, so it also catches a Tier-1 proposal claiming a node **Tier 0 already decided** — a collision class that did not exist before this phase. |
| **G3** | `unknown_member_id` **(exists)** | A `memberId` in `proposals[]` *or* `unrecognized[]` is not in the submitted context | **Block + retry.** Kept as a *validator* check, never a prompt instruction — the distinction is the guarantee (Section 1 failure mode 3). |
| **G4** | `invalid_kind` **(exists — WR-02)** | `kind` outside the short/long spelling set | **Block + retry.** `ProposalDto.ToEntityTagKind()` **throws** on an unknown kind (`PreviewRegistry.cs:110-123`); catching it Python-side keeps the failure on the retry loop instead of on the canvas. |
| **G5** | `too_many_proposals` / `too_many_members` **(exists)** | > 200 proposals or > 1000 members | **Block, no retry.** A DoS bound, not a formatting slip. Surface the per-procedure scoping advice. |
| **G6** | **`unaddressed_candidate` — NEW** | A scoped candidate id appears in **neither** `proposals[].memberIds` nor `unrecognized[].memberIds` | **Retry** with the missing ids named; on the final attempt, **auto-fill** them into `unrecognized[]` with reason *"not addressed by the model"* and **flag** the run. RCGN-04 promises *"never silently dropped"* and today nothing enforces it. Blocking the whole run over one dropped node would be worse than surfacing it — hence fill-and-flag on the last attempt. |
| **G7** | **`grammar_as_filter` — NEW; this is the one that would have caught UAT F3 in production** | Any `rationale` cites the naming grammar/convention as a *reason* (keyword + regex over "grammar", "convention", "does not match", `<NN>_…_<Name>` forms), **or** the structural signature `proposals == 0 ∧ candidates ≥ 5` | **Retry once with a targeted corrective message**, then **block** with a diagnostic the architect can act on: *"the model is filtering by name instead of classifying by topology — prompt version X, provider Y."* Zero-proposals-on-many-candidates is a strong enough signal to surface even without the keyword. Zero tolerance: this is Section 1's live root cause. |
| **G8** | **`output_truncated` — NEW (UAT F1)** | `finish_reason == "length"` (OpenAI) / `stop_reason == "max_tokens"` (Anthropic) / `done_reason` equivalent (Ollama) | **Block, explicitly NO retry**, and return the scoping hint immediately. Retrying an identical scope truncates identically: today that is 3× the most expensive call for zero value, and the user who most needs the "scope to one procedure" advice is the only one who never sees it. |
| **G9** | **`empty_procedure_scope` — NEW (UAT F2)** | `procedure_index` resolves to a tagged procedure with no members | **Block** with a user-actionable message. **Never widen scope silently** — the silent widening is what turns an intended 14-node call into a 214-node call and then into G8. |
| **G10** | **Confidence floor — NEW** | `confidence < 0.5` on a proposal | **Demote**, don't block: the proposal moves to `unrecognized[]` carrying the would-be kind as a hint. Below coin-flip, rendering a preview group costs more review time than it saves (1b Dim 5's asymmetry). **The 0.5 is provisional and must be labelled as a guess in the code**; re-derive it from the accept-rate-vs-confidence curve once ≥ 50 flywheel records exist. Configurable per call. |
| **G11** | **Flat-confidence detector — NEW** | ≥ 5 proposals and `stdev(confidence) < 0.02`, or a single unique confidence value | **Flag** the run `confidence_uninformative` and **render the legend without percentages**. The synthetic UAT payload used a flat `0.9` and nothing objected; showing `(90%)` when the number carries no information is worse than showing nothing, because it drives triage. Flag, not block — a flat-confidence run may still contain good proposals. |
| **G12** | **Accept-time publishability gate — NEW (UAT F5)** | At **accept** time (not preview): a proposed parameter whose `InferParameterDataType` would return null — e.g. a `Const` on a bare `Number` component | **Block that one proposal, allow the rest.** Message names the component and the fix. This moves the failure from Phase 36's all-or-nothing 422 — where *11 valid entities could not land because of 1 invalid one*, three phases away from the cause — to the moment the architect can still act on it. Per-entity, deliberately not all-or-nothing. |
| **G13** | **Tier-0/Tier-1 merge order stability — NEW** | Merged proposal array order differs between the preview call and the confirm call for the same input | **Block the confirm.** Proposal ids are synthesized C#-side as `p0, p1, …` **by array index** (`CanvasListenerComponent.cs:416-470`), so **array order is identity across the bridge**. If merge reorders, `p3` silently means a different entity than the architect approved. |

### Offline (Flywheel)

Fed by `recognition_labels.jsonl` (one record per confirm decision, §4 Tier-2) joined to
`recognition_runs.jsonl` (one record per recognition call, §7) on `runId`. **Every architect decision
in `DG STRUCTURE CONFIRM` is a labelled example with provenance** — the instrument already works
(UAT test 4 passes); nothing currently captures its output. Partial accepts are the highest-signal
record of all: *the boundary the architect redrew **is** the correction.*

**Sampling: log 100%.** At one user and a handful of runs per session there is nothing to sample —
the cost of full capture is a few KB per session. What is *selective* is the **review queue**, below.

| Metric | Sampling / cadence | Action on degradation |
|--------|--------------------|----------------------|
| **Accept rate** — `accept / (accept + reject + partial)` per `promptVersion × provider × model` | Every decision; evaluate on a rolling window of 20 | **The production quality signal**, and the closest thing to ground truth that is not self-graded (1b: prefer behavioural over self-reported evidence). < 0.5 ⇒ re-run the eval sweep. **If the sweep does not reproduce the drop, the corpus has drifted from real canvases — add a canvas, don't tune the prompt.** |
| **Partial-accept rate** and **mean boundary edit size** (`\|M_proposed Δ M_final\|`) | Every partial accept | E2's member-edit metric, measured in production for free. A rising partial-accept rate means boundary quality is degrading **even while accept rate holds** — it is the earlier signal of the two. Triggers an E2-focused prompt review, not a threshold tweak. |
| **Confidence → accept calibration curve** | Recompute every 25 new decisions | Sets **G10's floor from data instead of a guess**, and decides E6's open question: whether `confidence` should render on canvas at all. If the curve stays flat, stop showing the percentage. |
| **Abstention correctness** — fraction of `unrecognized[]` entries the architect later tags manually with a kind the system could have proposed | Weekly-ish over accumulated runs | High ⇒ over-abstaining, the mirror risk of the coverage-chasing 1b Dim 5 warns about. Low with a high reject rate ⇒ under-abstaining. Adjust the abstention licence in the system prompt, and re-run the sweep to confirm the change is real rather than noise. |
| **Zero-proposal run rate** (≥ 5 candidates, 0 proposals) | Every run; auto-queued for review | **The F3 signature.** Any occurrence is investigated immediately — this is the specific regression the whole phase exists to prevent, and it must never again be discovered by a human noticing. |
| **Tier-0 override rate** — Tier-0-decided proposals rejected or edited by the architect | Every decision involving a `tier: "0"` proposal | Tier 0 asserts `confidence 1.0`. **Any override is a rule bug, not a tuning opportunity.** > 2% over 50 Tier-0 proposals ⇒ open the rule, and prefer making it abstain over making it cleverer. |
| **Run health** — truncation rate, mean attempts, violation-code frequency, `negotiatedMode == "none"` rate | Every run | Truncation > 1 in 10 ⇒ the per-procedure chunking threshold is mis-set. Rising `bad_json` under a negotiated *strict* mode ⇒ **the capability negotiation is lying**, which §4b already calls out as a bug worth logging loudly. |
| **Cost / token drift** | Every run; rolling 30-run median | > 2× median ⇒ investigate. The cost risk here is not the steady state (cents/day) but the failure modes: retries on truncation, and prompts growing silently as the catalog grows. |

**Review queue (the selective part).** Auto-queue for the architect's eye: every zero-proposal run;
every rejection at `confidence ≥ 0.8` (the most expensive class of output this system produces);
every partial accept; every run with violations on the final attempt; every run where Tier 0 was
overridden; every run where `negotiatedMode` fell back to `none` unexpectedly — **plus a random 10%
floor**, so the queue is not purely failure-selected. Without the random floor there is no baseline
against which to notice *signal–metric divergence*, which is the early-warning system for the
failure modes the eval does not yet cover.

## 7. Production Monitoring

> **"Production" here is one architect using Rhino on their own machine.** A handful of recognition
> calls per working session, no SLA, no on-call, no second user. Monitoring must be proportionate to
> that, and the test of proportionality is simple: *does this artifact make the flywheel real and
> quality observable, or is it infrastructure for a problem the project does not have?*

### Tracing Tool — the Phoenix decision, made rather than deferred

**Recommendation: do NOT add Arize Phoenix in this phase.** Four concrete reasons, not a hedge:

1. **There is no volume for it to find patterns in.** Phoenix earns its keep by surfacing structure
   across many traces. This system produces perhaps a dozen recognition calls a week, from one user,
   on one canvas at a time. A trace UI over twelve spans is a more expensive way to read twelve
   lines of JSON.
2. **Cost of ownership is not zero.** A 13th `docker-compose` service, a port, a volume, an
   OpenTelemetry dependency chain inside `data-service` (against §2's *"net new runtime
   dependencies: zero"*), and — the part that actually matters — **a second place where the
   architect's full canvas topology is stored**. That is precisely the disclosure surface 1b's
   Regulatory item 2 flags as activating the moment a collaborator's definition is pulled.
3. **It would trace the easy half and miss the half that matters.** The questions this project needs
   answered are longitudinal and *outcome-linked*: accept rate vs. confidence vs. prompt version.
   The outcome — accept / reject / partial-accept — happens in **Grasshopper**, not inside the traced
   Python call. Joining a GH confirm decision back to a Phoenix span means pushing the outcome into
   Phoenix anyway, at which point the local log already has it and the span adds nothing.
4. **Reproducibility needs a committed, diffable, greppable artifact.** SC1 is a dissertation claim
   (1b, binding). A number that lives in a container volume outside git cannot back it. A JSONL file
   in `DATA_DIR`, summarised into a markdown report by the eval harness, can.

**Recommended instead: structured JSONL run logs written by the existing service.** Two append-only
files under the same `DATA_DIR` convention as `llm-settings.json` (`llm_gateway.py:410-411`), joined
on `runId`:

| File | One record per | Written by |
|---|---|---|
| `data/recognition_runs.jsonl` | `recognize_structure()` call | `cg_recognition.py` |
| `data/recognition_labels.jsonl` | confirm decision (accept / reject / partial) | the confirm endpoint, per §4 Tier-2 |

Most of this is **writing down what the code already computes and throws away**: `GenerateResponse`
already carries normalised `usage.prompt_tokens` / `completion_tokens`
(`llm_gateway.py:186-192`, `:244-249`, `:295-301`) **and nothing reads them** (§4b says so directly).

```jsonc
// data/recognition_runs.jsonl — one line per call
{
  "runId": "…uuid4…", "ts": "2026-07-…Z",
  "project": "…", "definitionId": "…", "contextSha256": "…",   // canvas identity, not canvas content
  "procedureIndex": 11, "scopeNodeCount": 14,
  "tier0DecidedCount": 9, "tier1ResidualCount": 5,
  "promptVersion": "r35.3", "promptSha256": "…",               // NOT the prompt body (§4b)
  "provider": "anthropic", "model": "claude-sonnet-5",
  "negotiatedMode": "json_schema_strict",
  "temperature": 0.0, "maxTokens": 856,
  "attempts": 1, "violationCodes": [], "finishReason": "end_turn", "truncated": false,
  "usage": {"promptTokens": 3714, "completionTokens": 588},
  "estimatedCostUsd": 0.0200, "latencyMs": 6180,
  "proposalCount": 5, "unrecognizedCount": 2,
  "confidence": {"min": 0.55, "mean": 0.74, "max": 0.92, "stdev": 0.14},
  "grammarCitationCount": 0, "valid": true
}
```

**Never the prompt body, never the API key** — `promptSha256` is enough to tie a run to a cassette
without persisting the architect's canvas a second time (§4b / LLMC-06). Rotate by size (10 MB, keep
3); it is a local file, do not over-engineer it.

**When Phoenix (or Langfuse) *does* become the right call — a real trigger, not a hedge.** Revisit
the moment any one of these is true: (a) more than one person uses the system; (b) per-procedure
chunking turns one recognition into a multi-call fan-out where per-span latency and cost attribution
stop being readable as flat JSONL; (c) v10.0 Script Intelligence introduces multi-step agentic flows
with tool loops. At that point Phoenix's OTel-based, framework-agnostic tracing is genuinely the
right choice, and the JSONL schema above maps onto spans essentially field-for-field — so choosing
JSONL now is not a dead end, it is the same data model without the container.

### Key Metrics to Track

Five, each with a decision attached (per `ai-evals.md`: only track what drives a decision):

1. **Accept rate per `promptVersion`** — the primary quality signal, and the only one that is not
   self-graded. Decides whether a prompt change shipped an improvement or a regression.
2. **Boundary edit burden** — mean `|M_proposed Δ M_final|` over partial accepts. Decides whether
   E2 (the deliverable) is degrading, and it moves before accept rate does.
3. **Zero-proposal run rate** (≥ 5 candidates, 0 proposals) — the **UAT F3 regression sentinel**.
   Decides whether the phase's central fix is still holding in the field.
4. **Run health** — truncation rate, mean attempts, and `negotiatedMode == "none"` rate. Decides
   whether the chunking threshold and the capability negotiation are correct in the real world
   rather than in the fixture.
5. **Cost and latency per run** — decides nothing most weeks, which is the point; it exists to catch
   the failure modes (retry storms, silently growing prompts), not the steady state.

### Alert Thresholds

**"Alert" at n = 1 means a `WARN` in the service log and a line in the next run report — not a
pager.** Saying otherwise would be theatre. What matters is that these are *computed*, so they
cannot be missed by not looking.

| Condition | Level | Why this number |
|---|---|---|
| Any run with ≥ 5 candidates and 0 proposals | **WARN immediately** | The F3 signature. Zero tolerance; this is the failure the phase exists to fix. |
| `grammarCitationCount > 0` on any run | **WARN immediately** | G7 already blocks it; a WARN here means the guardrail fired in production, which is prompt-regression evidence. |
| Accept rate < 0.50 over the last 20 decisions | WARN + re-run the eval sweep | Below coin-flip, 1b's pre-annotation literature says the assistant is producing **no net benefit** — correcting spurious suggestions costs more than annotating from blank. |
| Truncation on > 1 run in 10 | WARN | The per-procedure chunking threshold is mis-set (§4b says set it from measured `usage.prompt_tokens`, not by guessing). |
| `negotiatedMode == "none"` where the provider was expected to support strict | WARN | The negotiation is lying — a bug, and it silently changes which enforcement path is running. |
| Tier-0 override rate > 2% over 50 Tier-0 proposals | WARN | Tier 0 claims `confidence 1.0`. Any sustained override is a **rule** bug; the fix is abstention, not tuning. |
| Cost per run > 2× the rolling 30-run median | WARN | Catches retry storms and prompt growth. Absolute spend is cents; the *ratio* is the signal. |
| `stdev(confidence) < 0.02` on ≥ 5 proposals | WARN (G11 already flags in-band) | Confidence has stopped carrying information; triage silently degrades to reading top-to-bottom. |

### Smart Sampling Strategy

**Capture 100%; sample the *review*, not the logging.** Storage is a few KB per session; the scarce
resource is the architect's attention, and it is the same attention that does the design work.

Auto-queue for review (signal-based, all computable from the two JSONL files):

- every **zero-proposal** run — the F3 class;
- every proposal **rejected at `confidence ≥ 0.8`** — the most expensive output the system can
  produce (Section 1 failure mode 4), and the richest single input to the calibration curve;
- every **partial accept** — the highest-signal label available, because the redrawn boundary *is*
  the correction (1b, *Domain Expert Roles*);
- every run with **violations on the final attempt**, and every run where **Tier 0 was overridden**;
- every run where **`negotiatedMode` fell back** unexpectedly;
- **plus a random 10% floor.**

That last item is the one worth defending. A queue built only from failure signals can only ever
confirm the failure modes already known. The random floor is the sole source of a non-selected
baseline, and therefore the only way to notice **signal–metric divergence** — runs the architect
quietly abandons while every metric reads green. At this volume the 10% floor costs about one extra
review per session.

Reviewed items feed straight back into Section 5: a queue item that the metrics scored as *correct*
but the architect judged wrong is, by definition, a **gap in the reference corpus** — promote it to
a new reference block (bumping `corpusVersion`), rather than adjusting a threshold until the number
looks right.
