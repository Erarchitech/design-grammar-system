<plan_decisions>
- **The generator is C#, not `scripts/build_frame_ablated.py`.** Deliberate deviation from AI-SPEC §5's filename. The RawCanvas ⇒ `cgContextJson v1` serialization is `ComputgraphContextSerializer` + `CanvasAnnotationParser`, both C#-only; there is no serialized-context fixture in Python-land today (verified: `data-service/fixtures/` holds only the few-shot). A Python generator would have to re-implement the production serializer, and a corpus whose input is produced by a reimplementation of the code under test is worse than the drift it was meant to prevent. So the generator is a DG.Tests golden-file emitter using the production path, and Python only *reads* the two committed artifacts. Record this deviation in the summary.
- **One emitter, both files, golden-file asserted.** `FrameAblatedCorpusEmitterTests` reads the tagged RawCanvas, emits the reference from the entity groups it is about to strip, strips them, parses + serializes the remainder, writes both files, and asserts the committed copies match what it just produced. A fixture edit that would desynchronise input and reference therefore fails the build instead of silently skewing a score.
- **`tier0Evidence: false` on Corpus A, enforced by the harness, not by a comment.** `corpus.py` reads the flag and 35-13 stamps `evidence: false` on E0 rows from any corpus carrying it. AI-SPEC is blunt about why: wire the fixture so `Var`s have in-degree 0 and Tier 0 scores 100% by construction. Only Corpus B can be E0 evidence.
- **Matching is greedy with a *total* sort order, and the greedy-vs-optimal gap is measured rather than argued away.** `(-J, reference_block_id, proposal_index)` makes the ordering total so the pairing is byte-reproducible. Hungarian would be optimal but drags in scipy/numpy against the zero-dependency constraint; at these sizes, where most true matches are `J = 1.0`, greedy and optimal coincide — and a unit test asserts exactly that on small synthetic cases, plus a runtime warning on any J-tie.
- **Blocks are the unit of *n*, not nodes and not canvases.** SC1 says "blocks", the architect accepts or redraws blocks, and per-node counting actively rewards FM-4 over-segmentation. `M5` (segmentation ratio, fragmentation, fusion) exists specifically to catch the over-segmentation and catch-all failures a per-node metric would score well.
- **This plan writes scoring and corpus loading only.** Cassette record/replay, the arm definitions, the report emitter and the pytest driver are 35-13. Splitting them lets scoring land and be tested while the orchestrator (35-12) is still in flight.
- **`recognition_eval` lives under `tests/` as a test-only package**, not in the service root — it must never be importable by production code. AI-SPEC §5 Eval Tooling puts it at `data-service/tests/recognition_eval/`.
</plan_decisions>
