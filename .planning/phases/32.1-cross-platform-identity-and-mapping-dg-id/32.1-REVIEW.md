# Phase 32.1: Code Review Report

**Reviewed:** 2026-07-27
**Depth:** deep
**Files Reviewed:** 27
**Status:** issues_found

## Summary

The cross-language hash parity contract (`DgIdMintingService.Mint` in C# vs. `compute_dg_id` in Python) is byte-identical and independently verified in this review: I recomputed `SHA-256("p1|frame.gh|cg:1:proc:11_Proc")`, uppercased, first 16 hex chars, and it matches the golden vector `dg:BC8E62EE137E2B56` asserted by both `DgIdMintingServiceTests.Mint_KnownVector_MatchesExpectedDgId` and `test_dg_identity.py::test_compute_dg_id_matches_dotnet_golden_vector`. DTO round-tripping of `dgId` through `ComputgraphContextSerializer` and `DesignStatePayloadV2Serializer` is also correct and symmetric.

However, tracing the identity model across `dg_identity.py`, `computgraph_publish.py`, and `spec/DG-ID.md` surfaces a real, load-bearing defect: the pre-mint registry anchor (`mint_identity`) and the Phase 36 publish path use **structurally incompatible** MERGE patterns (label-less vs. labeled), which `computgraph_publish.py`'s own module docstring acknowledges but does not resolve — it just avoids the collision by never touching the registry anchor, silently orphaning any bindings made against a pre-minted dgId. This directly contradicts the "normative for Phase 36" constraint documented in `spec/DG-ID.md`. Separately, neither language's minting function escapes or rejects the `|` delimiter inside `project`/`definitionId`/`cgId`, which undermines the very cross-project collision-prevention guarantee the hash-folding design is built to provide. Several schema-propagation documents (Plan 07's sweep) also drifted from the implemented API surface.

## Critical Issues

### CR-01: Pre-minted identity registry node never coincides with the published Computgraph node — silently orphans bindings

**File:** `data-service/dg_identity.py:166-190` (mint_identity), `data-service/computgraph_publish.py:1-19,301-317,360-368` (publish MERGE), `spec/DG-ID.md:55-64` (normative Phase 36 constraint)

**Issue:** `dg_identity.mint_identity` anchors its registry node with a **label-less** MERGE:
```cypher
MERGE (e {cgId: $cgId, definitionId: $definitionId, project: $project})
SET e.dgId = $dgId
```
`spec/DG-ID.md` explicitly declares this the "Phase 36 constraint (normative)": a pre-minted node created via `/identity/mint` "ahead of a full publish" and the node later written by `POST /computgraph/publish` must "coincide as ONE node, never duplicate."

But `computgraph_publish.py` MERGEs with an explicit label for every entity, e.g.:
```cypher
MERGE (o:Object {cgId: $cgId, definitionId: $definitionId, project: $project})
```
(equivalently `:Procedure`, `:Pattern`, `:Parameter`, `:Interface`). Neo4j `MERGE` pattern matching requires **all** labels in the pattern to be present on the candidate node. A label-less node created by `mint_identity` does **not** satisfy `(o:Object {...})`, so this MERGE does not find it — it creates a **second, distinct** node with the `Object` label and the identical `dgId` string (recomputed independently via the pure `compute_dg_id` function). The original label-less anchor is left behind, permanently orphaned, still carrying whatever `HAS_REPRESENTATION`/`HAS_SHARED_PROPERTY` edges were attached to it via `/identity/bind` or `/identity/{dgId}/properties` before publish ran.

`computgraph_publish.py`'s own module docstring (lines 8-19) **already documents this exact failure mode** ("a later `MERGE (n:Pattern {...})` from this module would never coincide with that anchor and would create a duplicate, orphaned node") and works around it by never calling the registry's persistence helper from the publish path at all — but this only prevents publish from *crashing into* the anchor; it does nothing to prevent the anchor from being orphaned when a caller follows the exact workflow the spec calls out as intended ("pre-minted registry node created via `/identity/mint` ahead of a full publish").

Net effect: any consumer (e.g. a Grasshopper session that mints a dgId and binds a native id or writes a shared property **before** the canvas is published) permanently loses that binding/property once publish runs — the published `:Object`/`:Procedure`/etc. node has zero `HAS_REPRESENTATION`/`HAS_SHARED_PROPERTY` edges, and the node that does have them is an untyped, unreachable-by-label orphan. This is exactly the "duplicate, orphan the pre-minted dgId" failure the spec's normative section says must not happen.

**Fix:** Pick one of:
1. Make `mint_identity`'s anchor MERGE match the *actual* entity label used by publish (requires knowing the entity kind up front — awkward, since `/identity/mint` is currently kind-agnostic), or
2. Have `computgraph_publish.py` explicitly reconcile with the label-less anchor on first write (e.g. `MATCH (e {cgId:$cgId, definitionId:$definitionId, project:$project}) WHERE NOT e:Object SET e:Object` before/instead of a fresh `MERGE (o:Object {...})`, then continue writing properties onto `e`), or
3. Document and enforce (with an integration test) that `/identity/mint` must never be called before `/computgraph/publish` for the same triple — and reject/no-op `/identity/mint` calls for triples that don't yet have a published entity, until publish has run. Whichever direction is chosen, add a regression test that mints, binds a representation, publishes, and then asserts the published entity (not an orphan) still carries the binding.

### CR-02: `dgId` hash input has no delimiter escaping — distinct `(project, definitionId, cgId)` triples can collide

**File:** `DG/src/DG.Core/Models/Identity/DgIdMintingService.cs:41` (`var input = $"{project}|{definitionId}|{cgId}";`), `data-service/dg_identity.py:61` (`input_str = f"{project}|{definition_id}|{cg_id}"`)

**Issue:** Both implementations concatenate the three fields with a literal, unescaped `|` delimiter and validate only that each field is non-empty/non-whitespace (`ArgumentException` in C#, no check at all in Python). Neither implementation rejects or escapes a `|` character occurring **inside** any of the three fields. Because there is no way to unambiguously recover the field boundaries from the joined string, two semantically distinct triples that shift a `|` across a field boundary hash to the **identical** input string and therefore the **identical** `dgId`. Concretely:
```
project="a|b", definitionId="c",   cgId="d"   -> "a|b|c|d"
project="a",   definitionId="b|c", cgId="d"   -> "a|b|c|d"   (same hash input, same dgId)
```
`cgId` values are partially derived from user-authored Grasshopper group/component nicknames (Phase 32's convention-name grammar), and `project` is an externally supplied string (e.g. via the `/identity/mint` request body or query params) — neither is guaranteed pipe-free. This directly undermines the documented purpose of folding `project` into the hash (`spec/DG-ID.md` "Collision Policy": "This applies the lesson of the shipped v2.0/v3.0 `Var` cross-project merge-key collision bug... folding `project` into the hash *and* scoping every query is the more defensive of the two precedents") — the fold itself is ambiguous at the exact class of boundary it was introduced to close.

**Fix:** Either reject any field containing `|` (fail fast with a clear `ArgumentException`/`ValueError`) in both `Mint`/`compute_dg_id`, or switch to an unambiguous encoding that can't collide across field boundaries, e.g. length-prefixing each field (`f"{len(project)}:{project}|{len(definitionId)}:{definitionId}|{len(cgId)}:{cgId}"`) or hashing each field independently and concatenating the digests before the final hash. Whichever fix is chosen, it must be applied **identically** in both `DgIdMintingService.Mint` and `compute_dg_id` (the golden vector will need updating in lockstep in both test suites), and a cross-boundary-collision test should be added to both suites to prevent regression.

## Warnings

### WR-01: `mint_identity`'s anchor node never gets the `graph:'Computgraph'` partition tag

**File:** `data-service/dg_identity.py:176-189`
**Issue:** Every other node this phase writes (`Representation` via `bind_representation`'s `ON CREATE SET r.graph = 'Computgraph'`, `SharedProperty` via `write_shared_property`'s `ON CREATE SET sp.graph = 'Computgraph'`, and every Phase 36 publish node) carries `graph: 'Computgraph'`, per the codebase-wide partition convention (`spec/DATABASE.md`: "all under `graph:'Computgraph'`"). `mint_identity`'s own anchor MERGE never sets this property. Combined with CR-01, this means the orphaned anchor is also invisible to any partition-scoped query, e.g. `computgraph_publish.py`'s `_find_stale_entities` (`MATCH (n {definitionId: $definitionId, project: $project, graph: 'Computgraph'})`) — so even a future generic "clean up stale/orphaned Computgraph nodes" pass will never find it.
**Fix:** Add `SET e.graph = 'Computgraph'` alongside `SET e.dgId = $dgId` in `mint_identity`'s Cypher.

### WR-02: `spec/DATABASE.md` documents a route that doesn't exist and the wrong HTTP verb for an existing one

**File:** `spec/DATABASE.md:336`
**Issue:** The Representation node section states: "Written only by the data-service identity API (`PATCH /identity/bind`, `POST /identity/{dgId}/representations`)". Neither route exists as written: the actual binding route is `POST /identity/bind` (not `PATCH`), and there is no `POST /identity/{dgId}/representations` route at all — the implemented routes under that path are `GET /identity/{dg_id}/representations` (list) and `DELETE /identity/{dg_id}/representations` (detach). `cypher_template.txt:71-72` documents the correct set (`/identity/mint, /identity/bind, /identity/{dgId}/properties`). This is exactly the kind of schema-propagation drift the task asked to check for — one of the seven propagation targets (`spec/DATABASE.md`) disagrees with both the implemented code (`data-service/app.py:1539,1564,1571`) and with a sibling propagation target (`cypher_template.txt`).
**Fix:** Correct line 336 to read `POST /identity/bind` for creation and `GET`/`DELETE /identity/{dgId}/representations` for read/detach.

### WR-03: `ALLOWED_PROPERTIES` allow-list is dead code and is itself incomplete

**File:** `data-service/dg_context.py:546-559`
**Issue:** This set (added by this phase's Plan 07 propagation sweep) is documented as "properties... that the validator must recognize to avoid false-positive unknown-property rejections on generated Cypher touching the identity registry." But `validate_cypher` (same file, `~line 661`) never references `ALLOWED_PROPERTIES` anywhere — it only checks `_extract_labels(...) - ALLOWED_LABELS` and `_extract_relationships(...) - ALLOWED_RELATIONSHIPS`; there is no property-name extraction/validation step in the function at all. `ALLOWED_PROPERTIES` is therefore unused dead code whose docstring overstates what the validator actually does. It is also incomplete relative to the schema it claims to cover: `SharedProperty.value` (documented in `spec/DG-ID.md` and `spec/DATABASE.md`) is missing from the set.
**Fix:** Either wire a property-name check into `validate_cypher` using this set (and add `"value"`), or remove the unused constant and its misleading comment if property-level validation isn't actually in scope for this phase.

### WR-04: `definitionId` in `spec/DG-ID.md`'s worked examples and test fixtures is ambiguous about which GH field it maps to

**File:** `spec/DG-ID.md:38` (hash input contract), `DG/src/DG.Core/Services/CgContextDgIdAssigner.cs:37` (`context.Definition.DocumentId`), `DG/tests/DG.Tests/Identity/DgIdMintingServiceTests.cs:13` (`DefinitionId = "frame.gh"`)
**Issue:** Production code (`CgContextDgIdAssigner`, `computgraph_publish.py`'s `definition.get("documentId")`) always uses `Definition.DocumentId` (a GUID) as the `definitionId` hash input — never `Definition.FileName` (e.g. `"frame.gh"`). But the golden-vector tests and `spec/DG-ID.md`'s narrative both use the literal string `"frame.gh"` as the example `definitionId` value, which reads as if `FileName` were the intended field. This is harmless for the hash itself (`Mint`/`compute_dg_id` treat `definitionId` as an opaque string, so the golden vector is still valid as a test fixture), but it is a documentation-clarity gap that could mislead a future implementer (e.g. a Revit connector author) into hashing the wrong field, silently producing a `dgId` that never matches the one actually stored in Neo4j for the same logical definition.
**Fix:** Update `spec/DG-ID.md`'s example/vector description to state explicitly that `definitionId` = `Definition.DocumentId` (the GH document GUID), not `FileName`, and note that the test literal `"frame.gh"` is an arbitrary opaque string chosen for readability, not a realistic `DocumentId` value.

## Info

### IN-01: Unused exception variable in `get_identity_properties`

**File:** `data-service/app.py:1622` (`except dg_identity.DgIdentityError as exc:`)
**Issue:** `exc` is bound but never read in the except block (`raise _dgid_not_found_error(dg_id)` doesn't use it), unlike the sibling handler in `post_identity_bind` which does use `exc.code`/`exc.existing_dg_id`. Harmless, but inconsistent with the pattern used elsewhere and will trip linters configured to flag unused bindings.
**Fix:** `except dg_identity.DgIdentityError:` (drop the `as exc`).

### IN-02: `bind_representation` silently no-ops metadata updates on an idempotent re-bind to the same dgId

**File:** `data-service/dg_identity.py:254-263`
**Issue:** `MERGE (r:Representation {nativeId, platform, project}) ON CREATE SET r.nativeIdKind = ..., r.connector = ..., r.boundAt = ...` only writes these fields when the Representation node is newly created. If a caller re-binds the same `(nativeId, platform, project)` to the same `dgId` intending to update `connector` (e.g. a connector version bump) or correct `nativeIdKind`, the call succeeds (200) but silently leaves the stale metadata in place — there's no indication to the caller that their new `connector`/`nativeIdKind` values were discarded.
**Fix:** If re-bind-with-updated-metadata is a supported use case, change `ON CREATE SET` to a plain `SET` (or add an explicit `ON MATCH SET` clause); if immutability is intentional, document it in `spec/DG-ID.md`'s Binding Model section alongside the existing "attach/detach never rewrite dgId" note.
