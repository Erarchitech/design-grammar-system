<objective>
Close `1202-VERIFICATION.md` gap 1 (REVIEW **CR-01**, Critical): `BuildPerObjectVerdicts`
silently collapses two evidence rows that share one `(ruleId, objectId)` pair into a single
rolled-up verdict, with no caller-visible signal — contradicting
`spec/EVIDENCE-CONTRACT.md` §4's rule that rows are identity-addressed by that pair and are
"never merged, collided, or deduplicated on value equality alone," and contradicting
ALGN12-10's own wording that mixed per-object outcomes "remain distinct through persistence
and C# retrieval."

Purpose: the canonical C# read path the Grasshopper canvas consumes
(`GetPerObjectVerdictsAsync`) is today strictly less honest than the Python leg for the same
bytes. `tools/de01/report.py`'s `compare_legs` keeps every row per pair on purpose
(`_rows_by_pair`, never deduplicating, with the multi-row ObjectPropertyAtom case documented
at `report.py:119-121`). The C# side folds the same data into one verdict and reports nothing.
This plan gives C# the equivalent safeguard.

Output: an additive, typed, caller-inspectable duplicate-identity signal on the existing
verdict result types; a `(RuleId, ObjectId)`-first grouping inside `BuildPerObjectVerdicts`
that feeds both the signal and the unchanged rollup; extended unit Facts pinning both the
preserved cross-rule behavior and the new duplicate-pair behavior; and the matching
`spec/EVIDENCE-CONTRACT.md` §5.1 propagation.
</objective>

<design_decision>
## CR-01 fix option: **(a) with an additive flag — NOT a new `VerdictSource` member**

The review offers (a) detect-and-surface or (b) document-the-boundary. This plan takes **(a)**,
and within (a) chooses an **additive property on the existing result types** over a third
`VerdictSource` enum member. Stated reasoning, since this is the plan's load-bearing call:

**Why (a) and not (b)-alone.** D-11's governing philosophy for this exact phase is "typed
absence, never fabrication." A duplicate-pair collapse is *fabrication*: it reports one verdict
as though one row produced it. Documentation alone (option b) leaves the runtime behavior
fabricating and leaves the canvas consumer with no way to know. The review itself frames both
CRs as BLOCKER-class precisely because they "produce a wrong, silently-accepted verdict rather
than a typed absence or a loud failure." Option (b)'s documentation duty is still discharged
here (Task 2 rewrites the doc-comment), but as an addition to (a), not instead of it.

**Why a flag and not a new `VerdictSource` member.** `VerdictSource` answers *where did this
verdict come from* — its doc-comment at `IValidGraphRepository.cs:37-40` says the evidence
envelope is "the only canonical source (D-10)" and `Absent` "marks the degrade case when no
envelope could be read (D-11)." A duplicate-pair row set is **still sourced from the evidence
envelope**; nothing about its provenance changed. A third member such as
`EvidenceEnvelopeWithDuplicates` would:
1. break the invariant that `Source == EvidenceEnvelope` ⟺ the envelope was readable, which
   callers can rely on today, so every existing `switch`/comparison silently mis-handles the
   new case;
2. be a change to the D-10/D-11 provenance vocabulary that `spec/EVIDENCE-CONTRACT.md` §5.1
   governs, dragging in the full CLAUDE.md Schema Change Propagation sweep for a data-quality
   signal that is not a status and not a provenance;
3. conflate two orthogonal axes (provenance × integrity) into one enum, which is the same
   drift class this milestone exists to remove.

An additive boolean/collection is **additive-not-breaking** (1200 D-03, this repo's house
style, and the pattern 1202 already used for `GetPerObjectVerdictsAsync` itself under D-13).
Existing callers compile and behave identically; new callers opt in.

**Blast radius, verified on disk.** `VerdictSource`, `PerObjectVerdict`, and
`PerObjectVerdictResult` have exactly three consuming sites in the repo:
`IValidGraphRepository.cs` (definition), `Neo4jValidGraphRepository.cs` (sole producer), and
`Neo4jValidGraphRepositoryTests.cs` (tests). There is no canvas component consuming
`GetPerObjectVerdictsAsync` yet, so an additive property costs nothing downstream today and
is available the moment one is wired.

**Why flag-and-continue, not degrade and not throw.** D-11's contract for this function is
degrade-not-throw for *malformed* input. A duplicate-pair envelope is **not malformed** — it
parses, it has valid rows, every row has a valid canonical status. Degrading it to
`EnvelopePresent = false` would throw away real, correct verdicts for every other object in
the run and would be indistinguishable from a pre-1200 run (D-11's own reserved meaning).
Throwing would break the canvas read path. The condition therefore **flags**: the verdict list
is returned complete and usable, with the collision reported alongside it.

**Spec propagation.** `spec/EVIDENCE-CONTRACT.md` §4 already states the row-identity rule;
this plan does not change it. §5.1 (the canonical per-object verdict source, Phase 1202 plan
05, D-10) is where the C# read path's behavior is described and is therefore where the
detection behavior belongs — §4 and §5.1 currently read as contradictory at this boundary, and
Task 3 reconciles them. No status is added, renamed, or reinterpreted, and no envelope field
changes, so the EVIDENCE-CONTRACT governance rule is satisfied by a scoped §5.1 addition;
`spec/DATABASE.md` needs **no** change because the stored `evidenceEnvelopeJson` shape is
untouched (this is a reader-side behavior, and `spec/DATABASE.md:158` explicitly delegates the
property's content authority to `spec/EVIDENCE-CONTRACT.md`).
</design_decision>
