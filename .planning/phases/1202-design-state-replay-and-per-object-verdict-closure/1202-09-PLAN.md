<objective>
Close VERIFICATION.md gap 2 by claiming ALGN12-09's own escape hatch: write the `parameters[]`
dual-wire-shape divergence into the spec surfaces as an **explicit exclusion contract**.

Purpose: plan 1202-03's mandated parity proof found a real, currently-shipping collision — the
Python accept-candidate writer (`data-service/cg_paramstate_store.py`) emits a flat
`numberValue`/`integerValue`/`booleanValue` shape that only the inline C# reader parses correctly,
while `DesignStatePayloadV2Serializer.Deserialize` expects its own condensed `{type, value}` shape
and the inline reader **silently mis-parses** that one (returns null values, no exception).
Converging the readers as D-09 literally instructs would have silently dropped typed parameter
values for every already-stored accept-candidate-writer payload.

**The halt was correct engineering judgment, not a defect.** This plan does not reverse it and does
not frame it as a bug. What is missing is only the paperwork: the divergence lives in
`1202-03-SUMMARY.md` prose and two xUnit Fact names, and was never propagated into
`spec/DATABASE.md` or `spec/EVIDENCE-CONTRACT.md` — verified on disk, where grepping every
divergence term (`dual-wire`, `wire shape`, `numberValue`, `TryParseDesignState`,
`cg_paramstate_store`) across both spec files returns **zero hits**. Plan 1202-05 propagated every
OTHER declared exclusion (geometry D-06, legacy-run `not_evaluated` D-11, immutable/mutable D-15)
into exactly these files, so the pattern is already established in-repo.

Output: the exclusion-contract entry, its cross-reference, and code comments pointing at it. **No
reader changes. No behavior changes. No migration.**
</objective>

<disposition_decision>
## Why the exclusion-contract branch, not one of 1202-03's three disposition options

`1202-03-SUMMARY.md` offers three dispositions. This plan takes the third (documented exclusion),
deliberately:

1. **Extend the serializer to accept both shapes** — plausible and the SUMMARY's own favorite
   ("likely the lowest-blast-radius"), but it is a *reader behavior change* on a path that parses
   already-stored production payloads. Getting it subtly wrong silently changes what a stored
   payload means, which is the exact failure mode the halt existed to prevent. It also does not
   itself satisfy the gap: the gap's `missing:` entry asks for a written contract **or** a
   resolution, and a resolution still leaves the two-shape reality undocumented for the payloads
   already in Neo4j.
2. **Change the Python writer to emit the condensed shape** — strictly worse here. It creates a
   *third* population (old flat rows, new condensed rows) and needs a migration or a
   dual-shape reader anyway, plus it touches a live write path outside this gap's scope.
3. **Document the exclusion** — chosen. Zero risk to stored data, satisfies the ROADMAP's own
   "or an explicit exclusion contract" wording verbatim, and matches the in-repo pattern plan 05
   established for every other exclusion this phase declared.

**This is not a one-way door and needs no `checkpoint:decision`.** It changes no code behavior and
no reader authority — it *records* the authority that already exists in the shipped code. Full
reader convergence (option 1) remains available to any later phase, and this plan's own text names
what would force it. Had this plan instead changed which reader is authoritative for stored data,
that would be one-way and would require a blocking decision checkpoint first.
</disposition_decision>

<assumption_delta_decision>
**Seam:** "one reader for the v2 payload" (singular, as D-09 assumed) is actually "two readers,
each authoritative for a different producer" (plural).

**Decision:** `add-alongside` — accepted debt. The two readers remain split, and the split is
promoted from undocumented accident to declared contract. Both directions stay pinned by the two
existing regression Facts.

**What would force a later `promote` (full convergence to one reader):**
- a third producer of v2 `parameters[]` appearing, since three shapes with two readers is no longer
  describable as a two-way exclusion; or
- any consumer needing to read *both* producers' payloads through a single code path (today each
  reader is reached only by its own producer's rows); or
- a v3 payload version, which would have to pick one shape and migrate the other, making the
  exclusion moot.

**Cost of the debt if left:** a future author who reads only the serializer will believe the
condensed shape is the only v2 parameter shape. The spec entry and the two code comments this plan
adds are the mitigation; the two regression Facts are the tripwire.
</assumption_delta_decision>
