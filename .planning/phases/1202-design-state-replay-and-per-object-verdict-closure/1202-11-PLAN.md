<objective>
Close `1202-VERIFICATION.md` gap 2 (REVIEW **CR-02**, Critical): `ObjectStateComponent.SolveInstance`
hard-errors on a Label-vs-Geometry list-length mismatch but has **no equivalent guard for
Object vs Geometry**. The only Object-side handling is
`var perItemObject = i < objects.Count ? objects[i] : null;` — which silently degrades every
geometry index past the wired Object list's end: `ResolveInstanceRef(null)` returns null,
`classIri` falls to null (because `broadcastClassIri` is also null whenever `objects.Count != 1`),
and `ObjectRef` drops to the `GeometryReferenceId` / `$"obj_{i}"` fallback.

Purpose: those tail ObjStates get plausible-looking `OS_`-prefixed 16-hex ids from
`DesignStateIdGenerator.ComputeObjectStateIdFromRef` that are **missing information the user
actually supplied**, with zero canvas diagnostic — in the very component whose doc-comment
promises "Each ObjState gets a UNIQUE ObjectRef" and that the ontology class IRI is extracted.
The identical shape of bug (a list-length mismatch on a broadcast component) is already fatal
for Label. ALGN12-08's classification taxonomy is fully verified; this is its "stable per-object
identity" half.

Output: a pure, SDK-independent length-guard predicate in `DG.Core`; a dedicated Object-side
error template; the guard wired into `SolveInstance` mirroring the Label guard; and unit Facts
pinning the predicate's exempt cases and the new message's wording.
</objective>

<design_decision>
## A dedicated error template is required — reuse is NOT acceptable here

The review left this open ("or a dedicated template"); the planning context required it to be
decided on evidence rather than assumed. **Verified on disk** at
`DG/src/DG.Core/Services/ErrorMessageTemplates.cs:53-56`, the existing template reads:

> `OBJECT STATE: Geometry list length ({geometryCount}) and Label list length ({labelCount}) must
> be equal at every index. Ensure each index provides both values.`

The word **Label** is hardcoded in the message body, and its second parameter is literally named
`labelCount`. Passing `objCount` into it would tell a user on the canvas that their **Label**
input is mis-wired when their **Object** input is the one at fault — actively misleading in a
component that has two separately-wireable list inputs and two separate failure modes. Reuse is
therefore rejected; a dedicated template naming the Object input is required.

The existing template is also pinned by a Fact in `ErrorMessageTemplateTests.cs`, so rewording
it in place (the alternative to adding one) would break an existing test *and* change the
Label-path message that has shipped — both forbidden by this plan's prohibitions.

## Testability: the guard predicate moves to DG.Core

`ObjectStateComponent.cs` is entirely inside `#if GRASSHOPPER_SDK`, and that constant is only
defined when `DG.Grasshopper.csproj` finds `RhinoCommon.dll`, `Grasshopper.dll`, and `GH_IO.dll`
under the Rhino install dir. `DG.Tests` targets `net9.0` and references **only** `DG.Core`;
`DG.Grasshopper` targets `net7.0-windows`. The component's `SolveInstance` therefore **cannot**
be unit-tested from `DG.Tests` — stating that plainly, as the planning context required.

What IS verifiable, and what this plan commits to:
1. **The guard predicate**, factored into `DG.Core` as a pure function over two integers, is
   fully unit-testable — every exempt and non-exempt case is a `DG.Tests` Fact.
2. **The error message text**, since `ErrorMessageTemplates` already lives in `DG.Core` and
   already has a dedicated test file.
3. **`dotnet build DG/DG.sln -c Release`** compiling the Grasshopper project (on a machine with
   Rhino 8 installed, which is where the plugin is built per CLAUDE.md's Common Commands), which
   proves the guard's call site type-checks inside the `GRASSHOPPER_SDK` branch.
4. **A targeted grep** proving the component calls the shared predicate rather than re-expressing
   the condition inline.

What is NOT claimed: no acceptance criterion in this plan asserts runtime Grasshopper canvas
behavior, because nothing in this repo can execute it headlessly. The canvas-level confirmation
is left to the human who rebuilds and loads the plugin; it is recorded as an optional
`<human-check>` in Task 3's verify, not as a blocking automated gate.
</design_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Grasshopper canvas wiring → `SolveInstance` inputs | User-supplied lists of arbitrary length crossing into identity minting |
| `SolveInstance` output → persisted `:DesignState` / `ObjState` identity | A minted `OS_` id that will be stored and later replayed as an authoritative identity |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1202-11-01 | Spoofing | `ObjState.ObjectRef` / `StateId` | high | mitigate | An unguarded length mismatch mints `OS_`-prefixed ids from a fallback `obj_{i}` ref with `ClassIri = null` — an identity that looks well-formed but does not correspond to the object the user designated. Task 2's guard refuses to emit rather than minting a spoofed-looking identity. |
| T-1202-11-02 | Tampering | persisted Design State identity | high | mitigate | Those degraded identities persist into `:DesignState` and are replayed by this milestone's own replay contract, so a wiring slip silently corrupts downstream replay. Erroring at the source prevents the corrupt row from ever being written. |
| T-1202-11-03 | Repudiation | canvas diagnostics | medium | mitigate | Today the degrade is entirely silent — no `AddRuntimeMessage`, so no record that a mismatch occurred. The new Error message makes the condition attributable at the moment it happens. |
| T-1202-11-04 | Denial of Service | OBJECT STATE component | low | accept | The guard converts a silent-partial-success into a hard stop, which could surprise a user relying on the tail-degrade behavior. Accepted: the Label input already behaves this way, the degraded output was never correct, and the message states the three legal wirings. |
| T-1202-11-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager install occurs in this plan — all three tasks edit existing C# source and existing test files. No new dependency is added, so the package legitimacy gate has nothing to audit. |
</threat_model>
