## 1. Reference product — Ant (rhino-ant.ai)

The user's stated analogy. Confirmed behaviours:

| Aspect | Ant's approach |
|---|---|
| Entry point | An **Ant widget** on the canvas; chat opens on click **or `Shift+Shift`** |
| Chat surface | Built-in **dockable** chat window, light/dark modes — stays inside Grasshopper |
| Context | **Selection-based**: single component, a group, or the whole definition. Reads component input names, data types, list/item access patterns |
| Serialization | "Translates the actual logic of your components and wires into a structured format the LLM can understand" |
| Modes | **Ask** (explain/debug/plan), **Edit** (build/modify components from NL), **Script** (generate Python/C# into script components) |
| Proposals | Edit/Script mode **creates real components on the canvas** rather than returning opaque text |
| Slash commands | Only `/feedback` documented — **no full slash-command system**. This is where DG differentiates. |
| Model choice | **No documented BYO-API-key or user-facing model selection** — another DG differentiator (the platform's LLM gateway already does this) |

**Implication for DG:** the shape (canvas widget → dockable chat → selection as context → on-canvas proposals) is validated by a shipping product. DG's differentiators are (a) an explicit `/dg-` slash-command namespace mapped to deterministic tool calls, and (b) a visible, user-chosen LLM from the platform.

## 2. UI hosting inside Grasshopper

### Options

| Option | Verdict |
|---|---|
| **Eto.Forms** modeless `Form` | McNeel's recommended path (Rhino 7/8, cross-platform Win+Mac). `Eto.Forms.Form` = modeless, `Dialog` = modal. Sample: `SampleEtoModelessForm.py`. |
| **Rhino docked panel** — `Rhino.UI.Panels.RegisterPanel(plugIn, type, caption, icon, PanelType)` | Registered at plugin `OnLoad`; opened via `Panels.OpenPanel(typeof(T).GUID)`. Gives true docking (what Ant has). Panel content derives from `Eto.Forms.Control`. |
| **WinForms / WPF** | Works, Windows-only. Rhino 8 guidance is to prefer Eto. |
| **WebView** (`Eto.Forms.WebView`) | Can host a full React/Vue frontend from `http://localhost:port` or local files. Path to reusing `ui-v2/` design tokens/components. |

### Attaching a window to a GH component

Standard pattern — override `GH_ComponentAttributes.RespondToMouseDoubleClick`:

```csharp
class ChatComponentAttributes : GH_ComponentAttributes
{
    public ChatComponentAttributes(IGH_Component owner) : base(owner) { }

    public override GH_ObjectResponse RespondToMouseDoubleClick(
        GH_Canvas sender, GH_CanvasMouseEvent e)
    {
        if (ContentBox.Contains(e.CanvasLocation))
        {
            (Owner as ChatComponent)?.ShowChatWindow();
            return GH_ObjectResponse.Handled;
        }
        return GH_ObjectResponse.Ignore;
    }
}

public class ChatComponent : GH_Component
{
    public override void CreateAttributes() => m_attributes = new ChatComponentAttributes(this);
    public void ShowChatWindow() { /* open Eto form or Panels.OpenPanel(...) */ }
}
```

Alternative/additional triggers: `AppendMenuItems` context-menu entry; a custom grip drawn in the attributes.

**Panel ↔ component communication** should go via a plugin singleton or shared service class, **not** direct object references — avoids lifetime issues when either side is disposed.

### Threading rules (hard constraints)

- Rhino/GH have a **single UI thread**. Updating Eto/Rhino UI from a background thread crashes Rhino on macOS (`Modifications to the layout engine must not be performed from a background thread...`).
- Marshal back with **`RhinoApp.InvokeOnUiThread(Delegate, params object[])`**.
- **Never block `SolveInstance` on an LLM/network call** — it stalls the whole Grasshopper solution loop and can freeze Rhino if the call hangs. RhinoMCP explicitly advertises "non-blocking communication via HTTP server" for this reason.
- Correct async shape:
  1. double-click → open modeless UI on the UI thread
  2. chat posts to an async service (`Task.Run` / HTTP client)
  3. on completion → `RhinoApp.InvokeOnUiThread` to update chat UI / mutate canvas
  4. `SolveInstance` stays fast and side-effect-free, only reading shared state

> **DG note:** this is exactly the shape `CanvasListenerComponent` already uses (`InvokeOnCanvas` / `InvokeOnCanvasWrite` + `TaskCompletionSource`, per Phase 33/35 decisions). The chat panel reuses that marshalling layer rather than inventing one.

## 3. Auto-start / always-listening (replacing the `Run` toggle)

### Lifecycle hooks

`IGH_DocumentObject` exposes `AddedToDocument`, `RemovedFromDocument`, `DocumentContextChanged`, `MovedBetweenDocuments`.
`GH_Document` exposes `ContextChanged`, `ObjectsAdded`, `ObjectsDeleted`, `SolutionStart`, `SolutionEnd`.

Recommended wiring:

```csharp
public override void AddedToDocument(GH_Document doc)
{
    base.AddedToDocument(doc);
    if (!Service.IsRunning) Service.Start(port);   // singleton
    doc.ContextChanged += OnDocumentContextChanged;
}

public override void RemovedFromDocument(GH_Document doc)
{
    base.RemovedFromDocument(doc);
    doc.ContextChanged -= OnDocumentContextChanged;
    // stop service if no components remain
}

private void OnDocumentContextChanged(object s, GH_DocumentContextChangedEventArgs e)
{
    if (e.Context == GH_DocumentContext.Unloaded) Service.MarkDocumentClosed(doc);
}
```

### Pitfalls (the price of dropping the `Run` toggle)

1. **Multiple instances race to bind the same port.** With a `Run` toggle the user serialises this by hand; on auto-start they don't. Needs a **singleton service + explicit already-running guard**, and the second component must degrade to "attached to existing listener", not error.
2. **Port conflicts.** RhinoMCP's own troubleshooting is dominated by "ensure ports are available". Auto-start needs port fallback/scan or a clear, non-fatal status.
3. **Status must be surfaced without a `Run` input.** RhinoMCP keeps a `Status` output and shows state in the panel; DG should show it in the **chat header** (as the user requested) *and* keep a component-level indicator.
4. **Don't do heavy work in GH event handlers.** `SolutionStart`/`SolutionEnd` and object events fire constantly — use them to set a dirty flag only; defer real work.
5. **Old canvases.** Auto-start changes the component contract; a `.gh` saved with the old `Run`/`Port` inputs is affected (see §6).

## 4. Canvas selection as LLM context

How the field does it (Ant, grasshopper-mcp, RhinoMCP):

- Traverse the GH document object graph — components, params, groups, wires — and emit **JSON** describing components, their inputs/outputs, and current values.
- `GH_Document.SelectedObjects()` is the selection source; group membership and wire adjacency give the structure.
- **grasshopper-mcp** (`alfredatnycu/grasshopper-mcp`): `GH_MCP.gha` runs a TCP server; a Python MCP bridge maps NL to deterministic component operations using a "component knowledge base" + "component patterns and intents".
- **RhinoMCP** (`rhino-gh-mcp`): Python MCP server + Rhino socket server (:9876) + GH HTTP server (:9999). Exposes "canvas inspection" (component graph + parameters) and "component management".
- **Proposal preview:** create the proposed components/groups on canvas, clearly labelled/grouped, and only commit on explicit user confirmation. Ant does this via Edit/Script mode placing real components.

> **DG note:** DG already has this end-to-end — `RawCanvas` → `CanvasAnnotationParser` → `ComputgraphContextSerializer` → `cgContextJson v1`, plus `PreviewRegistry` + temporary preview groups from Phase 35. v9.1 does **not** rebuild canvas serialization; it re-fronts it with a chat UI.

## 5. Slash-command design

### Discovery / autocomplete UX

- **Slack** — typing `/` opens a shortcuts menu; filter by typing; menu shows required arguments and formatting hints.
- **Cursor** — custom commands stored as `.cursor/commands/<name>.md`; typing `/` in the agent input opens a dropdown.
- **Claude Code** — commands from `.claude/commands/*.md`; a VS Code extension surfaces them through the Command Palette.
- **Discord** — fully structured options schema (`type`, `name`, `description`, `required`, `choices`) driving rich autocomplete and argument hints.

### Grammar rules worth copying

- **Verb-noun-target**: `/deploy <service> <env> [--dry-run]`, `/scale <service> <replicas>`.
- **Positional args for essentials, flags for options**: `/logs <service> [--since=10m]`.
- **Built-in help**: every command responds usefully to no args or `help`.
- **Namespacing by prefix** for multi-domain tools — which is exactly the user's `/dg-` requirement.

### Commands must be deterministic, not generative

The consensus pattern: if input starts with `/`, route to a **registered handler**, not the LLM.

```csharp
if (input.StartsWith("/"))
{
    var cmd = ParseCommand(input);
    var def = CommandRegistry.Lookup(cmd.Name);
    if (def == null) { ShowMessage("Unknown command. Type /dg-help."); return; }
    var result = def.Handler(cmd.Args, ghContext);   // deterministic, no LLM
    RenderResult(result);
}
else SendToLlm(input, ghContextSnapshot);
```

A structured command schema (Discord-style) lets you validate arguments *before* execution and drive autocomplete from the same source.

### Risk classification + confirmation + undo

| Risk | Examples | Treatment |
|---|---|---|
| Safe (read-only) | `/dg-status`, `/dg-explain` | run immediately |
| Caution (preview only) | `/dg-recognize` | create a preview group only, nothing persisted |
| Destructive / outward-facing | `/dg-confirm`, `/dg-publish` | summarise the change ("will create 5 groups, publish 32 entities"), require explicit Apply/Cancel, expose undo |

Slack's ChatOps guidance: destructive commands never execute directly — post a confirmation with explicit consequences first. Store each applied change set as a reversible operation for `/dg-undo`.

> **DG note:** GH has native undo (`GH_Document.UndoUtil`), already used by `EntityTagComponent` ("undoable"). Slash-command mutations should record undo records the same way.

## 7. Recommended build order (input to roadmap)

1. **Chat shell + auto-listening** — new component with `AddedToDocument` auto-start, singleton/port guard, custom attributes double-click → Eto chat window; header showing LLM / project / listener status.
2. **Selection context + free-form Ask** — `GH_Document.SelectedObjects` → existing serializer → `/llm/generate` via data-service; non-blocking, `InvokeOnUiThread` marshalling.
3. **Slash-command registry** — schema-driven `/dg-*` registry with autocomplete, argument hints, `/dg-help`; deterministic handlers, no LLM in the path.
4. **Mutating commands** — tag / mark / recognize / confirm / publish routed to existing services, with risk-gated confirm + GH undo.
5. **Retirement/deprecation of superseded components** + release notes + docs.

## Watch out for

- Blocking `SolveInstance` on the LLM call → Rhino freeze. **Highest-severity pitfall.**
- Background-thread UI mutation → hard crash on macOS.
- Auto-start without a singleton guard → port-bind race with multiple instances or multiple open documents.
- Slash commands that route through the LLM → non-deterministic behaviour for what the user expects to be a button.
- Silent GUID/port changes breaking saved `.gh` files without release notes.
