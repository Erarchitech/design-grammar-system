# Анализ исходных публикаций: место DeGram в Design Grammars

Статус: исследовательская часть, подготовлена основным агентом; синтез с литературой и исходниками ещё предстоит. Исходные PDF не изменены. Это архитектурная экспертиза предлагаемого milestone, а не редакционная рецензия или подтверждение публикационного статуса.

## 1. Что именно предлагают две статьи

P формулирует систему как посредника между **Model Domain** и **Grammar Domain** (с. 3–4, §2.1–2.2). Первый сохраняет геометрию и предметные модели, второй — правила, ограничения и семантические отношения. Shared Knowledge Core координирует их через идентичность и управляемые интерфейсы. P §2.3 (с. 5–6) отдельно допускает специализированные хранилища: граф — центральное семантическое хранилище текущего прототипа, но не требование скопировать в Neo4j все файлы, геометрию, временные ряды и документы.

T уточняет **онтологический контракт**, а не доказывает готовность всего многопользовательского продукта. §2.4 (с. 11) прямо разделяет schema-level, artefact-level и runtime-demonstrated evidence и исключает из доказанного user-level interoperability, governance, identity-conflict resolution и reliability of LLM-assisted authoring. §4 (с. 18–20) представляет организационную архитектуру и непрерывную синхронизацию как предмет будущей эмпирической проверки.

Отсюда позиция DeGram: **прикладная среда управляемых действий между человеком, корпоративным знанием и локальными авторскими системами**. Это конкретизация Communication/Integration и пользовательской оркестрации P; потребитель пяти графов T; не новый графовый слой, не новый reasoner и не онтологический объект, подменяющий DG Object.

### Два разных значения «пять слоёв»

S, слайд 17, различает communication/integration/orchestration/analysis/data storage. T §3.2 различает Ontograph/Metagraph/ComputGraph/ValidGraph/SpecGraph. Это разные архитектурные оси. Их нельзя механически сопоставить один-к-одному или вставить Agent шестым графом. P prose не перечисляет все пять сервисных слоёв столь же явно; слайд используется здесь только как вспомогательное обозначение.

## 2. Достоинства первоначального предложения

1. Локальный harness рядом с Revit/GH согласуется с разделением Model/Grammar Domain: инструменты выполняются в своей среде, граф хранит семантику и evidence.
2. Переиспользование `ui-v2` вместо второго Model Viewer сохраняет одну интерпретацию результата и снижает сопровождение.
3. Перенос v9.1 chat-функций в общую оболочку устраняет конкурирующие transcripts/command registries.
4. Явное подтверждение и локальный read-back согласуются с операторской ответственностью P §3 (с. 7) и tag–recognise–preview–confirm–publish T §4 (с. 20).
5. Разделение LLM-предложения и предметного evaluator сохраняет центральный смысл T: правила — долговечные адресуемые артефакты, а не текст в диалоге.

## 3. Существенные коррекции первоначального предложения

### 3.1 От CRUD к управляемому жизненному циклу знания

Первое предложение слишком одинаково трактовало редактирование трёх графов. T §3.2 (с. 12–14) определяет **общий Ontograph организации**, проектные правила/состояния/заметки и процессы vocabulary proposal → approval → release → impact/regression checks. Поэтому право editor на проект не должно автоматически давать право менять общую семантику всех проектов.

Минимальное улучшение: существующие пользовательские роли + отдельное полномочие vocabulary steward; проектный draft термина; разрешение против опубликованного словаря; утверждение и версия словаря; явное обновление зависимости проекта. Для пилота достаточно одного организационного каталога и явных released versions — не нужен сложный distributed ontology marketplace.

Кодовая миграция общей vocabulary требует проверки и владельца. Снятие `project`-фильтра не является корректной реализацией общего Ontograph. Если runtime остаётся project-scoped, это нужно назвать переходным режимом, а не выполнением T.

### 3.2 Intent и rationale должны пережить диалог

P §3.2 (с. 8) уже включает project documentation, search-then-summarise и operator-mediated edits; T §3.1/§4 включает Session и SpecGraph rationale. Первое предложение ставило это ниже graph CRUD и connector packaging. Для цели фреймворка это неверный приоритет.

Минимальный authoritative результат взаимодействия: исходный фрагмент brief/документа и его версия, интерпретированное требование, выбранная формализация, краткое утверждённое основание решения, затронутые объекты/правила, автор и дата. Длинный личный transcript Hermes — вспомогательная история, не корпоративная память проекта. Сохраняется краткое пользовательское обоснование, не скрытая цепочка рассуждений модели.

Достаточно расширить существующий SpecNote/Session и typed links; отдельный memory graph, vector DB и автоматическое накопление всего чата не требуются.

### 3.3 В центре интерфейса — объект и вопрос проектирования

T CQ1–CQ3 (с. 8, 21–24) дают готовые пользовательские операции: откуда правило, что оно проверяет, какой параметр связан, какому объекту принадлежит verdict. Поэтому основной экран — **объект/требование/изменение/результат**, рядом чат и существующие graph/model views. Пять графов остаются экспертной навигацией, а не обязательным маршрутом обычного архитектора.

Не следует сводить ontology, разрешения и обмен к универсальному prompt. Повторяемые операции должны иметь формы/кнопки и typed handlers; LLM выбирает и объясняет, но не нужен для каждого чтения, фильтра или запуска проверки.

### 3.4 Активация проекта — версия контекста, а не один projectId

Рекомендуемая session context tuple: корпоративный endpoint + user + project + vocabulary release + rule-set revision + CAD process/document + snapshot/revision + выбранная задача/вариант. Часть полей определяется автоматически, интерфейс показывает только существенные. Перед записью повторно проверяются project/document/revision. Context не должен храниться как один mutable глобальный active project на сервере.

### 3.5 Каноническая цепочка доказательства важнее общего graph browsing

T §3.2 (с. 13) называет REFERS_TO, ATTRIBUTE_OF, VALIDATES, ENCODED_AS, GROUNDED_IN, DERIVED_FROM. Необходимо проверить, какие из них реально создаются production-путём. Наличие ontology property или демонстрационного Cypher не доказывает end-to-end запись.

Приёмочная цепочка: **source revision → утверждённая rule revision → vocabulary version → mapping → native document snapshot → measured value/unit → evaluator/version → per-object outcome → решение пользователя**. Использовать существующие envelopes/specs; отсутствующий мост обозначать явно. Не подменять `DERIVED_FROM` ссылкой на изменяемый current Parameter без value/snapshot context.

### 3.6 История и удаления

T §3.3 (с. 14–15) требует immutable snapshots и сохранения результатов при новой редакции rule set. Значит, generic edit/delete, сохраняющий только текущее дерево atoms, недостаточен. Для использованных в расчёте правил/терминов нужны revision/supersession/retirement; физическое удаление допустимо для неиспользованного draft либо административной процедуры с impact check.

Минимально сохранить immutable accepted change record + before/after reference/hash и привязать run к точной rule revision. Не требуется event-sourcing всей системы или вечное хранение каждого keystroke. Отдельно должны существовать жизненный цикл draft, техническое выполнение операции, статус проверки и approval — одно поле `status` их смешивать не должно.

### 3.7 Операторский выбор не равен последней версии

«Опубликовано», «вычислено», «прошло выбранные проверки» и «принято руководителем» — разные события. P §3 утверждает первенство архитектора; это нельзя реализовать автоматическим выбором последнего/зелёного результата. В MVP нужна явная запись selected/accepted alternative с причиной, ответственным и ссылкой на evidence. Это не сертификация соответствия всем нормативам.

### 3.8 Editing в GH: сохранить пользу, ограничить обещание

P §3.1 (с. 7) использует существующий генератор Grasshopper/Kangaroo. Knowledge Core задаёт программу/ограничения; генератор вычисляет альтернативы. DeGram должен сначала помогать найти/подключить нужный параметр, собрать DG-обвязку и изменить выбранный блок, сохраняя solver у GH.

Полноценная synthesis произвольного definition и автоматический перевод каждого SWRL rule в вычислительную схему — отдельные задачи. Типизация портов доказывает совместимость connection, а не проектную корректность. `ATTRIBUTE_OF` показывает отношение к величине, но не доказывает, что она независимый управляющий slider, что зависимость монотонна или что её изменение устранит нарушение.

Сохранить bounded intent-based editing в MVP, чтобы не нарушить запрос пользователя: allowlisted компоненты, real GUID/ports, small patch, topology snapshot, undo/rollback, solve/readback. Произвольные script source/cluster internals/новые plugin installs — отдельные capabilities. Для пилота использовать реальные уже существующие definitions, а не писать новый генератор ради демонстрации агента.

### 3.9 Revit: mapping не завершает семантическую интероперабельность

T §2.2/§4/§6 (с. 9, 18–20, 26) сохраняет source-specific ownership и различает classification, identity и exchange. Связать UniqueId с dgId — необходимый, но недостаточный результат. Требуется bounded cross-platform information contract: конкретное свойство, unit, expected meaning, источник измерения, версия документа, allowed direction и conflict rule.

Полезный минимальный сценарий: настоящий Revit object/space и его свойства → привязка к DG object → сравнение с GH-derived property/требованием → объяснимый conflict/evidence. Не обещать «один DG ID делает все свойства взаимозаменяемыми». Для различающихся величин сохранять обе с provenance, а не last-write-wins. Общая многоплатформенная геометрическая синхронизация и произвольные Revit writes остаются вне базового MVP до решения пользователя.

### 3.10 CDE — владелец документа, DeGram — клиент

T §4 предусматривает четыре входа: parametric, BIM, CDE update, direct authoring. Первоначальный milestone полноценно прорабатывал только CAD/direct authoring. Минимальная CDE-связь обязательна как provenance: источник, version/hash, section/page, кто утвердил интерпретацию. Для пилота — ручной import/URI attachment и контроль новой редакции; автоматические коннекторы к каждому CDE позже.

DeGram не должен дублировать document approval, storage и revision control корпоративного CDE. Изменение документа формирует proposal/impact notification, но не автоматически переписывает принятый словарь и правила.

### 3.11 Клиент не нужен каждому наблюдателю

P различает domain expert и computational designer (§2.5), S слайд 19 добавляет client/lead architect. Desktop оправдан там, где требуется локальный CAD и agent tools. Клиент/проверяющий может использовать тот же web UI, не устанавливая CAD runtime. Единая среда означает общие контракты/данные/права, а не обязательную одинаковую локальную установку у всех. Это рекомендация, не отмена заявленного Desktop-доступа каждому участнику.

## 4. Утверждения статей, которые нельзя превращать в product assumptions

1. **P low temperature for deterministic output, с. 3:** низкая temperature не доказывает детерминизм LLM. Фиксированный формальный артефакт и versioned evaluator — отдельная граница воспроизводимости.
2. **P ontology prevents conflicts, с. 3–4:** непротиворечивость vocabulary не доказывает совместимость всех ограничений и выполнимость геометрического решения.
3. **P Table 1, с. 8:** ~45→~15 минут, ~30→<2 минут, 3–5→12–20 alternatives и ~95% retention — preliminary/controlled/self-reported; выборка и сопоставимость не достаточны для продуктовой гарантии. Точка сравнения DeGram должна быть современный DG web+addin, а не только ручной file-based процесс.
4. **T 'interpretation no longer principal bottleneck', с. 1/5:** это общая интерпретация выбранной литературы, не измерение надёжности DG authoring; проверить по первичным источникам.
5. **T Boolean verdict, с. 15:** будущий клиент должен потреблять актуальный typed evidence contract, включая non-verdict, а не возвращать систему к бинарной модели рукописи.
6. **T population + SHACL, с. 25:** одни targetClass shapes не гарантируют существование всех ожидаемых объектов. Локальный synthetic experiment (`standards/shacl-population-experiment.json`) показал conformant пустой граф. Нужен independent expected population/coverage manifest и проверка omission. Это не live regression DG.
7. **T BOT called W3C standard, с. 25:** статус следует брать из официального LBD источника, который обозначает BOT Community Group Report; термин нельзя переносить как W3C Recommendation.
8. **S generative SWRL, слайд 6:** вывод `PatternNode(?v)` классифицирует связанный объект; сам по себе он не создаёт CAD-геометрию. Программные операторы генерации и логические constraints должны быть разведены.
9. **T chronology/refinement, с. 26:** сравнение разных состояний не автоматически означает улучшение/реформулирование. Нужно фиксировать comparable scope, task/alternative partition и rule baseline. Не внедрять полный DesignSpaceGraph ради этой минимальной оговорки.
10. **T V8 deposit vs runtime:** публикационный artifact contract, демонстрационные записи и рабочий V7/V8 runtime не тождественны; владелец их alignment — существующий v11, а не незаметная миграция внутри Desktop.

## 5. Предлагаемый компактный процесс

1. Получить brief/изменение документа с версией и выбрать project/task.
2. Разделить утверждённое требование, предлагаемую интерпретацию и неформализуемое пожелание; сохранить rationale.
3. Разрешить термины против опубликованного vocabulary; для новых — steward proposal, а не тихий mint.
4. Согласовать rule revision и mapped objects/parameters; зафиксировать units и representation semantics.
5. Выполнить локальный bounded patch либо ручное моделирование в CAD.
6. Capture согласованного snapshot, проверка completeness/freshness, запуск нужного evaluator.
7. Рассмотреть результат в reused Viewer с переходом к source/rule/parameter; принять альтернативу либо вернуть задачу на уточнение.
8. Опубликовать утверждённые артефакты/evidence и краткое решение. Другой участник воспроизводит контекст без чтения чужого чата.

Чтение и обычные queries не требуют повторного approval; одна meaningful change proposal объединяет относящиеся к одному замыслу операции. Backend и CAD не образуют общей ACID-транзакции: successful local apply + failed publish должен сохранять понятное pending-publication состояние и безопасный retry, а не сообщать полный rollback.

## 6. Исследовательская проверка пользы

Базовое сравнение: **A — текущий DG web+addin; B — тот же DG backend через DeGram**. Не менять одновременно LLM, правила, datasets и UI и затем приписывать весь эффект harness. Третья ablation-конфигурация (по возможности) — DeGram с явными typed commands без NL agent; она отделяет пользу объединённого контекста от пользы LLM.

Задачи из P: rule authoring/refinement, изменение ограничения и повторная оценка альтернатив, handover независимому участнику, поиск/редактирование документационного знания. Добавить vocabulary conflict и реальные GH→DG→Revit mappings. Использовать одинаковые approved requirements, frozen rule snapshots, task counterbalancing; baseline и acceptance margins согласовать до измерения.

Метрики: полное время до правильного принятого результата (включая review/rework), setup effort, число ручных переносов/переключений, доля correctly formalized atomic requirements, source/rule/state trace completeness, false-pass/omission, обоснованный abstention, review burden, mapping conflict recovery, повторная работа получателя handover. Количество tool calls или количество созданных вариантов не являются самостоятельными показателями качества.

В исследовательском протоколе отделить correctness/traceability gates (блокирующие) от экономии времени (эмпирическая гипотеза). Нулевая ошибка на малой выборке не доказывает нулевой риск. Не заявлять масштабируемость/production readiness без отдельной нагрузочной и организационной проверки.
