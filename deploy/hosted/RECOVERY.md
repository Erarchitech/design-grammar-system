## Required transaction and restore protocol

1. Require explicit source/restore target/project identities and owner-approved operation scope, synthetic fixtures, duration/resources/network, backup destination, key custody and cleanup. The previous ingest/n8n approval is not assumed to authorize this larger recovery exercise.
2. Verify the source release revision/images and state mapping; refuse arbitrary volume names, existing restore destination, source=destination or broad workspace binds. Dry-run has zero service mutations.
3. Disable ingress/schedulers and stop all writers under permission. Verify stop/drain, not just command dispatch. No unattended backup against a changing multi-store state.
4. Export each store natively, hash bytes, record checkpoint boundaries and queue disposition. An interrupted export has no completion marker and cannot be sealed/accepted. Raw live-volume tar is not a consistent backup.
5. Encrypt the completed export for the approved recipient, authenticate its manifest, then transfer ciphertext to the approved current-PC directory. Verify ciphertext hash after transfer. Record completion atomically only after every step succeeds. Protected export scratch cleanup must be verified; failure is reported, not hidden.
6. Authenticate ciphertext, revision, key identity, complete inventory and all checksums **before** creating restore state. Restore into a new isolated project, never overwrite source/production. Keys → DB/graph/objects/n8n/DG files → services → read-only semantic verification → optional separately approved activation.
7. Verify users/login, memberships, two projects, model/object reads and hashes, a revoked session remains rejected, LLM settings key decrypt, n8n workflow/credential state and no stale queue replay. Do not call paid LLMs to test decrypt.
8. Record source-unmodified assertion, rollback, cold-start/reboot and measured RPO/RTO. Health alone is not a reviewer journey.

## Implementation boundary

An encrypted offline snapshot transport can exercise seal/authenticate/open on synthetic regular files. It cannot certify quiescence, native dump correctness, job drainage, database restore, storage durability or all HOST-04 assertions. Full `backup.py`/`restore.py` adapters and an authorized real multi-store trial are still required; no placeholder CLI is represented as a working backup.

`recovery_archive.py` now implements a size-limited reference `seal`/`open` CLI using RSA-OAEP-SHA256 and AES-256-GCM. It accepts an existing recipient PEM, exact framework revision, key-id and an explicit `export-complete.json` declaration. The marker is not proof of store consistency; anyone with the public key can seal data, so encryption does not authenticate exporter identity. Key custody remains external. No actual user keys were generated. Limits: 8 MiB plaintext including manifest, 9 MiB envelope, 1024 entries. Authentication, all hashes and paths are checked before restore staging. Existing output/restore destinations are never overwritten; Windows staging uses a protected DACL. See the module docstring for CLI usage and operational limitations.

Parent verification with scratch-only Python 3.14 + `cryptography==50.0.2` exercised actual synthetic seal/open, wrong key/revision, corrupt/truncated envelope, authenticated malformed manifests, interrupted export/publication, destination preservation, protected staging and Windows junction rejection. **24 tests: 23 pass, 1 skipped** because this host cannot create a symlink.
