# Synthetic capability package (not release)

Only on **DESKTOP-OS4Q8CP**, Windows 11, Docker Desktop Linux containers. No repository, Python, local credentials or existing DG installation is needed there. No Docker command is run on the development machine. Uses a dedicated project, three containers, three named volumes, no published ports, an internal network, generated in-memory credentials, and a disposable synthetic note. Pull/build requires target Internet access; it never invokes paid inference. The three images are version-tagged, **not digest-frozen**; this is not a release or production deployment.

1. Transfer only the ZIP and its SHA-256 separately. On the target, before expanding, verify `Get-FileHash -Algorithm SHA256 <zip>` equals the supplied full hash. Select an empty directory, run `Expand-Archive -LiteralPath <zip> -DestinationPath <empty-dir>` (PowerShell), then run:

   `powershell.exe -NoProfile -ExecutionPolicy Bypass -File <empty-dir>\deploy\hosted\sandbox\Run-Sandbox.ps1 -PackageZip <zip> -ExpectedZipSha256 <full-hash> -ReportPath <separate-empty-parent>\dg-1309-report.json`

   The script rechecks ZIP and every extracted file before ANY Docker invocation; it aborts on an unexpected file, symlink, wrong host, occupied project/port, low free disk or old Compose. Report path must be outside extraction; do not transfer logs, env files, Docker volumes or credentials. Review output report before sharing.

Runtime budget: 1 CPU and 1.25–1.5 GiB per container, combined maximum 3 CPUs/4 GiB; 256 PID/container; 12 GiB initial free disk; 20-minute build/pull, 5-minute start, 2-minute individual probes, 35-minute overall deadline; 4 named volumes (including isolated n8n evidence) and no host ports or host-gateway. The script always attempts `docker compose -p dg-hosted-1309-sandbox down -v --remove-orphans` **only for this project**. It does not prune images, build cache or other volumes. Check `docker compose -p dg-hosted-1309-sandbox -f <empty-dir>\deploy\hosted\sandbox\compose.yaml ps -a` after the run; if cleanup fails, stop and arrange owner-supervised cleanup only of this named project.

The data-service probe makes a real admin login, rejects an unsafe request without CSRF, ingests the named read-only `hosted-ingest` folder, checks exact synthetic `SpecNote` in isolated Neo4j, and rejects absent/private/escape paths. n8n's own CLI imports and executes the named mounted workflow; the `Read/Write Files from Disk` node reads `/files/workflows/sandbox-file-read.json`, the JSON extraction and Code node verify its content. A second n8n workflow attempts `/etc/passwd` with `continueOnFail`, checks that the read node returned the specific access-denied message, and only then writes a distinct fixed marker. Both markers are placed in a fresh disposable named volume, not in CLI stdout. A one-shot root container changes only that empty volume's ownership to UID 1000; normal n8n writes the markers and a separate one-shot Node verifier checks exact filenames and bytes (no extras) after each execution. CLI output is ignored, never parsed or copied to the report. A missing marker, wrong bytes, extra file, nonzero import/execute/verifier or missing read-node denial fails closed. This is synthetic workflow evidence, not an authenticated audit of n8n internals; a forged/malicious workflow could write a marker, so only the package's exact committed blobs and the isolated target are in scope. All results must be observed; no static PASS. Until a fresh target run, workflow node support and actual volume permissions remain unconfirmed.

Report includes only machine name, commit, ZIP hash, bounded check booleans/counts, status and cleanup status. Neo4j must first pass an authenticated `cypher-shell` health check (without putting the password in the process arguments) before data-service is started; `running` alone is insufficient for its startup index transaction.
